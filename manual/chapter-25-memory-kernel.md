# Chapter 25: Memory in the kernel

Part 6 began with the kernel: Chapter 22 designed the small core at the center of the system, what it does and what it does not do, with no layers for the sake of layers. Chapter 23 designed the boot: the firmware, the bootloader, and the first program, the shell, whose prompt is the first thing the user sees. Chapter 24 designed processes and scheduling: how the kernel names running programs, how it starts and stops them, and how it shares the two cores fairly between them. This chapter designs what those programs run in: the memory. Who owns what, how the kernel hands it out and takes it back, and how one program is kept from touching another's.

Four promises from earlier chapters meet here. Section 6.4 said the kernel's side of the out-of-memory story belongs to this chapter: what happens when the whole machine is out. Section 22.1 said the kernel owns the memory and hands it out, and how it hands it out is this chapter's design. Section 24.1 said the record holds how many bytes a program holds, and this chapter designs how the kernel tracks which runs those bytes are. And section 24.2 said how one core waits for the other when the shared list changes is this chapter's design. Each one is settled here.

There are two sections. The first designs who owns what: the record, the handing out, the taking back, and what happens when the machine is out. The second designs protection without waste: how the machine's own hardware keeps one program out of another's memory, and what happens when a program tries anyway.

One warning, stated up front the way Chapters 4 through 24 stated their own. This chapter designs memory in the kernel. It does not build it. No record exists yet, no hand-out has run, and no claim in this chapter says any of it does. The chapter claims no measured improvement on real hardware, so no scoreboard table is due. The numbers here are arithmetic on the chapter's own examples, counted by hand. No time is claimed anywhere in this chapter, because no hand-out has been measured on the target machine, and Chapter 3 forbids numbers without a method. The measured proof comes in Chapter 31, on the real PC.

## 25.1 Who owns what

Start with the job, in one sentence. The kernel owns the machine's memory, all 8 GB of it, and hands it out in runs, keeps the record of who has what, and takes it back when a program is done.

A run is a stretch of memory with one owner, one start, and one length. It runs without a break from its first byte to its last. A run belongs to one program, or to the kernel, or to no one, which means it is free. A program's memory is not one run: it is several, one for each thing the program holds, and the record names each one.

The record is the kernel's own list of runs, in the order they sit in memory, lowest start first. One entry per run, with four fields:

| Field | Bytes | What it holds |
| --- | --- | --- |
| Start | 8 | The first byte of the run, counted from the start of memory |
| Length | 8 | How many bytes the run holds |
| Owner | 4 | The number of the program that owns the run, from section 24.1, or 0 for the kernel's own runs and for free runs |
| Kind | 1 | What the run is for, one byte, eight kinds, listed below |

Count one entry by hand: 8 plus 8 is 16, plus 4 is 20, plus 1 is 21 bytes. The record costs 21 bytes per run it names.

Say why the start and the length are 8 bytes each, because the sizes are the design. Section 5.1 fixed the sizes: four bytes count to 4,294,967,295, which names the first 4 GB of the machine. The machine holds 8,589,934,592 bytes, twice that, so four bytes name only the first half of the memory. Eight bytes count to about 18.4 quintillion, far past the machine's 8 GB, so eight bytes name every byte in the machine with room to spare. The owner is 4 bytes because section 24.1 fixed program numbers at 4 bytes, and the owner is a program number. The kind is 1 byte because one byte counts to 255, and eight kinds need far less.

The record is binary, fixed-size entries the kernel reads directly, the way section 2.2 puts the binary form first, and one record serves every program, the kernel included, the way section 2.3 shares one form across the whole system.

The eight kinds are fixed here:

| Kind | Number | What it holds |
| --- | --- | --- |
| Free | 0 | No owner, waiting to be handed out |
| Code | 1 | A program's translated native code |
| Data | 2 | A program's data-section values, from section 9.2 |
| Pile | 3 | A program's pile, on the machine's own stack, from section 10.3 |
| Static | 4 | A program's name table, function mapping, and named-value slots |
| Heap | 5 | Memory a program asked for while running, the ask from section 6.4 |
| Log buffer | 6 | A program's debug log buffer, 1,024 bytes, from section 17.1 |
| Kernel's own | 7 | The kernel's own runs: its code, data, pile, log buffer, and record |

The data run and the static run are both static memory in section 6.3's sense: they live for the whole run and are released together, in the finish routine's fourth step, the way section 15.2 designed it. They hold different things: the data run holds the values from the file's data section, and the static run holds the name table, the function mapping, and the slots for named values. A program whose file has an empty data section holds no data run, the way the hello loop holds none. An arena from section 6.2 is one heap run, divided by the program itself and given back in one act.

The record starts at boot, and section 23.2 said the kernel's first act is to set it up. The kernel's own code and data are marked used, because the kernel is running in them. The bootloader's memory is released back to free, because the bootloader's job is done. The rest of the memory is free, waiting to be handed out. So the record at boot holds three entries: the kernel's own run, starting at byte 0, holding the kernel's code, data, pile, and log buffer; the record run, holding the record itself, with room for entries beyond the boot's three; and one free run, holding everything else, including the memory the bootloader ran in. Three entries, 21 bytes each, 63 bytes of record. The record lives in its own run because it grows: it grows the way a list grows, from section 5.2, a bigger run when it fills, the old contents copied, the old run freed. The kernel's own run holds what does not grow: its code, its data, its pile, and its log buffer.

Say how the kernel hands memory out. A program asks for a size, the ask from section 6.4, by calling the kernel's ask routine by number, the way section 16.1 calls a routine by number. The kernel walks the record from the start, in order, and takes the first free run big enough to hold the size. First big enough, not best fitting: finding the best fit would mean walking the whole record every time, and the first fit means the walk stops as soon as a run fits. If the free run is bigger than asked, the kernel splits it: the handed run takes the low end, the size asked for, and the free remainder keeps the high end, so the record stays in address order without rewriting. The record gains one entry for the handed run, and the free run's entry is updated to its new start and length. If the free run is exactly the size asked, there is no split and no remainder: the run changes owner, and the record gains no entry. The hand-out has one more step, and it belongs to the next section: the kernel tells the hardware the new run's boundaries, so the hardware's check knows them. Handing memory out is not a pause, the way section 1.3 measured a collector's pause: there is no collector and no sweep, and the hand-out is a walk of the record and a split, and then the program runs on.

Say how the kernel takes memory back. A program gives a run back when it is done, by calling the kernel's give-back routine by number, naming the run. The kernel marks the run free, and then it joins: if the run beside it, on either side, is free, the two become one run, one entry, and the joining repeats until no free neighbour is left. Joining is what keeps the record from filling with small pieces: without it, every hand-out and hand-back would leave the free memory in more and smaller runs, and the record would grow with every program that ran. With it, the free memory gathers itself back into whole runs, and the record shrinks as programs end. The record changes; the memory does not move. No program's memory moves when a neighbour is freed, because moving is copying and copying is waste.

Now say which runs the loader asks for, because the loader's eight steps from section 15.1 are where a program's runs come from. After the first four validity checks pass, the loader asks for the log buffer, 1,024 bytes, the way section 17.1 designed it: a file that fails the checks is not a program and gets no log. In the fifth step, placing the sections, the loader asks for the data run, if the data section holds anything, and for the static run, sized for the name table, the function mapping, and the slots for the named values, all of which the loader knows by then. In the sixth step, translating, the first pass counts how many native bytes the middle form becomes, the way section 10.3 designed it, and the loader asks for the code run of exactly that size, and the second pass writes the native instructions into it. In the seventh step, setting up the memory, the loader asks for the pile run, sized by the count below, and sets up the static slots in the static run. Four asks for a program with no data section, five for a program with one, and each ask is a walk of the record and a split. The asks are part of the startup cost section 1.4 counted: a program pays for its runs before its first operation runs.

Say how the pile is sized, because the pile is the one run whose size is counted, not read from the file. The loader counts the deepest the pile goes, on the first translation pass, a walk it already does. It tracks the values on the pile, operation by operation, and the return addresses the translation pushes for calls, and it takes the deepest total it sees. The count covers the program's own code: its own values and the return addresses its own calls push. A library routine's own use of the stack past its return address is counted when the library is built, and the loader adds the deepest frame of any routine the program calls. No library routine is built yet, so no frame is counted yet, and the book does not claim a pile size for a program that calls into the library. What the book claims is the rule: the pile is as big as the deepest pile the loader counts, and no bigger, because a pile bigger than the deepest pile is memory held for nothing.

Work one hand-out and one hand-back through, with the record counted before and after. The scene follows section 24.1: the shell is running as number 1, the tester is running as number 2, and the tester starts the hello loop as number 3. The shell holds five runs: code, data, static, pile, and log buffer. Its data run holds the command table, 95 bytes, the table section 21.1 counted, loaded into static memory the way section 23.2 said. The tester holds four runs: code, static, pile, and log buffer, because its file carries no data section. The record before the hello loop starts holds 12 entries: the kernel's own run, the record run, the shell's five, the tester's four, and the one free run. Twelve entries at 21 bytes each is 252 bytes of record.

The tester calls the kernel's start routine and names `hello`. The kernel's two checks pass, and the loader's eight steps run. The loader asks four times, in order: the log buffer, 1,024 bytes; the static run, 15 bytes; the code run, the count from the first translation pass; and the pile run, the count from the same pass. Count the static run by hand: the name table is 13 bytes, the way section 9.2 counted it, the function mapping is 1 byte, the count saying 0, and the slot for `count` is 1 byte, because `count` is a 1-byte number, the way section 17.2 counted it. Thirteen plus 1 plus 1 is 15 bytes. Each ask splits the free run, and the four new runs sit beside each other in memory, in the order they were asked: log buffer, static, code, pile, and then the free remainder. The record now holds 16 entries: 12 plus 4 is 16. Sixteen entries at 21 bytes each is 336 bytes of record. The hello loop's start costs the record 4 entries, 84 bytes.

The hello loop runs, prints `hello` three times, and reaches END. The finish routine's five steps run, and the runs go back in two steps. In the third step, free what the program owned, the pile goes back first: its neighbours are the code run, still held, and the free remainder, so it joins the remainder, and the record falls to 15 entries. The code run goes back next: its neighbours are the static run, still held, and the joined free run, so it joins that run, and the record falls to 14 entries. The log buffer goes back last in the step: its neighbours are the tester's last run, still held, and the static run, still held, so it joins nothing, and the record stays at 14 entries. In the fourth step, release the static memory, the static run goes back: its neighbours are the free log buffer on one side and the joined free run on the other, so all three become one run, and the record falls to 12 entries. Twelve entries, 252 bytes, the record back where it was before the hello loop started. The hand-out added 4 entries, the hand-back took 4 away, and the joining kept the free memory in one run.

Now settle the deferral from section 24.1: the running-program record holds how many bytes a program holds, and this chapter designs which runs those bytes are. The memory-held count is the sum of the program's runs, and the record is the truth it is checked against. The kernel adds a run's length to the count when it hands the run out, and subtracts it when it takes the run back, and it can check the count at any time by adding the lengths of the record's entries for that owner number. For the hello loop, the count is the sum of its four runs: the log buffer, 1,024 bytes, the static run, 15 bytes, the code run, the count from the first pass, and the pile run, the count from the same pass. One thousand twenty-four plus 15 is 1,039 bytes the book counts, plus the code run and the pile run as the loader counts them. The user sees the count through the list of running programs from section 24.2: this chapter adds one field to the entry the running call hands back, the memory-held count, 8 bytes, so the user can see what each program holds, not only that it runs. The kernel does not log every hand-out: the record is the record of hand-outs, and the log holds starts, ends, and failures, the way section 22.2 said the kernel logs the acts, not the calls.

Now settle the deferral from section 6.4: what happens when the whole machine is out. The ask fails cleanly, code 4, out of memory, the way section 6.4 designed it. The four steps run as the program's side designed them: the program asks, stating the size; the request fails cleanly, a clear no; the failure comes back as an error the program can see and handle, code 4, an error value the way section 7.3 designed errors; and the program decides what to do: ask for less, wait and ask again, or give up cleanly. The kernel's side, this chapter's design, is three refusals. No program is killed to make room: killing a program to feed an ask would break the ownership section 6.1 requires, because the killed program owned its memory and had not given it back. No memory is taken from a running program: the kernel hands out only what is free, and what a program holds is that program's until it gives it back. And no ask waits in a queue for memory to come free: the ask fails at once, and the program decides, because a queued ask is a program waiting on a hope, and the program that asked is the one that knows whether waiting is worth it.

Say one honest limit about the failure, because the failure has a shape a reader must not learn by surprise. The ask fails when no single free run is big enough, even if the free bytes added together would cover it. A run is one stretch, and the kernel does not stitch free runs together across a used run, because stitching across a program's memory would mean moving that program, and the kernel does not move a program's memory once it is placed. A machine with 1,000 free bytes in ten runs of 100 cannot serve an ask for 500, and the ask fails with code 4. Joining keeps the pieces as large as they can be, and the limit is what is left after joining.

Now settle the deferral from section 24.2: how one core waits for the other when the shared record changes. The target machine has two cores, from section 3.1, and only one core changes the record at a time. The record has a hold, one value in the kernel's own memory, naming which core holds it, 0 when no core holds it. A core that wants to change the record takes the hold first, makes its change, and gives the hold back. Taking the hold is one act the hardware does whole, so two cores cannot both take it at the same moment: the machine has the hardware for this, and the book uses it, it does not design it. If both cores ask at the same moment, the lower-numbered core goes first, a fixed rule, stated here. The other core waits, and it waits by asking again, not by sleeping, because a sleeping core is a core doing nothing, and the hold lasts only for one change, a few entries, so the wait is short and the asking is cheaper than the sleep and the waking. The same rule covers the waiting list from section 24.2, the list both cores share: the list has its own hold, separate from the record's, so a core changing the memory record does not block a core changing the waiting list, and a core that finds the list held waits by asking again, the same way. One rule, two records, and no core sleeps while a change is waiting.

Say what the record costs, honestly, per rule 7 of section 1.5. The record costs 21 bytes per entry: 63 bytes at boot, 252 bytes with the shell and the tester running, 336 bytes with the hello loop running beside them. Each running program adds one entry per run it holds, 4 entries and 84 bytes for the hello loop, 5 entries and 105 bytes for the shell. A program that asks for heap memory adds one entry per ask, so the record grows with the asks, and shrinks as the runs go back. The record run holds the entries plus room to grow, the way a list holds room to grow, and the room is the list's shape, not waste. The record is small beside the memory it names: the worked scene's 336 bytes fit easily in the 32 KB data cache on each core from section 5.3, 32,768 bytes, so the hand-out walk reads the fastest cache the chip has. The record holds 1,560 entries inside 32,768 bytes, 1,560 times 21 is 32,760, so it stays in the fastest cache long past any scene this book works through. The hand-out costs a walk of the record, one forward pass that stops at the first run big enough, and the hand-back costs a join, and the chapter claims no time for either, because Chapter 31 measures them. The record is stated, not hidden, the way section 2.4 requires: every field named, every byte counted, in this chapter.

## 25.2 Protection without waste

Start with the job, in one sentence. Protection means one program cannot read or write another program's memory, and no program can read or write the kernel's memory, and the check costs the kernel no extra work and the data no extra copy.

Say what protection means, in plain words, before designing it. Every byte of memory belongs to one owner, the record in section 25.1 says who, and a program may touch only the bytes its own runs hold. A program that reads another program's memory reads what it does not own, and a program that writes it changes what it does not own. And the kernel's memory belongs to the kernel: no program reads it, no program writes it, because a program that could write the kernel's memory could rewrite the record, and a record a program can rewrite is a record that protects nothing.

Say how it is done without waste. The machine's own hardware checks each read and write against the record. The machine has the hardware for this: the same hardware every modern machine uses to keep programs apart. The book does not design the hardware, it uses it. When the kernel hands a run out or takes one back, it tells the hardware the boundaries that changed, and the hardware checks each read and write against them as the program runs. The check costs no extra work in the kernel, because the kernel does no checking: it hands the hardware the boundaries once, at the change, and the hardware does the checking. It costs no extra copy of the data, because the program reads and writes its own memory in place, and the hardware checks the address, not a copy. And it costs no second record, because the kernel keeps one record, the record from section 25.1, and the hardware's check reads the boundaries from it.

Say what happens when a program touches memory it does not own. The hardware stops the program, at the read or the write that crossed the line. The kernel reports it in plain words, naming the program's number, and the program ends, the way a program stopped from outside ends per section 24.1: the finish routine does not run, and the book says so plainly. Open files are not flushed, and the bytes still waiting in memory are lost; files already closed are safe. The kernel takes back the memory the record names for that program, frees its runs, joins them with their free neighbours, and removes its entry from the running-program record. The report goes to whoever started the program, naming the number and saying the program was stopped. The other programs keep running.

Work one protection failure through, step by step. The program is the word counter from section 16.1, running as number 4, the way section 24.1 ran it. The counter is counting words, and a mistake in its own code writes past the end of its pile: the write names an address one byte past the pile run's last byte. The address belongs to no run of number 4, because the pile run ends where the write begins. The hardware checks the write against the counter's runs, finds the address outside them, and stops the program, before the byte is written. Nothing is changed: the byte is never written, and no other program's memory is touched.

The kernel reports it. The report goes to the tester, number 2, which started the counter, in plain words, naming the number: program 4 tried to write memory it does not own, and was stopped. The kernel writes one line to its log, the way section 22.2 designed it: `1794700800 stopped counter 4 protection`. The line is 39 characters plus the newline, 40 bytes: the time, 10 digits, a space, `stopped`, a space, `counter`, a space, `4`, a space, and `protection`. The kernel takes back the counter's runs, frees them, and joins them with their free neighbours. The counter's entry leaves the running-program record. The shell, number 1, and the tester, number 2, keep running. One program stopped, two kept running, and the record shows the counter's memory free again.

A read past the line is stopped the same way as a write: the hardware checks reads and writes alike, and a program that reads another program's memory is stopped at the read. And the kernel's memory is checked the same way: a program that reads or writes an address in the kernel's own run is stopped at the act, because the kernel's run belongs to owner 0, and no program number is 0.

Say what the kernel does not do, because the refusals are the design. It does not copy memory to protect it: no copy of the memory is made before the program runs, because the copy would double the memory and double the work, and the hardware check protects the memory where it sits. It does not check every read and write in software: a kernel that checked each one itself would spend more on the check than on the act it guarded. It does not keep a second record for protection: one record names the runs, and the hardware's check reads the boundaries from it, so there is nothing to keep in step and nothing to go stale. And it does not move a program's memory once it is placed, because moving is copying and copying is waste: a run handed out stays where it was handed out, from the hand-out to the hand-back, and the record changes around it, never under it.

Say what protection costs, honestly, per rule 7 of section 1.5. The record itself costs bytes, and section 25.1 counted them: 21 bytes per entry, 63 bytes at boot, 336 bytes with three programs running. The hardware check costs time, and the book does not measure it here: how long the check takes on each read and write, and whether it slows the programs that run, is Chapter 31's measurement, on the real PC. The hand-out and the hand-back each tell the hardware the boundaries that changed, and that telling is part of the hand-out's cost, counted in steps, not in time. What protection does not cost is a copy, a second record, or a check in software, and the chapter claims those as designs, not measurements, because nothing here is built yet.

The test suite grows with this chapter. Eight new tests cover memory in the kernel. Four cover the record: a hand-out splits a free run and the record gains one entry; a hand-back joins free neighbours and the record shrinks back; the hello loop's start and stop take the record from 12 entries to 16 and back to 12; and the memory-held count equals the sum of the program's runs. Two cover the failures: an ask bigger than any free run fails with code 4, and no program is killed and no memory is taken; and two cores changing the record at once change it one at a time, the other waiting by asking again. Two cover protection: a program that writes past its pile is stopped, its memory is taken back, and the other programs keep running; and a program that reads another program's memory is stopped at the read. That is 8 new tests, and the suite grows from 137 to 145: 137 plus 8 is 145. Each test runs on the target PC, the way section 2.5 demands.

This chapter adds no new routines to the core library. The ask call and the give-back call are the kernel's own calls, numbered the same way the library's routines are numbered, in Appendix A, the way section 22.2 designed it. The library stays at 35 routines, and the suite grows to 145 tests.

---

Memory in the kernel is one record, kept by the kernel, of who owns what: runs with a start, a length, an owner number, and a kind, 21 bytes per entry, 63 bytes at boot. The kernel hands a run out to the first free run big enough, splitting it when it is bigger than asked, and takes it back by marking it free and joining it with its free neighbours, so the record does not fill with small pieces. One start and one stop worked through by hand show the proof: the hello loop takes the record from 12 entries to 16 and back to 12, and its memory-held count is the sum of its runs. When the whole machine is out, the ask fails cleanly with code 4, no program is killed, no memory is taken, and the program that asked decides. One core changes the record at a time, and the other waits by asking again, not by sleeping, and the same rule covers the waiting list. Protection is the machine's own hardware checking each read and write against the record, so the check costs the kernel no extra work and the data no extra copy, and a program that writes past its pile is stopped, reported by number, and ended, while the other programs keep running. No new routines join the library, and the suite grows from 137 tests to 145.
