# Chapter 30: The full system image

Parts 1 through 6 designed the whole system, one piece at a time: the language, the file format, the compiler, the library, the tools, the shell, the kernel, the boot, the filesystem, the drivers, the services, and the rules that say what any of it may do. This chapter opens Part 7, and Part 7 is about proof and delivery. Its first job is to put the pieces together. The system image is one file holding the whole system: every program and every record the machine needs to boot and to work, laid out block for block the way Chapter 26 designed the disk, so that Chapter 33's install can write it to a disk and Chapter 23's boot can run from it.

Two promises from earlier chapters meet here, and both are about counting. Chapter 26 fixed the layout and the first fixed places, the bootloader's, the kernel's, and the shell's, and left the filesystem service's own place to this chapter, because the kernel must find that file before any filesystem exists to ask. Chapter 28 fixed that every service starts from its fixed place and left all four places to be counted here. Chapter 29 fixed the permission record's shape and left its first form, the entries the system ships with, to this chapter. This chapter settles all three.

There are two sections. The first designs what goes in the image and what stays out: the contents, the fixed places counted in full, and the permission record's first form. The second designs building the image from scratch: the steps in order, what the build reports, and what it refuses to do.

One warning, stated up front the way Chapters 4 through 29 stated their own. This chapter designs the system image and its build. It does not build either one. No image exists yet, and no claim in this chapter says one does. The chapter also claims no measured improvement on real hardware, so no scoreboard table is due. The numbers here are arithmetic on the chapter's own layout, counted by hand: blocks, bytes, entries. No time is claimed anywhere in this chapter, because no image has been built or booted on the target machine. No code size is claimed anywhere either, for the reason Chapter 22 gave: the code is not written yet, and a size claimed for unwritten code would be a made-up number. What this chapter counts is room, places, and records. The files' true sizes are the build's to report, and the measured proof comes in Chapter 31, on the real PC.

## 30.1 What goes in, what stays out

Start with the job, in one sentence. The image holds every piece of the system, each in the place the layout gives it, and nothing else.

Say what goes in, one piece at a time, each tied to the chapter that designed it.

The bootloader comes first, because the firmware looks for it first. It sits at the start of the disk, blocks 0 to 63, where section 23.1 designed the firmware to find it, before all the filesystem's places. It is stored as native code, the one exception to translated at load, because the firmware runs native code and no translator is running yet. It carries the loader's eight steps, the translator, and the disk and screen drivers in native form, so those pieces live twice, one source in two stored forms, the cost section 23.1 stated in the open. Its place is counted below with the rest. What the build puts in the place is the build's report, not this chapter's claim: the chapter counts the room, and the build counts the code.

The kernel is next. Its file sits at its fixed place carrying its five driver modules inside it, the screen, the keyboard, the disk, the network, and the clock, because section 27.1 fixed that a driver is a module of the kernel, loaded with the kernel and living in the kernel's memory. So there are no driver files at places of their own. The disk and screen drivers appear a second time inside the bootloader, in native form, and that is the stated exception above, not a second set of driver files.

The shell is next, at its fixed place: the first program, the user's prompt, with the file tools and the text tools joined into it as library calls, the way section 21.1 designed them.

The four services follow, each at its own fixed place, counted below: the filesystem service from Chapter 26, and the time, network, and update services from Chapter 28. Each starts when its job is first needed, never at boot, and the kernel starts it from its place.

The rest of the system lives in the general space, as files in the top folder, named by the top folder's record. The core library file, holding the 39 routines from Chapter 16 that programs call by number. The compiler, from Chapters 11 to 13, and the build tool, from Chapter 14: both go in, because the image can rebuild itself, and Chapter 13's self-hosting is completed in the shipped system, not left as a test the book once ran. The developer tools from Chapter 20: the formatter, the checker, the tester, and the debugger, with the test suite the tester runs, because Chapter 31 proves the installed system by running that suite on it. And the permission record, the file named `permissions` in the top folder, in the first form counted below. Every one of these files is a Chapter 9 file, the same header and the same sections, the way section 9.2 defined them: the image holds no special kind of file.

Now the fixed places, counted in full, settling the deferrals from Chapters 26 and 28. Section 26.1 fixed the first four rows of this table. This chapter fixes the four service rows, in the order the kernel needs the services: the filesystem service first, because every file found by name waits on it, then time, network, and update, the order Chapter 28 designed them in. Each service place has the same shape as the kernel's and the shell's places from section 26.1: an 8 byte size record first, then the file's bytes in one long run, so the kernel reads any of them the same way, size first, then that many bytes, needing no filesystem to do it. That shape is the whole reason the filesystem service's place is fixed by the layout itself: the kernel must be able to find the service's file before the service exists, so the file cannot live in the general space like an ordinary file, found through the service's own records. The other three services are placed the same way, so starting a service is one act with one shape, whichever service it is.

| Place | Blocks | Bytes | What it holds |
| --- | --- | --- | --- |
| Bootloader's place | 0 to 63 | 64 blocks, 262,144 bytes | The bootloader, as native code |
| Kernel's place | 64 to 1087 | 1,024 blocks, 4,194,304 bytes | A size record, then the kernel's file, with its five drivers inside |
| Shell's place | 1088 to 1343 | 256 blocks, 1,048,576 bytes | A size record, then the shell's file |
| Top folder's entry | 1344 | 1 block, 4,096 bytes | The top folder's entry, from section 26.1 |
| Filesystem service's place | 1345 to 1600 | 256 blocks, 1,048,576 bytes | A size record, then the filesystem service's file |
| Time service's place | 1601 to 1664 | 64 blocks, 262,144 bytes | A size record, then the time service's file |
| Network service's place | 1665 to 1792 | 128 blocks, 524,288 bytes | A size record, then the network service's file |
| Update service's place | 1793 to 1920 | 128 blocks, 524,288 bytes | A size record, then the update service's file |
| The general space | 1921 to 244,140,624 | 244,138,704 blocks | The folder records and the files |

The sizes of the service places are design choices, stated as choices. The filesystem service gets the shell's size, 256 blocks, because its job is the largest of the four: it owns every folder record on the disk and rebuilds the free record at its start. The time service gets 64 blocks, the bootloader's size, because its job is the smallest: it learns the world's count and asks the kernel to write it. The network and update services get 128 blocks each, between the two. The kernel's place is 1,024 blocks, 4 MiB, and the shell's is 256 blocks, 1 MiB, both from section 26.1.

Count the fixed region in the open. 64 blocks for the bootloader, plus 1,024 for the kernel is 1,088, plus 256 for the shell is 1,344, plus 1 for the top folder's entry is 1,345, plus 256 for the filesystem service is 1,601, plus 64 for the time service is 1,665, plus 128 for the network service is 1,793, plus 128 for the update service is 1,921 blocks, blocks 0 to 1920. In bytes, 1,921 times 4,096 is 7,868,416 bytes. The general space is what is left of the disk from section 26.1: 244,140,625 blocks in all, minus 1,921, is 244,138,704 blocks, running from block 1921 to block 244,140,624.

Now correct an earlier count in the open, the way Chapter 24 corrected Chapter 22's log count. Section 26.1 counted the general space as blocks 1345 to 244,140,624, 244,139,280 blocks, and section 26.2's rebuild of the free record starts its one free run at block 1345. Both counts were made before the services' places were fixed, when the only fixed places were the ones Chapter 26 itself set. The four service places take 576 blocks, 256 plus 64 plus 128 plus 128, out of the front of that space. So the general space starts at block 1921, not 1345, and holds 244,138,704 blocks, not 244,139,280: 244,139,280 minus 576 is 244,138,704, and the two counts agree. The rebuild in section 26.2 runs its first free run from block 1921 to block 244,140,624, and everything else in that section stands as written. Read the whole fixed region's cost honestly, per rule 7 of section 1.5: the fixed places reserve 7,868,416 bytes of the disk's 1,000,000,000,000, whether the places are full or nearly empty, because a place that can move is a place the boot cannot find. The cost is stated, not hidden, the way section 2.4 requires.

Say what a place's size is, and what it is not, because the difference is this chapter's honesty about unwritten code. A place's size is room set aside: counted, fixed, and known before any code exists. The file inside the place is whatever the compiled code comes to. That size is not known here, is not claimed here, and becomes known only at the build, which reports it, the way Chapter 22 claimed no size for the kernel and Chapter 23 counted the kernel file's shape and stopped there. A file that comes out bigger than its place fails the build, in plain words, the way section 30.2 designs: the build stops and says which file outgrew which place, and no image is called done. Making a place bigger is a change to this layout, a new first block for everything after it, and it belongs to a later version of the system, not to a quiet edit. Chapter 34 takes up what changes after v1.

Now the permission record's first form, settling Chapter 29's deferral. Section 29.1 fixed the shape: one entry per program, the name in the shape section 4.3 fixed, a length byte and the characters, plus one byte of acts, one bit per guarded act, in the order section 29.1 fixed: start, stop, read outside, write outside, device, talk, set time, update. The first form holds an entry for each system program whose job needs a guarded act, or whose limits the book has designed one by one. Each entry is set wide enough for the program's job and no wider, and the reason for each is stated with it.

| Program | Acts it may do | Why |
| --- | --- | --- |
| `shell` | Start, stop, read outside, write outside, set time, update | The shell is the user's hands at the prompt. It starts and stops the programs the user names, the stop command from section 24.1 among them. The file tools joined into it work on the folders the user names, so it reads and writes outside its own folder, as the user's hands, on the user's typed commands and never on its own. And the user's asks to set the time and to run an update travel through it, the way Chapter 28 designed. It holds no talk and no device: the shell itself opens no talks, and it uses only the screen and keyboard it was started with |
| `filesystem` | Read outside, write outside, device | The whole disk is its job. It drives the disk through the disk driver, and it reads and writes every folder's records and every file in them, for whichever program asked |
| `time` | Talk | When the user asks it to check the time, it opens a talk through the network service to ask a machine that keeps time, the way Chapter 28 designed. Setting the clock itself is the kernel's act at its ask, and needs no act in its own entry |
| `network` | Device | It drives the network hardware through the network driver. The talks it carries are opened by programs whose own entries allow talk; carrying them is its job, not an ask of its own |
| `update` | Talk, read outside, write outside | Its run from Chapter 28: fetch a package through the network service, read a package file the user already has, place the new files and move the old versions aside, across the folders and the fixed places its job names |
| `build` | Start, read outside, write outside | The build tool works in the user's project folders, not its own: it reads the sources there, keeps its record there, and writes the built file there, the way section 14.1 designed. And it runs the tests as step five of the build, and running a test is starting a program |
| `tester` | Start | It runs the programs it tests, the way Chapter 24's worked example showed it starting the hello loop |
| `compiler` | Read outside | It reads the source files of the project it is compiling, which live in the user's folders. It starts nothing and places nothing: the build tool does the joining, the writing, and the testing |

The remaining developer tools, the formatter, the checker, and the debugger, ship with no entry at all, which is the default entry from section 29.1: they may run, work in their own folder, and do no guarded act until the user widens them. The kernel holds no entry, because nothing starts the kernel by an ask: the bootloader starts it, the way the boot starts the shell without a check. The core library holds no entry either, because it never runs as a program: its routines run inside the programs that call them. And the bootloader holds none, because it is native code that runs before the record can be read.

Count the first form by hand, the way section 29.1 counted its example. Each entry is the name, a length byte plus the characters, plus 1 byte of acts. `shell` is 1 plus 5 plus 1, which is 7 bytes. `filesystem` is 1 plus 10 plus 1, which is 12. `time` is 1 plus 4 plus 1, which is 6. `network` is 1 plus 7 plus 1, which is 9. `update` is 1 plus 6 plus 1, which is 8. `build` is 1 plus 5 plus 1, which is 7. `tester` is 1 plus 6 plus 1, which is 8. `compiler` is 1 plus 8 plus 1, which is 10. Add them in the open: 7 plus 12 is 19, plus 6 is 25, plus 9 is 34, plus 8 is 42, plus 7 is 49, plus 8 is 57, plus 10 is 67 bytes. The permission record's first form is 67 bytes, eight entries, in one small file in the top folder. The user can narrow or widen any entry after install, the way section 29.1 designed, and can remove the record whole: the first form is the system's starting answer, not a lock on the owner.

Now say what does not go in, because the refusals are half the design. The file tools and the text tools do not go in as separate programs: they are joined into the shell as library calls, the way section 21.1 designed, and a second copy of each as its own file would be a second form of the same work, which section 2.3 forbids. The user's own programs and files do not go in: the image is the system only, and the user's work arrives after install, into the general space, the way Chapter 33 designs. Logs do not go in: a log is written as a program runs, the way Chapter 17 designed, so the image ships no log files and no logs folders, and each is created when the first line is written to it, the way section 23.2's boot log waited for the filesystem service to open its file. Test data and build leftovers do not go in: the build's record, its temporary files, and the scratch of compiling are the build's working, not the system, and none of it is in the image. And no second copy of anything goes in, beyond the one stated exception: the bootloader's native form of the loader, the translator, and the disk and screen drivers. One shared form from top to bottom, the way section 2.3 requires, and the image holds nothing the book has not named, the way section 2.4 requires.

## 30.2 Building the image from scratch

Start with the job, in one sentence. The build takes the system's sources and the bootstrap compiler, and nothing else, and produces the image, with every file checked, placed, and counted.

From scratch means exactly that, stated plainly: no Riza binary is used that the build did not just make. The only tool the build starts with is the bootstrap compiler from Chapter 11, the smallest compiler that works, built first in an existing language. Everything else in the image is built by a compiler this build produced. The steps are in order, and the order follows what needs what, the way section 14.1's build steps followed each other. There are eleven steps.

First, gather the inputs: the sources of every program in the system, and the bootstrap compiler. Nothing else is an input. No downloaded tool, no library from another system, no file the build cannot account for.

Second, the bootstrap compiler compiles the compiler's source, and the output is the first Riza-built compiler, R1, in the naming section 13.2 fixed.

Third, run the bootstrap test from section 13.2, inside the build. R1 compiles the same source, and the output is R2. The build compares R1 and R2 byte for byte. If they differ, the build stops here, in plain words, because a compiler that cannot reproduce itself cannot be trusted to build the system. If they agree, R2 compiles the source once more and the output must agree again: the test runs until the output no longer changes. The compiler that comes out of this step is the self-hosted one, and it builds everything after this step, and it is the compiler that goes into the image.

Fourth, build every other program with that compiler, each one by the build tool's shape from section 14.1: compile, join, optimize, write under a temporary name, run its tests, move into place only on pass, and report. The core library. The kernel, with its five driver modules compiled into it. The shell. The four services. The build tool itself, built here like everything else, because the ladder is down and every build is Riza building Riza. And the developer tools, the formatter, the checker, the tester, and the debugger. Each program is also packaged, in the format section 14.2 designed, because Chapter 14 closed by fixing that the system image is built from programs installed as packages: the package is the unit the system is built from, for the system's own programs exactly as for the user's.

Fifth, translate the bootloader into native form. The bootloader's sources are the same sources as everything else: the loader's eight steps, the translator, and the disk and screen drivers. The self-hosted compiler's translator turns them into native code once, here, and that native code is what goes into the bootloader's place. This is the one exception to translated at load, made for the firmware's reason from section 23.1, and it is made from the same source as the middle form copies, never from a second source.

Sixth, run the six validity checks from section 9.4 on every file the build is about to place: magic, version, sizes, bounds, references, value shapes. Every file passes all six before anything is placed. A file that fails a check stops the build, in plain words, naming the file and the check, and nothing is placed at all.

Seventh, place the fixed files. The bootloader's native code goes to blocks 0 to 63. The kernel, the shell, and the four services go to their places from section 30.1, each in the crash-safe order section 26.2 designed: the file's bytes are written first, and its size record is written after it, so no place ever names a file that is not there whole. A half-placed image is not an image, and this order is what keeps a stopped build from leaving a place that lies.

Eighth, write the general-space files: the core library, the compiler, the build tool, and the developer tools, each placed from its package into the top folder, checked the way section 14.2's install checks a package.

Ninth, write the permission record's first form, the 67 bytes counted in section 30.1, as the file `permissions` in the top folder.

Tenth, write the top folder's record last: the entry at block 1344 and the top folder's entries file naming every file in the general space. The record that names a thing is written after the thing, the rule section 26.2 fixed for a file's entry, applied here to the whole folder: when the record exists, everything it names is already there, whole and checked.

Eleventh, report, in plain words, the way section 14.1's report answered section 2.4's test. The build reports every file's real size. For each fixed file, its size is reported beside its place's size, so the reader sees the room and what fills it, side by side. It reports the bootloader's true size in its place, settling what Chapter 26 left to the image: the place is 262,144 bytes of room, and the build says how much of it the native code takes. It reports the general-space files' sizes and the image's total bytes. The build is where sizes stop being design and become fact: until this report, every size in this book is a place, a shape, or a hand-counted example, and Chapter 31 will measure the built image itself on the real PC.

The build fails cleanly, the way section 7.3 designs a clean no. Any step that fails stops the build: a bootstrap comparison that differs, a test that fails, a file that fails a check, a file that outgrows its place. The report names the step and the reason in plain words, and no partial image is called done. The last good image, if there is one, is untouched, the same rule the build tool keeps for a program's file in section 14.1.

Say what the build does not do, because the list keeps it one job. It does not install: writing the image to the machine's disk is Chapter 33's design, and the build only produces the file. It does not run the system: Chapter 31 boots the built image on the real PC and measures it there. And it needs nothing from the network and nothing paid, the way section 3.2 fixed: offline first, hard $0. The first builds run on the target machine under today's system, because there is no Riza to run them on yet. Once the image boots, the same build runs on Riza itself, from the sources the image carries and the compiler the image contains, and rebuilds the image whole: self-hosting at the level of the whole system, the ladder from Chapter 11 finally out from under everything.

The test suite grows with this chapter. Eight new tests cover the system image. Three cover the build: a build from the sources and the bootstrap compiler alone produces the image, using no Riza binary the build did not just make; the bootstrap test inside the build ends with the output no longer changing, and the compiler in the image is that self-hosted compiler; and a build stopped at any step reports the step and the reason and calls no partial image done. Two cover the checks and the places: every file in the image passes the six validity checks, and a file made to fail one stops the build with nothing placed; and a file made to outgrow its place fails the build, naming the file and the place. Three cover what the built image holds: the fixed places read back as counted here, the kernel at block 64, the shell at 1088, the filesystem service at 1345, the time service at 1601, the network service at 1665, the update service at 1793, and the general space from 1921; the permission record's first form reads back at 67 bytes, with the eight entries counted in this chapter; and the top folder's record names every general-space file in the image, the image holds no second copy of anything beyond the bootloader's stated exception, and the free record rebuilt on the built image covers the general space from block 1921, the corrected count. That is 8 new tests, and the suite grows from 177 to 185: 177 plus 8 is 185. Each test runs on the target PC, the way section 2.5 demands.

This chapter adds no new routines to the core library. The image and its build use the compiler, the build tool, and the tester already designed, and name no new call for a program to make. The library stays at 39 routines, and the suite grows to 185 tests.

The chapter counts as done when the image is built on the target PC from section 3.1: the build runs from the sources and the bootstrap compiler alone, the bootstrap test's output no longer changes, every file passes the six checks and sits at the place counted here, the permission record's first form reads back at 67 bytes, and the image's sizes are measured in Chapter 31. Until that run happens, the chapter's claims are marked plainly as waiting for the real-PC run, the way part 5 of the done test in section 3.3 requires.

Chapter 31 boots the built image on the real PC and measures it: the file sizes against their places, the boot itself, and everything the earlier chapters deferred to measurement. Chapter 32 benchmarks the whole stack against today's, and the image's total size is one of the numbers it compares. Chapter 33 designs install, update, and recovery: install writes this image to the Mint PC, and updates swap files at the places counted here, with the size record written last. Chapter 34 designs what comes after v1, and what to never add, and growing a fixed place is among the later layout changes it weighs.
