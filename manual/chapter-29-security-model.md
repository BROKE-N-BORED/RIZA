# Chapter 29: Security model

Part 6 began with the kernel: Chapter 22 designed the small core at the center of the system, Chapter 23 designed the boot, Chapter 24 designed processes and scheduling, Chapter 25 designed memory in the kernel, Chapter 26 designed the filesystem, Chapter 27 designed the drivers, and Chapter 28 designed the services. This chapter designs the last piece of the operating system: the security model, the rules that say what a program may do, and what happens to code the user did not write and has not yet trusted.

Five promises from earlier chapters meet here. Section 22.1 fixed that the kernel does not decide what the user is allowed to do: permissions are data the user owns, the kernel reads the data and follows it, and the error code for a refused start is this chapter's to fix. Section 24.1 left the codes for a refused start and a refused stop here too. Section 27.1 fixed that a driver does not decide policy, and the kernel reads the permission data before a call reaches a driver. Chapter 28 fixed that who may ask the update service to run and who may set the time is this chapter's design. And section 16.2 promised true randomness for security, for secrets and keys, and left its design here.

Start by separating two designs the book has kept apart on purpose, because confusing them is how security models go wrong. Protection, Chapter 25's design, is about memory: a program cannot read or write memory it does not own, the machine's own hardware checks every read and write against the kernel's record, and no asking is involved. A program does not request protection and cannot talk its way past it. Permission, this chapter's design, is about acts: what a program may do, starting another program, opening a network talk, writing outside its own folder. Permission is decided by data the user owns, and the kernel reads that data before the act and follows it. The two are independent, and both stand at once. A program can sit fully inside its own memory, protection satisfied, and still be refused an act its entry does not allow. A program can be allowed an act and still be stopped by protection the moment it reaches for memory that is not its own. Neither one replaces the other, and this chapter is the second one.

There are two sections. The first designs permissions in plain words: the data, who writes it, the default, when the kernel checks, and the refusal code, fixed here. The second designs what untrusted code can and cannot do under that data, and settles the randomness for secrets.

One warning, stated up front the way Chapters 4 through 28 stated their own. This chapter designs the security model. It does not build it. No permission record exists yet, no refusal has been handed back, and no claim in this chapter says any of it does. The chapter also claims no measured improvement on real hardware, so no scoreboard table is due. The numbers here are arithmetic on the chapter's own examples, counted by hand: entries, bytes, checks. No time is claimed anywhere in this chapter, because no check has been measured on the target machine, and Chapter 3 forbids numbers without a method. The measured proof comes in Chapter 31, on the real PC.

## 29.1 Permissions in plain words

Start with the job, in one sentence. Permission data says, for each program, what it may do, in words the user can read, and the kernel follows it.

Say where the data lives. The permission record is one file in the filesystem, in the top folder, named `permissions`. It is the user's file: the user owns it the way section 6.1 requires every value to have an owner, and the user is the only one who writes it, the way the next part of this section designs. The kernel reads it through the filesystem service, the way section 22.1 designed the start checks: the kernel asks, the service reads, the entry comes back. The kernel holds no copy of its own. Section 9.3 fixed the rule for the loader, the file is the truth and there is nothing to go stale, and the rule holds here with more reason: a copy of the permission record held in the kernel could go stale the moment the user edits the file, and a stale permission is a wrong permission. So the kernel reads the entry at each check, from the file, and a change the user makes takes effect at the next check, with no restart and no reloading. The record is also the one file no program may reach: no program may read it or write it through the file routines, whoever's folder it sits in, because a program that could read the record could plan around it, and a program that could write it could allow itself anything. The kernel reads it, and the kernel is its only writer: the user commands the changes through the shell, the way the next part of this section designs, and the kernel writes them. Nothing else touches it.

Say what an entry holds. One entry per program, and an entry holds two things: the program's name, and the acts it is allowed. The name is stored the way section 4.3 stores every name: one byte saying how many characters, followed by the characters. The acts are a fixed list of guarded acts, the acts a program may not do unless its entry allows them, and the list is fixed here, in this order:

| Act | What it means |
| --- | --- |
| Start | Start another program |
| Stop | Stop another program |
| Read outside | Read a file outside its own folder |
| Write outside | Write a file outside its own folder |
| Device | Use a device beyond the screen and keyboard it was started with |
| Talk | Open a network talk, through the network service |
| Set time | Ask the time service to set the time |
| Update | Ask the update service to run |

Eight acts, so the allowed list fits in one byte: one bit per act, in the order above, 1 for allowed and 0 for not. An entry is the name plus that one byte. Count the entries by hand, the way section 24.1 counted the running-program record. The shell's entry: the name `shell` is 1 length byte plus 5 characters, 6 bytes, plus 1 byte of acts, 7 bytes. The tester's entry: `tester` is 1 plus 6, 7 bytes, plus 1, 8 bytes. The hello loop's entry: `hello` is 1 plus 5, 6 bytes, plus 1, 7 bytes. A record holding those three entries is 7 plus 8 is 15, plus 7 is 22 bytes. The entries sit one after another in the file, each walked from its own first bytes, the way section 26.1 walks a folder's entries, and the file's size bounds the walk. The byte shape is fixed here as a design choice, stated as one. The record is binary, like every record in this book, and the user never has to read the byte: the record's text view, the way section 8.2 generates text from the binary form, shows each program's name followed by the acts it may do, named in plain words from the table above, or the word none. The user reads words. The kernel reads the byte. The round trip between them is exact, the way section 8.2 requires.

A program's own folder, which the read and write acts name, is a path fact from section 26.1: the folder the program's file sits in. For a program the user built, it is the folder the build placed it in. For a program installed from a package, it is the folder it was installed into. Reading and writing inside that folder is not guarded at all: it is the program's own place, and no entry is consulted for it.

Say who writes the data. The user, and only the user. The user reads and changes the record through the shell, as the user's own act, at the user's own keyboard: the shell shows the record's text view and takes the user's changes, widening an entry, narrowing one, adding a program, removing one, and the kernel writes each change into the record itself. A program cannot change any entry, not even its own. That rule has no exceptions, because it is the whole design: data a program could rewrite to allow itself an act would not be permission at all, it would be a suggestion. The shell's own entry is the user's to change like any other, and so is every tool's and every service's. The system's own programs ship with entries in the record's first form, the form Chapter 30 puts in the system image, set wide enough for each one to do its job: the shell can start the programs the user names, the services can do the work their chapters designed. Every one of those entries is the user's to narrow afterward, and a service narrowed past its job will refuse and report like anything else, in plain words, for the user to see.

Say the default, because most programs have no entry the user has written. A program with no entry runs under the default entry, fixed here, small and stated plainly. It may run. It may read and write its own folder. It may print to the screen and read keys from the keyboard when the user runs it from the shell in the open, where the user sees what it does. It may ask the clock for the count, through `now`, because knowing the time harms nothing. And it may not do any guarded act: no starting, no stopping, no reading or writing outside its folder, no device beyond the screen and keyboard it was started with, no network talk, no setting the time, no update. In the record's byte shape, the default is the acts byte holding 0, all eight bits clear. A program the user built on the machine gets its entry when it is built, and a program installed from a package gets its entry when it is installed, following the installed record from section 14.2: at the build or the install, the kernel writes the new program's entry into the record at the tool's ask, set to the default, and the user widens or narrows it from there. A tool can only ever ask for the default entry; neither one can bring a wider entry into the record, because a wider entry is the user's decision, not the tool's.

Say when the kernel checks, and what the check costs. The kernel checks at three moments. At a start, as the second of the two checks from section 22.1, after the file exists: the asking program's entry must allow the start act, or, when the user starts a program from the shell, the shell's entry must allow it. The boot's first start of the shell is not checked, the way section 23.2 fixed: the permission data governs the first program the shell starts, not the shell. Before a guarded ask reaches a driver, the way section 27.1 fixed: the kernel reads the data before the call, not after. And before a guarded ask reaches a service, the way Chapter 28 fixed: setting the time, running an update, and opening a talk are checked against the asking program's entry before the service is even started. Ordinary work is never checked: a program reading its own folder, printing in the open, or asking the clock for the count pays no check at all, because none of those acts is guarded. The check itself is one ask: the kernel names the program to the filesystem service, the service reads the record file and hands back the one entry for that name, and the kernel reads the one byte. The kernel does not search: it asks for the entry by name and gets that entry, the way it asks for a file by name and gets the file. One ask, one entry, one byte read. No timing is claimed for it; Chapter 31 measures it.

Now fix the refusal, because Chapters 22 and 24 left the code here. When the data forbids an act, the kernel refuses it, and the refusal is an error value, the way section 7.3 designed errors: a code and a message in plain words. The code is fixed here: code 10, not allowed. It is the next system code after the nine section 16.3 fixed, 1 to 9 taken, and it sits inside the system's range, 1 to 127, the way section 16.3 divided them, leaving 128 to 255 for programs' own codes as before. One code for one meaning: a refused start, a refused stop, and a refused guarded ask all hand back code 10, because all three are the same failure, the data did not allow the act. The message names the act that was refused and the program that asked, in plain words, so the user and the program read what happened without a table: `racer is not allowed to open a network talk`. The asking program decides what to do with the refusal, the way section 7.3 gives every program the same three ways: deal with it, pass it up, or give up cleanly. And the refusal is logged as an act in the kernel's log, the way section 17.1 designed the layer: one line naming the program and the act, and nothing else, no values, no contents, log the act and never the secret, the way section 16.3 requires.

Work one refusal through, step by step. The program is a game the user fetched as a package, `racer`, installed under the default entry, and it asks to open a network talk. First, the routine call: the program calls `open_talk` from section 28, and the routine asks the kernel, the way every service ask travels. Second, the check: before the ask reaches the network service, the kernel asks the filesystem service for racer's entry, and the entry comes back with the talk bit clear, because the default allows no guarded acts. Third, the refusal: the kernel hands the error back, code 10, with the message naming the act and the program. The network service is never started, the network driver is never called, and no byte leaves the machine. Fourth, the log: the kernel writes one line to its log, `1794700800 refused racer talk code 10`, 37 characters plus the newline, 38 bytes: the time, the act refused, the program, and the code. Fifth, the program decides: racer can run without the talk, or give up cleanly, and nothing is killed and nothing is punished, because asking is not a crime in this design. Count the refusal: 1 routine call, 1 entry read, 1 error handed back, 1 log line, 0 services started, 0 driver calls. A refused start is shorter still, against the shape section 22.1 counted: 1 call, 2 checks, the file exists and the permission refuses, 0 loader steps, and the start call hands back code 10 instead of a number.

Say what permission is not, because three misunderstandings would bend the design. It is not a password system. The machine is one person's, the way section 3.2 fixed, and there are no accounts in this design, no list of people, no signing in: the record names programs, not people, because the question the kernel can answer is what this program may do, not who is sitting at the keyboard. It is not a lock on the user. Section 2.4's test asks three questions of everything in the system: can the user see it, can the user measure what it costs, can the user turn it off. Permission passes the first two, the record is readable and the refusals are logged, and it passes the third in full: the user can change any entry at any time, and the user can turn the whole record off by removing the record file. While no record is there, the kernel allows what programs ask, and it writes one line to its log saying permission is off, so the state is never silent. Protection still stands while permission is off, because protection is not permission: the hardware still stops every program at the edge of its own memory, record or no record. Turning permission off is the owner's choice about their own machine, and the design's job is to make the state visible, not to overrule the owner. And permission is not validity. Section 9.4's six checks prove a file is a Riza program, shaped right and safe to load. They say nothing about what the program may do once it runs. A file can pass all six checks and hold no entry but the default. Validity is the loader's question. Permission is the user's. This chapter answers the second one.

## 29.2 What untrusted code can and cannot do

Start with the word, in plain words. Untrusted code is a program that arrived from somewhere else: installed from a package the user fetched, or was given on a disk or a stick, that the user has not marked trusted in the permission data. Trusted is not a stamp the system grants. Marking a program trusted means the user editing its entry, widening it past the default by the acts the user chooses, as the user's own act, taking effect at the next check, the way section 29.1 fixed. A package cannot mark itself trusted: nothing in the package format from section 14.2 asks for acts, and an install carries no widening with it. An install that passes every check in section 14.2, the magic, the description, the dependencies, the six validity checks, is still untrusted the moment it lands, because validity is not trust, and this is the place where that sentence bites: the checks proved the file is a program. Only the user can say what it may do.

Untrusted code runs. Say that plainly, because the opposite design exists and this book refuses it: the user installed the program on purpose, the machine belongs to the user, and the system is not a prison. What untrusted means is not that the code is stopped. It is that the code runs under the default entry, inside the walls this section names, until the user decides otherwise. It also runs under protection, like every program, trusted or not: Chapter 25's wall holds for the user's own programs too, because protection is not a judgment about trust, it is the shape of memory.

Say what it can do, under the default entry. It can run, inside its own memory, for as long as the user lets it. It can read and write files in its own folder, the folder it was installed into: save its own work, keep its own settings, hold its own data. It can print to the screen and read keys from the keyboard when the user runs it from the shell in the open, so a fetched game can be played and a fetched tool can be used. It can ask the clock for the count through `now`. It can write its debug log, the way section 17.1 gives every program a log, and the user can read that log. And it can use the core library's routines that touch only its own values and its own folder: the text, list, and math routines, and the file routines inside its folder. That is a working program's worth of ability. Most programs the user fetches need nothing more, and the ones that do can be widened, act by act, by the user.

Say what it cannot do, under the default entry, each item tied to its guard. It cannot start another program, and it cannot stop one: the start and stop acts are clear in its byte, and the kernel refuses with code 10. It cannot read or write another folder's files: not another program's folder, not the user's documents folder, not other programs' logs in their `logs` folders, and not the permission record itself, which no program may reach at all, the way section 29.1 fixed. It cannot open a network talk, and it cannot ask any service for a guarded act: it cannot ask the time service to set the time, and it cannot ask the update service to run. It cannot use a device beyond the screen and keyboard it was started with: no direct word with the disk or the network hardware, which are reached, when they are reached at all, through the services and the filesystem, under their own guards. And it cannot change any permission entry, its own above all, because entries are the user's writing, not programs'.

Say what happens when it tries, because the trying is certain and the design must meet it calmly. The ask is refused: the kernel hands back code 10, not allowed, with the message in plain words naming the act and the program. The refusal is logged in the kernel's log, one line, so the user can see what the program asked for and when. And then nothing else happens. The program is not killed for asking. It is not marked, throttled, or punished. It goes on with its work, or gives up cleanly, its own choice, the way section 7.3 gives every program the same three ways with any error. A program that asks for the network a hundred times gets a hundred refusals and a hundred log lines, and the user reading the log learns something true about the program, which is the point of logging it. Refusal is information, for the program and for the user, and it costs the program nothing but the act it was never allowed.

Now settle the promise section 16.2 made: true randomness for security. Section 16.2 fixed what the library's random routines are: seeded from the time, from `now`, and from the machine's own noise, gathered as the machine runs, good enough for games, shuffles, sampling, and tests. They are not for secrets, and the reason is one sentence: a seed that can be guessed makes every number after it guessable, and the time can be guessed, because an attacker who knows roughly when a key was made knows roughly what the seed was, and can roll the same numbers forward. A key rolled from a guessable seed is a key that is not a secret, however long it is.

The design for secrets is fixed here, plainly. When a program asks for numbers for a secret, it calls the kernel, by a kernel call of the kernel's own, numbered with the kernel's calls in Appendix A, the way section 25.1's ask and give-back calls are the kernel's own. The program names how many bytes it needs. The kernel gathers noise at that moment, fresh, from the machine itself: the exact timings of the disk's reads, of the keys pressed, and of the clock, the timings the drivers from Chapter 27 see as they work and no program can predict or replay. The kernel mixes the timings together, so no one source decides any byte of the result: a byte depends on all the sources at once, not on the disk alone or the clock alone. Then the kernel hands the program the bytes. There is no seed. Nothing is stored, nothing is kept to roll forward, and nothing about one ask says anything about the next: bytes handed back before teach an attacker nothing about bytes handed back after, because there is no seed to steal and no sequence to continue. The bytes live in the program's own memory from the moment they arrive, under Chapter 25's protection, like everything the program holds. They are never logged, the way section 16.3 requires: the kernel's log can hold the act, a program asked for secret bytes and got them, and never the bytes. And the system never hands one program's secret bytes to another program: there is no call that asks for another program's numbers, because the numbers are gathered for the asker, at the ask, and belong to the asker, the way section 6.1 gives every value one owner.

State the honest limit in the open, because randomness is where designs lie most easily. This design is only as good as the machine's noise, and the noise is not constant. A machine that has been running, reading its disk and taking keys, has timings no one can replay. A machine just booted, with no disk moving and no keys pressed yet, has less noise to gather, and bytes asked for in that moment rest on less. The book does not hide that: the kernel gathers what the machine has, and a program that needs secret bytes on a quiet machine is working with a quieter source. And Chapter 31 cannot measure randomness into being true. No test proves bytes are unguessable. What Chapter 31 can check is the shape: different asks at different moments give different bytes, no ask repeats an earlier ask's bytes, and no pattern carries across a restart, the way a seed carried across a restart would repeat the same sequence. The design's claim is the shape, no seed, fresh noise, mixed sources, and the claim is stated at exactly that strength, no stronger.

That closes the security model, and it closes Part 6. The operating system is designed whole: the kernel, the boot, the processes and the sharing, the memory and its protection, the filesystem, the drivers, the services, and now the permissions that say what any of it may be asked to do. What remains is Part 7: putting the whole system in one image, proving it on the real PC, benchmarking it against today's stack, and designing how it installs, updates, recovers, and grows.

The test suite grows with this chapter. Eight new tests cover the security model. Four cover permissions: a start the data forbids gives code 10, and nothing starts; a stop the data forbids gives code 10, and the program keeps running; a program with no entry runs under the default, its own folder open to it and a guarded ask refused with code 10; and with the record removed, the kernel allows a guarded act, writes the line saying permission is off, and protection still stops a program that reaches outside its own memory. Four cover untrusted code: a fetched program reads and writes its own folder, and reading another folder gives code 10; a fetched program's talk is refused with code 10, and the program goes on running; a package that installs with every check passing is still untrusted, and its first guarded ask is refused until the user widens its entry; and two asks for secret bytes at different moments give different bytes, with no byte sequence repeating across a restart. That is 8 new tests, and the suite grows from 169 to 177: 169 plus 8 is 177. Each test runs on the target PC, the way section 2.5 demands.

This chapter adds no new routines to the core library. The permission checks are the kernel's own work, and the secret bytes are a kernel call, numbered with the kernel's calls in Appendix A. The library stays at 39 routines, and the suite grows to 177 tests.

The chapter counts as done when the security model runs on the target PC from section 3.1: a refused start and a refused stop hand back code 10, a program with no entry runs under the default, a fetched program works in its own folder and is refused outside it, two asks for secret bytes give different bytes, and the times are measured in Chapter 31. Until that run happens, the chapter's claims are marked plainly as waiting for the real-PC run, the way part 5 of the done test in section 3.3 requires.

Chapter 30 builds the full system image: what goes in, what stays out, and the permission record's first form, the entries the system ships with. Chapter 31 runs the tests on the real PC, the refusals among them, and checks the shape of the secret bytes. Chapter 32 benchmarks the whole stack against today's, security model included. Chapter 33 designs install, update, and recovery, where the permission record is part of what an install writes. Chapter 34 designs what comes after v1, and what to never add, and permission data a program could edit is on the never list.

---

The security model is two designs kept apart. Protection, the hardware's check, keeps every program inside its own memory, trusted or not, asking or not. Permission, this chapter, is data the user owns: one record, one entry per program, a name and one byte holding eight guarded acts, read by the kernel at a start and before a guarded ask, never copied, never stale. The default entry is small: run, your own folder, the screen and keyboard in the open, the clock's count, and nothing guarded. Code 10, not allowed, is the refusal for a start, a stop, and a guarded ask alike, reported in plain words, logged as an act, and final only until the user edits the record, because the record is the user's and the user can change any entry or remove the record whole. Untrusted code runs under the default, works in its own folder, and is refused, calmly and without punishment, everything beyond it. Secrets get fresh noise from the machine itself, mixed from the disk, the keys, and the clock, with no seed kept and nothing logged. Part 6 is complete. No new routines join the library, and the suite grows from 169 tests to 177.
