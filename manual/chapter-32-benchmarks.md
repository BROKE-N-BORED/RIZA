# Chapter 32: Benchmarks vs today's stack

Chapter 31 asked whether Riza does what its own chapters said it would do. This chapter asks the harder question: whether it does those things better than the stack the user already has. Same machine, same work, same way of measuring, both sides. A system can pass every one of its own tests and still lose to what it replaces, and the user does not live inside the book's promises. The user lives at a prompt, doing real work, on a machine that already runs something. That something is the opponent here, and it is a fair opponent: today's stack on the target machine, used the way its user actually uses it.

The hard honesty stands at the front, the same as Chapter 31's. This chapter reports no scores. It claims no time, no size, and no energy figure for either side, because neither side has been measured on the target machine yet. Chapter 1's numbers were measured on the machine used to write this manual, a virtual machine with 4 cores and 8 GB of RAM, and rule 1 of section 1.5 forbids comparing numbers across machines. Those numbers are background: they say why the book believes there is waste worth attacking, and nothing more. The before in this chapter is today's stack measured fresh on the target PC, the same way Chapter 31 measures the after. What this chapter fixes is everything except the numbers: the exact tasks, the exact inputs, the counting rule for each of the five measures, the fairness rules, and the scoreboard's shape. Section 1.5 said in so many words that this chapter fixes the exact task list and the exact inputs, so that any reader can repeat the measurements. That fixing is the first job below.

There are two sections. The first fixes the standard tasks and their inputs, then takes the five measures one by one: size, boot time, RAM, speed, power, each with what exactly is counted on each side. The second designs the scoreboard and its standing rule: score before, score after, every time a change could move a number.

## 32.1 Size, boot time, RAM, speed, power

Start with the job, in one sentence. The comparison runs one fixed list of tasks, on identical inputs, on the target machine, and reports five measures for each side, with the method written beside every number.

First the tasks, because a comparison is only as honest as its work list. Section 1.5 fixed the shape: cold start to first output, warm start to first output, and one real task per tool. This chapter fixes the list itself, eight tasks, short enough to run in one sitting, each input counted exactly.

| Task | The work, with its input counted | Today's side | Riza's side |
| --- | --- | --- | --- |
| Cold start | The hello program prints one line and exits, run when its files are not in the disk cache | The Python interpreter running the same one line program | The hello program from Chapter 4's worked example, run from the shell |
| Warm start | The same program, run again at once, its files now in the cache | The same, run again | The same, run again |
| List files | List the counted tree: 100 folders of 100 files each, every file exactly 1,000 bytes, so 100 times 100 is 10,000 files and 10,000,000 bytes in all | The system's own file listing tools, the command a user would type | The list tool joined into the shell, from section 18.1 |
| Search | Find a named word in one text file of exactly 10,000,000 bytes: lines of 100 bytes, repeated 100,000 times, 100 times 100,000 is 10,000,000, the word standing once in every line, so 100,000 matches to report | The system's text search tool | The search tool joined into the shell, from section 18.2 |
| Format | Put a program file of exactly 1,000 lines, written out of canonical form, into canonical form | The formatting tool the machine as it stands already has, or the job done the way its user does it today, recorded as such | The formatter from section 20.1 |
| Build | Turn that same 1,000 line source into the runnable form, ready to run | The interpreter compiling the same size of source into its bytecode, timed on its own, with the note below | The build tool from section 14.1 |
| Count words | Count the words in the same 10,000,000 byte text file the search task uses | The system's word counting tool | The word counter program from Chapter 16's worked example, on the bigger input |
| Copy | Copy the counted tree, all 10,000 files, to a fresh folder, and check the copy's file count | The system's copy tool, with the flags a user would type | The copy tool joined into the shell, from section 18.1 |

Three things about this list are rules, not decorations. The inputs are made once, by a counted generation step whose output is checked against the counts in the table, and the same files serve both sides. Where a later round must make them again, the generator and its counts are the same, and the check is the byte counts and the file counts, so no side ever gets an easier input. Today's side is today's stack at its honest best: the tools a user on the Mint PC would actually reach for, run the way a careful user runs them, with the commands written into the record. Beating a crippled before proves nothing, and a before tuned specially for the test would prove the opposite of nothing, so neither is allowed: the commands are the ones a user would type, no more and no less. And the build row carries its note in the open: on today's side, compiling source into bytecode is a step a user rarely runs alone, because the interpreter folds it into startup, and the start rows above show what that folding costs the user in practice. The step is timed alone here so the same step is visible on both sides, and a reader who wants the user's-eye view reads the start rows. Nothing is hidden by the choice, because the choice is printed beside the row.

Now the five measures, one by one. Each one says what is counted on Riza's side, what is counted on today's side, and the rule that keeps the two counts the same kind of count.

Size is the whole stack each task list needs, counted from the disk the same way on both sides, by the method section 1.5 fixed: the installed tree, measured whole. On Riza's side the count is the system image's total bytes, from the build's report in section 30.2: the bootloader, the kernel, the shell, the services, the library, the compiler, the tools, the records, everything the machine boots into and every task runs on, because the image is the whole system and there is nothing outside it to forget to count. On today's side the count is the Mint system as it stands on the disk: the operating system's installed tree, the shell and its tools, the Python interpreter and its standard library, the editor, everything the tasks boot into and run on, counted tree by tree with the trees named in the record so a reader can recount them. The exclusions are the same in spirit on both sides: the user's own files and documents are not the stack on either side, and caches a program builds while running are reported separately where they matter, the way section 1.5 requires, not folded silently into the size. The hard edges are named in the open, because this is the measure most easily rigged. Counting only the interpreter's own binary against the whole Riza image would rig it for today, since the interpreter cannot run without its library and its system under it. Counting every extra program the user ever installed, games and all, against the image would rig it for Riza, since the tasks never touch them. The rule threads between the two: the full system each side boots into, plus the named tools the tasks use, and the record lists what was counted so the threading itself can be checked.

Boot time is the wait from the power switch to a prompt that answers, defined once for both sides: ready means the user can type a command and get its answer back. On Riza's side the number is Chapter 31's boot test: the outside timer's whole wait, from power to the shell's prompt, with the inside breakdown beside it. On today's side it is the same wait on the same machine running Mint: power switch, the machine's firmware, the system loading, the user signed in, a terminal open, and a command typed and answered. Signing in and opening the terminal are counted on today's side because ready was defined as a prompt that answers, and a desktop that cannot yet take a command is not ready by that definition; leaving them out would flatter today, and leaving the shell's own start out would flatter Riza, so both sides pay for everything up to the same finish line. The timing method is Chapter 31's outside timer, a phone or a watch the user already has, costing nothing under section 3.2's hard $0, taken over 5 cold boots with the middle wait as the verdict and the slowest reported beside it, the same repetition rule Chapter 31 fixed.

RAM is the peak memory each task holds while it runs, section 1.5's peak resident set size, the most physical memory the work held at any point. On Riza's side the account is the kernel's own record from section 24.1: every running program's entry carries the bytes it holds, counted and updated as it runs, so a task's row reads the peak of that count for each program the task ran, including any service the task woke, each program named with its own peak. On today's side the account is the operating system's own, the peak resident set size the system recorded for each process the task started, read by the harness section 1.5 described. The trap section 1.5 named applies to both sides and is handled the same way: resident memory is not additive across processes, because a shared library loaded by ten processes is counted in all ten. So the rows list each program's peak on its own line rather than summing peaks into a total that double counts the shared parts, and where a single figure for a whole task is wanted, the record says which measure produced it and how the shared pages were handled, the way section 1.5 requires. What the rows must never do is compare one side's per-program peak against the other side's summed total. Same quantity, both ways, or the row does not count.

Speed is the whole job, from launch to result, in wall clock time, the way a person waiting feels it, by section 1.5's method: median of at least 5 runs, the slowest run reported too, on the target machine with nothing else running. Startup counts and shutdown counts, because rule 6 of section 1.5 says the whole job is measured or the measurement is cheating: the list task ends when the last name is printed, the copy task ends when the copy checks, the build ends when the runnable form is written and reported. On Riza's side the stopwatch is section 16.2's shape, `now` and `elapsed`, with Chapter 31's loop method for acts too small for whole seconds. On today's side the stopwatch is the system's own timing, the harness from section 1.5 or the time builtin a user would use, written into the record. CPU time is reported beside wall time on both sides, the way section 1.5 requires, because the difference is information: on a 2 core machine, a job that finishes in one second of wall time by burning four seconds of CPU time has spent cores another program needed, and the row should say so.

Power is the energy to finish a fixed set of work, in joules or watt hours, because energy is what the user pays for, the way section 1.5 explained: a fast program can draw more watts and still use less energy by finishing sooner. The fixed set is fixed here: the eight standard tasks, run once each in the list's order, cold start first, on a machine that has done nothing else since booting. The method follows section 1.5 and Chapter 31's check, in that order. Chapter 31 recorded whether this machine exposes the chip's energy counters, the Ryzen equivalent of Intel's RAPL under `/sys/class/powercap` on today's system. If the counters are there, they are the method on both sides, read the same way around the same set. If they are not, the method is the plug in meter on the wall socket: the whole machine measured over the set, minus the idle baseline measured the same way over the same length of time, because the machine draws power doing nothing and only the extra above idle is the work's cost. And if neither is at hand on the day, no meter the user owns and no counters the machine exposes, then the power rows read not measured, with the reason, under Chapter 31's rule that a not measured is never a pass and never a number. No meter is bought to fill the row, because section 3.2's budget is zero and stays zero; an honest gap in the table costs less than a broken rule. Whichever method a round uses, it uses for both sides and says so beside the numbers, because section 1.5 forbids comparing figures taken by different methods: a counter number and a wall meter number measure different wholes, and placing them in one row would be a quiet lie.

The fairness rules, gathered in one place, because a rule scattered across five measures is a rule that gets lost. Same machine: the HP All-in-One from section 3.1, both sides, no exceptions, because rule 1 of section 1.5 is the oldest rule in the book. Same task, same inputs: the counted files from the table, made once, checked by their counts. Same round: both sides are measured in the same round of work, today's side fresh on the target machine, never one side quoted from an old record while the other is measured new; Chapter 1's writing-machine numbers in particular are never the before, only background. Cold and warm stated for every start, and for every task the machine's state is stated: what had run before it, what else was running, which was nothing, because a number taken on a busy machine is a number about the busyness. Method beside every number, so a reader can repeat any row. And the whole job, every time, from the first act to the last, with nothing trimmed off either end to flatter either side.

## 32.2 Score before, score after, every time

Start with the job, in one sentence. The scoreboard is one fixed table, kept as records, that every change to the system must face before the change and after it, so the cost of every choice stays on the page where it was made.

The board's shape grows out of the scoreboard section 1.5 sketched: a task, today's number, Riza's number, the machine, the method. Filled out for this chapter's design, one round of the board is one record, kept with the system the way Chapter 31's records are kept, with header lines naming the machine, the round, and what changed since the last round. Inside it, one row per task per measure:

| Task | Measure | Before: today's stack | After: Riza | Method |
| --- | --- | --- | --- | --- |
| Each of the 8 standard tasks | Speed, median and slowest | | | Section 1.5's timing, whole job |
| Each of the 8 standard tasks | Peak RAM, per program | | | Section 1.5's peak resident set, or the kernel's record |
| The whole stack | Installed size | | | Installed trees counted whole, trees named |
| Cold boot | Time to a prompt that answers | | | Outside timer, 5 boots, middle and slowest |
| The 8 tasks run once through | Energy above idle | | | Energy counters, or wall meter minus idle baseline |

Count the rows: 8 tasks times 2 measures is 16, plus the size row, the boot row, and the power row is 19 rows. Nineteen rows is the whole board. It fits on one screen at the target machine's 1366 by 768, it can be read in one sitting, and a reader can hold all of it in mind at once, which is the point: a board too big to read is a board nobody checks. The before column is filled in the round's first half, on the machine running today's stack as it stands. The after column is filled from Chapter 31's run on the installed Riza system, whose record already holds most of these numbers under their own names; where Chapter 31's record holds a number this board needs, the board copies it with its method, and where it does not, the missing line is measured in this round or reads not measured with its reason, the rule Chapter 31 fixed and this board inherits without softening it.

Now the rule the section's title states, because the board without the rule is just a table somebody filled in once. Every change to the system that could move a number gets the board run against it, before the change and after it, both records kept, and the two compared in the open. A change means what it sounds like: a new compiler pass, a kernel change, a tool rewritten, a place in the layout grown, a service's shape altered, anything whose author believes it touches size, boot time, RAM, speed, or power. The before run is made on the system as it stands without the change, the after run on the system with it, on the same machine, on the same inputs, in the same round of work, because a before pulled from last month's record and an after measured today are two rounds pretending to be one, and the machine's state drifts between rounds in ways no header line fully captures. If the change makes a row worse, the record says so, and says what the loss bought: the trade stated in plain words beside the row, the way rule 7 of section 1.5 requires, because a loss with its reason on the page is a decision, and a loss averaged away or left unrun is a decision nobody admitted making. And a change whose author does not run the board is not finished. That is stated as a rule of the project, not a hope: it is part 5 of section 3.3's done test applied to changes, the same way it applies to chapters, and a change that ships without its after record waits for its proof exactly like a chapter that has not run on the real PC. The fixes that come out of Chapter 31's fails live under this rule too: Chapter 31 already sends the work back to its chapter and rebuilds the image, and this chapter adds that the rebuilt system faces the board, so a fix that quietly makes three other rows worse is caught by the same net that caught the fail.

Say plainly that there is no single total score, and why, because every reader will look for one. The five measures trade against each other by design. A smaller image can boot slower if its files are packed in an order the disk reads badly. A faster task can draw more energy by waking both cores for work one core would have finished cooler. A leaner RAM row can cost speed when a program recomputes what it used to hold. One number at the bottom would have to weigh those trades against each other, and any weighting chosen after the rows are known is a weighting chosen to reach a verdict somebody wanted, which is the exact dishonesty this book was written to refuse. So the board has no total row, and its shape forbids one: the verdict is read row by row, wins and losses both on the page, each with its size. A reader who wants a single word gets nineteen honest rows instead, and the word they form in their own head is theirs, reached by their own weighing, which is where section 2.4 always said judgment belongs: with the user, looking at numbers they can see, measure, and rerun. A board the user cannot rerun on their own machine fails section 2.4's first question, can the user see it, and this board passes it the plain way: the tasks are fixed, the inputs are counted, the methods are named, and nothing in a round needs a tool the user does not already have.

Say what a finished board lets a reader conclude, at exactly its strength and no wider. Which rows Riza wins, which rows it loses, and by how much, on this machine, the HP All-in-One from section 3.1, for this work, the eight standard tasks and the five measures over them. That is the whole claim. It is not a claim about computing in general, not about other machines with more cores or faster disks, not about work the task list does not cover, and the board's header says so by naming its machine and its tasks on every round. Chapter 29 stated its randomness claim at exactly its strength and no stronger; this board does the same, because a benchmark that claims the world from one desk machine is the kind of number Chapter 1 was written against. Inside its strength, though, the claim is real: if Riza wins the cold start row on this machine by a wide margin and loses the format row by a narrow one, both facts stand, both are repeatable by any reader with the same machine, and the project's next work is written in the losing rows for anyone to read.

That closes the argument Part 7 opened. Chapter 31 was section 2.5 carried out against the book's own promises: prove it on real hardware or it does not count, with the promises as the judge. This chapter is the same rule with the harder judge: the stack the user already has, at its honest best, on the user's own machine. Together the two chapters are the whole of the proof this book knows how to offer: first that the system does what it said, then that what it said was worth doing, measured against the alternative the user would otherwise keep. Everything after this chapter is delivery and growth, and both stand on these two records.

The test suite grows with this chapter. Eight new tests cover the scoreboard and its rules, because a board that is not tested is a board that drifts, and this book tests what it trusts. Two cover the standard inputs: the counted tree checks out at 10,000 files and 10,000,000 bytes, and the search file at 10,000,000 bytes with the word standing 100,000 times, on both stacks; and the format file checks out at exactly 1,000 lines, out of canonical form, before either side touches it. Two cover the board's shape: a finished round writes all 19 rows, each number with its method beside it and the machine named in the header; and a round whose record carries a total row is refused as malformed, because the board has no total. Two cover the not measured rule on the board: a power round run with no counters exposed and no meter at hand writes not measured for the power row, with its reason, and the round still stands for its other rows; and a row copied from an old record into a new round is flagged, because both sides of a round are measured in that round. Two cover the before and after rule: a change scored properly writes two records, before and after, and a row that got worse carries its trade line in plain words; and a change record with no after run is marked unfinished, not passed over in silence. That is 8 new tests, and the suite grows from 193 to 201: 193 plus 8 is 201. Each test runs on the target PC, the way section 2.5 demands.

This chapter adds no new routines to the core library. The board uses the tester's records from section 20.2, the stopwatch shape from section 16.2, and the kernel's memory record from section 24.1, all already designed. The library stays at 39 routines, and the suite grows to 201 tests.

The chapter counts as done when the first full round of the board has run on the target PC from section 3.1: the before taken on the Mint system as it stands, the after taken from Chapter 31's run on the installed image, all 19 rows filled with numbers or with an honest not measured and its reason, and the round kept as a record any reader can rerun. Until that round happens, this chapter's claims are marked plainly as waiting for the real-PC run, the way part 5 of the done test in section 3.3 requires, and this chapter waits like the thirty-one before it, by its own rule.

Chapter 33 designs install, update, and recovery: the install that puts the image from Chapter 30 on the Mint PC, the updates that cannot brick the machine, and the recovery when something breaks. The board stands behind that chapter as its guard: an update is a change like any other, so it owes the board a before and an after, and an update that silently worsens a row is caught by the rule this chapter fixed. Chapter 34 designs what comes after v1, and what to never add, and its first work list is written already: Chapter 31's fails, and this board's losing rows, the places where today's stack, at its honest best, beat the system this book built. What broke, what lost, and by how much: that is where the next version begins.

The comparison is eight fixed tasks on counted inputs, five measures with a counting rule each, and one board of 19 rows. Power spends one fixed set of work and follows Chapter 31's counter check to its method, or records an honest not measured rather than buy its way to a number. No scores are reported here, because neither side has been measured on the target machine, and the before is retaken there fresh, never borrowed from Chapter 1's writing machine. Every change that could move a number faces the board before and after, both records kept, losses carrying their trades in plain words, and a change without its after run is not finished. There is no total score, because the five measures trade against each other and one number would hide every trade the book exists to expose. No new routines join the library, and the suite grows from 193 tests to 201.
