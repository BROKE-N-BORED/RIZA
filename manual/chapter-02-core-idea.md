# Chapter 2: The core idea

Chapter 1 was the diagnosis. Today's computing wastes effort in four ways: it re-translates text on every use, it stacks layers that each redo the work of the layer below, it pays a background collector to find memory the program is done with, and it loads whole runtimes before the first useful act. The waste is real, it is measured, and it is the same waste in every layer.

This chapter is the idea that answers it. The idea has five parts, one per section, and they fit together like this: prediction is compression, so a system built on prediction is small by nature. Binary is the truth and text is a view, so loading is reading instead of re-translating. One form is shared from top to bottom, so work done once is done once. The core is small and does no hidden work, so nothing runs that the user cannot see, measure, or turn off. And none of it counts unless it is proven on real hardware, because an idea that cannot be measured is a preference, not a design.

Nothing in this chapter is built yet. The chapters that follow do the building. This chapter states the idea clearly enough that the rest of the book can be judged against it. If a later chapter contradicts this one, this one wins, and the later chapter is wrong.

## 2.1 Prediction is compression

Imagine two people, a sender and a receiver, passing a message one letter at a time. Before each letter, the receiver guesses what it will be. If the guess is right, the sender says nothing, and both of them write the letter down. If the guess is wrong, the sender sends the letter. At the end, both of them hold the same message, and the sender only paid to send the letters the receiver could not guess.

That game is the whole idea. What you can predict, you do not have to store. What you cannot predict is the information. Prediction and compression are not two ideas that happen to go together. They are the same idea seen from two sides. A good predictor is a good compressor, because every correct prediction is a piece of the message that never had to be sent. A good compressor is a good predictor, because the only way to make a message smaller without losing any of it is to spend bits only on the parts that surprise.

Work through three messages by hand and the point lands.

The first message is random: `xkqzfj`. Six letters, no pattern, each one a surprise. Stored plainly at 8 bits per letter, one byte each, it costs 48 bits. There is no shorter form that keeps all of it, because there is nothing to predict. Every letter must be sent in full. Random data is incompressible, not because compression is weak, but because there is nothing to compress. The message is all surprise.

The second message is repeated: `ha ha ha ha ha ha ha ha`. Count it: eight pairs of `ha` make 16 letters, plus 7 spaces between them, 23 characters in all. Stored plainly at 8 bits per character, that costs 184 bits. But after the first `ha `, every character is predictable. The pattern is fixed. So instead of storing all 23 characters, store the pattern once, `ha `, which is 3 characters or 24 bits, and store the count, 8, which fits in one byte or 8 bits. Total: 32 bits, against 184 for the plain form. Under a fifth of the size, and nothing is lost. The receiver rebuilds the message exactly by repeating the pattern 8 times. The prediction did the work, and the storage only paid for the surprises, of which there were two: what the pattern is, and how many times it repeats.

The third message is English, and it sits between the two. English is partly predictable. After `q` comes `u`, almost every time, so the `u` after a `q` is nearly free. After `th` comes a vowel far more often than a consonant. Common words like `the` and `and` appear over and over. A good predictor of English can guess a large share of each sentence, which means English text can be compressed well, but never down to nothing, because a sentence still carries real news. Most real data lives here, in the middle: predictable enough to shrink, surprising enough to matter.

In 1948, Claude Shannon put this idea on a firm footing. Shannon showed that the information in a message is the surprise in it. A message you can predict perfectly carries no information at all, because it tells you nothing you did not already know. A message you cannot predict at all carries the maximum information, because every part of it is news. The bit, the basic unit of computing, is a measure of surprise: one bit is the information in one yes or no answer. That is why the guessing game above is not a metaphor. It is the mechanism. Every correct prediction saves bits, and the number of bits a message truly needs is the number of surprises it contains.

Now apply this to programs, because programs are far more predictable than they look. A program is not random text. It repeats itself constantly. The same operations appear again and again: add, compare, jump, load, store. The same patterns appear again and again: a loop that walks a list, a check that a value is in range, a call that opens a file and reads it. The same names appear again and again: a variable defined once and used fifty times. A program is much closer to the repeated message than to the random one. That means a language that stores the surprises and predicts the rest is small by nature, not by cleverness. The smallness is in the material.

You have seen this idea before, in a familiar form. Morse code gives the shortest code to the most common letter: `E` is a single dot, `T` is a single dash, while rare letters like `Q` get long codes. That is prediction turned into storage. The code is short where the letter is common, because a common letter is easy to predict, and long where the letter is rare, because a rare letter is a surprise. Chapter 4 builds the same idea into the language itself: the most used operations get the shortest codes, and the dictionary of those codes is shared by every program. The details wait for Chapter 4. The principle is here, and it is the whole book in one line: if you can predict it, you do not have to store it.

The payoff runs through all four numbers from section 1.5. A program that is small to store is small to load, because there are fewer bytes to read from the disk, and on the target PC the disk is a spinning drive where every read costs time. A program that is small to load is quick to start, because startup in Chapter 1 was mostly the cost of loading things before the work begins. A program that is small in memory leaves more of the 8 GB for the user's work instead of the runtime's overhead. And a program that moves fewer bytes uses less energy, because moving data costs power and less data moved is less power spent. One idea, four numbers. That is why prediction is compression is the first section of this chapter and not a detail saved for later. Everything else in the book is this idea, worked out in one place after another.

## 2.2 Binary first, text second

Today, text is the truth and binary is derived from it. The program on disk is text. Every time it runs, the machine translates that text into something it can execute, and then throws the translation away. Section 1.1 counted this cost: the parse on every run, the bytecode cache that only helps for files run before, the whole parsing toolchain shipped inside every runtime and every browser. The system treats the human readable form as the real program and the machine form as a temporary convenience.

Riza turns that around. Binary is the truth and text is a view. The program on disk is stored in the binary form the machine runs. Loading it is reading, not re-translating. The loader reads the file, checks that it is valid, and runs it. There is no parse step at load, no bytecode cache to check for freshness, no first run that pays the full parse, because the parse already happened, once, when the program was written. The work of understanding the program is done one time, by the programmer's tools, and never repeated by the machine that runs it.

Say plainly what this changes for the programmer, and what it does not. What does not change: the programmer still writes words on a screen. The editor still shows text, with names the programmer chose, in lines the programmer can read. Programming is still a human activity done in a human readable form. What changes is what gets saved. Saving a program writes the binary form. The text the programmer sees is a view generated from that binary form whenever it is needed, and the round trip is exact: text to binary and back produces the same text, with nothing lost and nothing silently changed. Chapter 8 defines that text form and proves the round trip. The programmer's experience is text. The machine's experience is binary. Neither side is asked to live in the other's form.

The honest worry is that binary is unreadable to a human, and the worry is fair. A text file can be opened in any editor, read on any machine, searched with simple tools, and compared line by line with an older version. A binary file cannot. The answer is not to pretend the worry away. It is that the text view is a first class part of the system, not a tool bolted on later. Reading a program, searching it, comparing two versions of it, all work on the text view, which any tool can generate from the binary form at any time. Version control stores the text view. A printed listing is the text view. The binary form is the truth the machine keeps; the text view is the truth the human keeps; and the system guarantees they describe the same program, because one is generated from the other by a fixed rule. If the two ever disagree, that is a bug in the system, not a difference of opinion.

There is a second gain, quieter than the first. Today, every runtime ships a parser, because every runtime must read text. The parser is a large, complicated piece of software: it splits text into tokens, builds a tree, recovers from errors, and reports them in a helpful way. In Riza, the parser lives in the editor, where a human is writing and needs it, and not in the loader, which runs every time a program starts. The loader is smaller, simpler, and faster, because it never parses. The parser is still there when it is needed, and it is better for living in one place: one parser, maintained once, used by every tool, instead of a parser reimplemented inside every runtime. Chapter 9 defines the binary format the loader reads. Chapter 15 designs startup around it, so that starting a program is mostly reading, not computing.

One more consequence is worth stating now, because it shapes the whole design. A binary file can be checked quickly, before it runs, because its shape is fixed. The loader can verify the header, confirm the sections are the sizes they claim to be, and check that every reference points inside the file, all before executing a single instruction. A malformed file is caught at the door. A text file cannot be checked this way, because its meaning only emerges from parsing it, and parsing it is the expensive step the binary form skips. Validity checking is not an extra feature. It is a property the binary form gives for free, and Chapter 9 uses it.

## 2.3 One shared form from top to bottom

Every compiler has a middle form. The middle form is the list of simple steps that sits between what the programmer writes and what the machine runs. The programmer writes in a language built for humans. The machine runs instructions built for hardware. The middle form is the bridge: the compiler turns the human language into middle form, then turns the middle form into machine instructions. It is called a middle form because it lives in the middle of that journey. It is simple on purpose. Each step does one small thing: add two numbers, compare two values, jump to another step, load from memory, store to memory. Anything complicated is built from these steps, not added to them.

Today, every layer has its own middle form, and every boundary translates between them. The language has one. The runtime has another. The operating system has its own structures for the same ideas. The shell has another still. Section 1.2 followed one keystroke through that stack: driver, kernel, display server, toolkit, runtime, app, and back down again, with data copied and translated at every crossing. The string that gets copied four or five times before it reaches the screen is copied because each layer keeps its own private copy of the world in its own private format. The translation is not a detail. It is the work the machine spends most of its time doing.

The plan in Riza is one shared middle form for the language, the tools, and the operating system. The compiler produces it. The formatter reads it. The tester runs it. The shell executes it. The kernel schedules it. A program is written once, turned into the shared form once, and then every tool in the system works on the same form. Work done once is done once. There is no second translation at the next boundary, because there is no next form to translate into.

Why sharing matters more than cleverness is the key point, and it is easy to miss. A clever middle form used by one layer saves that one layer. A plain middle form shared by all layers removes the translation tax at every boundary in the system. The win is not in the form itself. It is in the boundaries removed. Most of the effort in today's stack is spent crossing boundaries between forms: serializing, parsing, converting, copying, checking. Remove the boundaries and the effort goes away with them, even if the shared form itself is nothing special. The shared form does not need to be brilliant. It needs to be good enough for every layer and shared by all of them. That is a harder requirement than it sounds, and it is the real design work of Chapter 10.

The shared form also makes the tools cheap, in a way that is worth spelling out. A tool that understands the middle form understands every program in the system, because every program is in that form. The formatter does not need a parser for each language. The tester does not need a runner for each runtime. The debugger does not need a separate view of the program's state, because the state is already in the form the tool reads. Each tool is smaller, because it does one job on one form instead of many jobs on many forms. And each tool improves every program at once, because there is only one form to improve. The same argument runs in the other direction: a program written once can be read, tested, formatted, and debugged by every tool, without any of them needing to know what language it was written in.

Be honest about the constraint, because it is real. One form must serve every layer, so it cannot be tuned for one job alone. A form designed only for the compiler could be rich and expressive. A form designed only for the kernel could be minimal and fast. The shared form has to be both simple enough for the kernel and rich enough for the compiler, and that tension is the design problem. The answer is not to make the form large enough to cover everything, because a large form is a complicated form, and a complicated form is slow to load and hard to check. The answer is to make the form small and to build complicated things from small steps, the way the middle form already works. Chapter 10 defines the form itself: its operations, its layout, and the step by step path from middle form to native machine code. Chapter 12 builds the optimizer on the same form, so that optimization is written once and benefits every program in the system.

There is a connection to section 2.1 worth naming. A shared form is itself a form of prediction. When every layer agrees on one form, each layer can predict what the next layer will do with a piece of work, because the work arrives in a shape it already understands. Nothing is re-examined, re-parsed, or re-checked at the boundary, because the boundary does not re-interpret the work. The shared form is the prediction that the whole system makes about itself, and like every prediction in this book, it saves the work of sending the same information twice.

## 2.4 Small core, no hidden work

The core is the part everything depends on. In an operating system, the core is the kernel and the small set of services every program needs. In a language, the core is the smallest set of operations every program uses. The core is the part that cannot be removed, so its size and its behavior set the floor for the whole system. A large core makes everything large. A core that does hidden work makes everything unpredictable. So the core in Riza is small on purpose, and it does no hidden work.

Small on purpose means the core does only what must live in the core: load a program, run it, hand out memory and take it back by the program's own structure, and talk to hardware through small drivers. Everything else is a module outside the core. A module can be added, removed, or replaced without touching the core, and a program that does not need a module does not pay for it. This is the opposite of today's shape, where the core grows with every release as features are baked in, and every program pays for all of them whether it uses them or not. Chapter 22 designs the kernel on this rule, and Chapter 34 guards it as the system grows, because the pressure to add to the core never stops and the rule has to be defended every time.

Small is not an aesthetic choice. It is a practical one, for three reasons. First, small is checkable. A person can read the whole core and understand what it does. A core nobody has read in full is a core nobody can trust. Second, small is measurable. Every byte the core occupies and every millisecond it spends can be accounted for, which is what section 1.5 demands of the whole system. A large core hides its costs in its size. Third, small is fixable. A bug in a small core has fewer places to hide, and a fix in the core is a fix everywhere, because everything depends on it. A large core spreads the same bug across more code and more copies.

No hidden work is the sharper rule, and it is the one this book is held to. Hidden work is anything the machine does that the user did not ask for, cannot see, and cannot turn off. Background indexing that scans files while the user is typing. Telemetry that sends usage data to a server the user never chose. An update check that runs on a schedule the user cannot see. A service that wakes up on its own and stays awake. All of it is work the user pays for in RAM, in CPU, in power, and in attention, and none of it appears in any number the user is shown. The rule in Riza is simple: if the machine is busy, the user can ask the system why, and get an answer in plain words. Every process is visible. Every cost is attributable. Nothing runs on a schedule the user cannot see, and nothing the user turns off comes back on its own.

The test for any new feature follows from that rule. Can the user see it? Can the user measure what it costs? Can the user turn it off? If the answer to any of those is no, the feature does not ship in that form. It is redesigned until the answer is yes, or it does not ship at all. This is not a guideline. It is the standard the rest of the book is held to, and Chapter 3 writes it down as a rule of the build, so that it cannot be quietly dropped when a feature is tempting.

Two parts of the design already show what the standard looks like in practice. Memory in Riza is freed by the program's own structure, not by a background collector, so there is no hidden process scanning memory and no pause that arrives unannounced. Chapter 6 builds that. And every program carries a debug log layer, a plain record of what it did and when, so that when something goes wrong the evidence is already there instead of having to be reconstructed. Chapter 17 builds that. Neither is an extra. Both are what the no hidden work rule looks like when it is taken seriously: the system explains itself as it goes, instead of hiding its work and asking to be trusted.

One objection should be answered now. Small does not mean weak. A small core with good modules does more than a large core with everything baked in, because each module can be replaced, improved, or removed without touching the rest. A large core is brittle: changing one part risks breaking another, so changes get slower and rarer as the core grows. A small core is a foundation, not a limit. The limit is set by what the modules can do, and modules can do anything, because they are ordinary programs with the full system behind them.

## 2.5 Prove it on real hardware or it does not count

Everything in this chapter so far is an idea. Ideas are cheap. This section states the rule that keeps the idea honest: nothing counts without a real number from real hardware. An idea that cannot be measured is a preference, not a design. A preference is a taste, and tastes cannot be argued with, which is exactly why they cannot be built on. A design makes claims that can be checked, and if the check fails, the design changes. That is the deal this book makes with its reader, and this section is where the deal is written down.

The judge is the four numbers from section 1.5: size, RAM, speed, power. Every design in this book is measured against them, on the same machine, doing the same task, with the median of repeated runs and the slowest run reported too, cold and warm stated, method stated, the whole job measured from start to finish. Those are the seven rules for honest numbers, and they apply to this book's own claims first, before they are applied to anyone else's. A chapter that claims an improvement reports its scoreboard table in the form section 1.5 defines, with today's number, Riza's number, the machine, and the method. A chapter that cannot fill in the table has not finished its work.

Why real hardware, and why this hardware in particular. The target machine is an HP All-in-One with a Ryzen 3 processor, 8 GB of RAM, and a spinning hard drive. It is the machine the system is built for, so it is the machine the system is measured on. A faster machine would flatter the design, because its extra speed would hide the costs the design is supposed to remove. A simulator would hide them more thoroughly, because a simulator does not have a spinning drive with real seek times, a real cache with real misses, or real RAM pressure when too many programs are open. Those are the costs that matter on the target machine, and they only show up on the target machine. If a design does not win on the Ryzen 3 with its spinning drive, it does not win. Chapter 31 runs the tests there: boot, tools, daily use. Chapter 32 runs the benchmarks there, against today's stack, and collects every scoreboard table in one place.

The burden of proof is on the new idea, not on the old stack. Today's stack is the default. It is installed, it works, and people know how to use it. Riza has to beat it to earn its place, and a tie is a loss, because switching to a new system costs effort, and effort spent for no gain is waste, the very thing this book exists to remove. That is a high bar, and it is set deliberately high. A design that wins on all four numbers earns its place. A design that wins on three and loses on one has to say so plainly and argue the trade in the open, so the reader can judge it. A design that loses on the numbers does not ship, however elegant the idea behind it.

If Riza loses on a number, the book says so. That is rule 7 from section 1.5, and it is the rule that makes the other six believable. A book that only ever reports wins is a book that is hiding its losses, and a reader who catches one hidden loss will stop believing the wins. The scoreboard tables in Chapter 32 will show losses where they exist, with the trade explained and the reason given. The goal is to win on all four numbers together. The commitment is to report the numbers as they are, win or lose.

The proof is public. Chapter 32 fixes the exact task list and the exact inputs, so that any reader can repeat every measurement in this book on their own machine and check the numbers. The method is stated alongside every figure, because a number without a method cannot be repeated and therefore cannot be checked. A claim nobody can check is a claim nobody should believe, and this book does not ask for belief. It asks for repetition. Run the task, read the number, compare it with the table. That is the whole proof, and it is available to anyone with the target machine and the time to run it.

Chapter 1 named the waste. This chapter named the idea. The next chapter writes down the rules and limits that keep the build honest while the idea is turned into a real system: the target machine, the hard zero budget, and what counts as a chapter done.

---

The idea is one idea with five parts. Predict well and you store little, because what you can predict you do not have to store. Keep binary as the truth and text as a view, so loading is reading instead of re-translating. Share one form from top to bottom, so work done once is done once. Keep the core small and do no hidden work, so the system can be seen, measured, and turned off. And prove all of it on real hardware, because an idea that cannot be measured is a preference, not a design. The rest of the book is this idea, worked out one chapter at a time.
