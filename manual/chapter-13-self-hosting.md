# Chapter 13: Self hosting: the compiler builds itself

Chapter 11 built the first compiler in Python. Chapter 12 optimized what it writes. This chapter takes the ladder down.

Self hosting means the compiler is written in the language it compiles. The Riza compiler is written in Riza, and it builds itself: the compiler reads its own source, the way it reads any program's source, and writes the file that is itself. That is the whole idea, and it is the point the last two chapters were building toward. Section 11.2 said the host compiler is a ladder, not the building, and that the ladder comes down in Chapter 13. This is Chapter 13, and the ladder comes down here.

Why it matters is the independence the whole book is built on. As long as the compiler is written in Python, the system depends on Python: every Riza program passes through a tool written in another language, running on another language's runtime. Once the Riza compiler builds itself, the chain is Riza all the way down. Riza programs are built by a Riza compiler, running on a Riza loader, with no Python anywhere in the chain. The system stands on its own, the way section 3.2 requires: the tools are the user's own, and nothing in the build depends on a tool the system does not own.

There are two sections. The first ports the compiler into Riza, piece by piece, in the order the compiler itself works, testing each piece against the Python version before the next one starts. The second proves both compilers produce the same output, with the bootstrap test: the Python compiler builds the Riza compiler, the Riza compiler builds itself, and the two results are compared byte for byte.

One warning, stated up front the way Chapters 4 through 12 stated their own. This chapter designs the self-hosted compiler. It does not build it. No self-hosted compiler exists yet, and no claim in this chapter says one does. The chapter also claims no measured improvement on real hardware, so no scoreboard table is due. The numbers here are arithmetic on the chapter's own examples, counted by hand. The measured proof comes in Chapter 31, on the real PC, with the comparison against today's stack in Chapter 32.

## 13.1 Porting the compiler into the new language

Start with what the port is, in one sentence. The port rewrites the compiler in Riza, piece by piece, without changing what the compiler does.

Say plainly what the port is not, because the list is the discipline of the whole chapter. It is not a rewrite from scratch. The design is the design Chapter 11 wrote down: three stages, one job each, the same checks, the same middle form, the same file. A rewrite from scratch would be a second compiler with a second set of decisions, and two compilers with different decisions are two compilers that disagree. The port keeps every decision and changes only the language it is written in. It is not a chance to add features. A feature the port adds is a feature the Python compiler does not have, and the two compilers would disagree about every program that used it. Features are designed in the open, the way Chapter 3 requires, and added to both compilers at once, or not at all. And it is not a chance to change the language. The language is the same language. The compiler is the same compiler. Only the host language changes.

The port follows the compiler's own order, because the compiler's order is the order its pieces depend on each other. The compiler works in three stages, from section 11.1: read and check the text, produce the middle form, write the file. The optimizer sits between stage two and stage three, from Chapter 12. So the port has five pieces, in this order: the parser, the checker, the middle-form producer, the optimizer, and the file writer. Each piece is ported and tested against the Python version's output before the next piece starts. The Python version is the reference, and the Riza piece must match it, or the port stops there until it does.

The parser goes first, for two reasons, and both matter. The first is that every other stage depends on it. The checker checks the tree the parser builds. The middle-form producer turns the tree into steps. A parser that reads the text differently changes everything downstream, so it is ported first and proved first. The second reason is that the parser is the part the editor also uses. Section 2.2 said one parser, maintained once, used by every tool, and section 11.1 said the editor's parser and the compiler's parser are the same parser, shared. The ported parser is that same parser, now written in Riza: the editor and the compiler still share one parser, and the parser is still maintained once. Porting it first means the editor gets the Riza parser as soon as the compiler does, and the two can never drift apart, because there is still only one of them.

The test for the parser is the tree. The Riza parser reads the same text the Python parser reads, and it must produce the same tree: the same names, the same values, the same structure, piece by piece. The three programs the book has already counted are the first test texts: `print("hello")`, 15 bytes; the hello loop, 68 bytes; the branch, 59 bytes. Each one is read by both parsers, and the two trees are compared. Then the compiler's own source, which is the largest text either parser will read, and the most demanding test of the two, because it uses every shape in the language: values, lists, records, functions, branches, loops, error checks. A parser that reads the compiler's own source the same way twice is a parser that reads the language.

The checker goes second. The checker is the rest of stage one: the checks section 11.1 listed. It checks the types, from Chapter 5. It checks the ownership, from Chapter 6. It checks the errors, from Chapter 7. It checks the calls, from section 7.1. And it checks the names. The test for the checker is the refusal: the Riza checker must refuse the same programs the Python checker refuses, with the same plain-words error naming the same line, and it must accept the same programs the Python checker accepts. The 7 refusal tests from section 11.3 are the checker's test, and each one must produce the same refusal from both checkers: the number added to a string, the unchecked error, the value with no owner, the double free, the use after free, the wrong kind to a function, the wrong number to a function. A checker that refuses a program the other accepts has a hole in one direction. A checker that accepts a program the other refuses has a hole in the other. Either hole is found by the comparison, because the two checkers are run on the same programs and their answers are compared, refusal by refusal.

The middle-form producer goes third. It is stage two: it takes the checked tree and turns it into the list of simple steps Chapter 10 defined, builds the name table, assigns the positions, and computes the jump targets. The test for the producer is the middle form itself: the same operations, in the same order, with the same operands, the same name table, and the same jump targets. The hello loop is the concrete check, because its middle form is already counted by hand in section 4.4: 14 operations, 24 bytes of code, a 13 byte name table, 37 bytes dense, with JUMP_IF_FALSE to position 23 and JUMP back to position 4. Both producers must write exactly that. A producer that writes a different operation, a different table, or a different jump target is a producer that changed the program, and the change is caught by the comparison, operation by operation.

The optimizer goes fourth, in the place Chapter 12 put it: between stage two and stage three. The ported compiler includes the optimizer, and the optimizer's output must match too, because an optimizer that changes the middle form differently in the two compilers would produce different files from the same source, and the bootstrap test in section 13.2 would fail for a reason that is not a bug in the port. The test for the optimizer is the optimized middle form. The worked example from section 12.1 is the concrete check: the program that folds from 19 operations and a 116 byte file to 3 operations and a 40 byte file, still printing 9. Both optimizers must produce the same 3 operations. And the hello loop is the other check: the optimizer changes nothing in it, no dead code, no foldable constants, no functions, so both optimizers must leave it at 14 operations and 72 bytes. An optimizer must not change a program it has nothing to improve, and the hello loop is the test of that, in both compilers.

The file writer goes last. It is stage three: it takes the middle form and the tables and lays them out in the shape Chapter 9 defined, the 33 byte header, the code section, the data section, and the dictionary section. The test for the writer is the file itself, byte for byte. The hello loop's 72 byte file is the concrete check, because section 9.2 counted it by hand: 33 bytes of header, 24 of code, 0 of data, and a dictionary section of 15 bytes, the 13 byte name table plus a 1 byte function count plus a 1 byte comments count. Both writers must write exactly that file, every byte in its place. The file is the compiler's product, and the product is where the whole port is judged: two writers, one file.

One piece at a time is the discipline that makes the port checkable. At any moment, only one piece is new. The rest of the compiler is still the Python version, which is tested and known, and the new piece is checked against the piece it replaces. If a test fails, the new piece is the suspect, not the whole compiler. Port two pieces at once and a failure could be in either, and the search is twice as wide. Port all five at once and a failure could be anywhere, and the port is a rewrite, which is the thing this section said it is not. The port is five small steps, each one proved, not one big step taken on faith. That is the same discipline as the optimizer's passes in Chapter 12: one change, one check, and the next change only after the check passes.

The compiler eats its own cooking, and that is worth a paragraph, because it is the first time the language is tested on a program of real size. The Riza compiler source is a Riza program, and it must pass the compiler's own checks. Its types must check, from Chapter 5. Its ownership must check, from Chapter 6: every value has one owner, and the owner frees it when it is done. Its error checks must be in place, from Chapter 7: every call that can fail is checked before its result is used. The compiler is the first large Riza program, and it is checked by the rules it enforces. A compiler that cannot compile itself cleanly is a compiler whose rules do not fit real code, and that is a finding worth having early, while the rules are still easy to change, rather than late, when programs are already written against them.

The port uses only the language as the Python compiler already implements it. That is a rule, not a suggestion, and it follows from the order of the work. The Riza compiler source is built first by the Python compiler, in section 13.2, so the source cannot use a feature the Python compiler does not understand. If the port needs a feature the language does not have, that is a language change, made in the open the way Chapter 3 requires, added to the Python compiler first, and then used in the port. No feature is invented during the port, because a feature invented during the port is a feature the two compilers might implement differently, and the whole point of the port is that they agree. The language grows one rule at a time, the way section 11.1 said the grammar grows, each rule written down and tested before it is used.

One more job carries over, and it is the job that makes Appendix A possible. Section 4.1 said the compiler counts the operations in real programs, and the tally is the data the final dictionary is built from. The ported compiler keeps counting, the same way, because it already walks every operation in every program it builds. The tally does not restart and does not change hands. The count is the count, whichever compiler made it, and the dictionary in Appendix A is built from the same data before and after the port. A tally that restarted with the port would throw away everything the Python compiler counted, and a tally that counted differently would build a different dictionary. Neither happens, because the counting is part of the compiler, and the compiler is the same compiler.

What happens to the Python compiler, once the port is done, is stated here so the plan is on the record. The ladder comes down, but it is not thrown away. The Python compiler is kept as a record and as a recovery path: if the Riza compiler is ever lost, the Python compiler can rebuild it from the source, because the source is text and the Python compiler reads text. But it is not part of the system. It is not in the shipped image, which Chapter 30 defines. No Riza program depends on it. The build tool, which Chapter 14 designs, runs the Riza compiler, not the Python one. The ladder is stored in the workshop, not left leaning against the building, and the building stands without it.

## 13.2 Proving both compilers produce the same output

The port in section 13.1 is five pieces, each one tested against the Python version. This section is the test that proves the whole port at once: the bootstrap test. It has three steps, and the names for them are fixed here so the rest of the section can use them.

The input is the Riza compiler source, one text, written in Riza, the port from section 13.1. The Python compiler is the host compiler from section 11.2. R1 is the first Riza-built compiler: the file the Python compiler writes when it builds the Riza source. R2 is the file R1 writes when it builds the same source. R1 and R2 are both files in the shape Chapter 9 defined, and both are the compiler, built from the same source by different compilers.

Step one: the Python compiler builds the Riza source, and the output is R1. This is the last time Python touches the chain. The Python compiler reads the Riza text, checks it, produces the middle form, writes the file, and the file is R1, a Riza program, ready for the loader to run. After this step, every build is Riza building Riza, and Python is out of the chain.

Step two: R1 builds the same source, and the output is R2. R1 is a Riza program, running on the loader, doing the compiler's job on the compiler's own source. It reads the same text, runs the same checks, produces the same middle form, and writes the file. The file is R2, a Riza program, built by a Riza compiler. This is the moment the compiler builds itself: the tool that builds Riza programs is itself a Riza program, built by itself, from its own source.

Step three: compare R1 and R2, byte for byte. Every byte, from the first byte of the header to the last byte of the dictionary section. The comparison is a straight walk through both files, one byte at a time, and it ends in one of two ways.

If the two files match, the port is proved. Two different compilers, one written in Python and one written in Riza, produced the same output from the same source, and the Riza compiler reproduced itself exactly. The port changed nothing about what the compiler does. The ladder can come down, because the system builds itself without it. R2 can build R3, and R3 will match R2, and the chain continues, each generation identical to the last, because a compiler that reproduces itself once reproduces itself every time, as long as the source does not change.

If the two files do not match, the difference is a bug in one of them, and the bug is found by comparing the outputs. The first byte that differs names the place to look, and the fixed file layout says which part it is in: the header is bytes 0 to 32, the code section follows, then the data section, then the dictionary section. A difference in the header names a field the writer computed differently. A difference in the code section at a known position can be looked up in the middle form, and the operation at that position says what the two compilers did differently. A difference in the dictionary section names a table entry one of them counted differently. The comparison does not only say the compilers disagree. It points at the disagreement, and the pointing is what makes the bug findable.

The comparison only works if the compiler is deterministic, and determinism is a requirement on the compiler, stated here. Deterministic means the same source in gives the same file out, every time, with no variation from run to run. No timestamp in the file, and the header in section 9.1 has none, which is a help the format gives for free: a file that stamped the time of day into its header would differ every time it was built, and the comparison would fail for a reason that is not a bug. Name table entries in the order the names are defined, so the table is the same every time. Sections in fixed order, code, data, dictionary, the way section 9.2 laid them out. Jump targets computed from the code, not guessed. No random numbers, no dependence on the time of day, no dependence on the order the filesystem returns files. Determinism is tested on its own, before the bootstrap test runs: build the same source twice with the same compiler and compare the two files. If they differ, the compiler is not deterministic, and the bootstrap test cannot run until it is, because a comparison between two compilers means nothing when one compiler cannot agree with itself.

Now the worked check, because a test described in words is worth less than a test worked through on programs the reader has already counted. Three compilers build each of the three counted programs, the Python compiler, R1, and R2, and all three must produce the same file, byte for byte. The table gives the size each file must be, and the size is the first check: a file of the wrong size is already a failure, before any byte is compared. The byte comparison is the real check, because a file of the right size with the wrong bytes is still a failure.

| Program | Text | Dense | File, all three compilers |
| --- | --- | --- | --- |
| `print("hello")` | 15 bytes | 11 bytes | 46 bytes |
| Hello loop | 68 bytes | 37 bytes | 72 bytes |
| Branch | 59 bytes | 38 bytes | 73 bytes |

Check the file sizes, because two of them are new. The hello loop's 72 bytes were counted in section 9.2: 33 header, 24 code, 0 data, and a dictionary section of 15 bytes. The `print("hello")` file is 33 header, 4 code, 0 data, and a dictionary section of 9 bytes: the 7 byte name table from section 8.2, a 1 byte function count saying 0, and a 1 byte comments count saying 0. 33 plus 4 is 37, plus 0 is 37, plus 9 is 46. The branch file is 33 header, 18 code, 0 data, and a dictionary section of 22 bytes: the 20 byte name table from section 7.2, a 1 byte function count saying 0, and a 1 byte comments count saying 0. 33 plus 18 is 51, plus 0 is 51, plus 22 is 73. All three programs are counted the same way, in the shape Chapter 9 defined, and all three compilers must produce the same three files.

The bootstrap test joins the suite from section 11.3, and the suite grows by one. Seventeen operation tests, seven refusal tests, six validity tests, three round-trip tests, and one bootstrap test. 17 plus 7 is 24, plus 6 is 30, plus 3 is 33, plus 1 is 34. The suite has 34 tests, and 34 is the floor, the way 33 was the floor in section 11.3. The count grows as the language grows, and the bootstrap test stays in the suite for as long as the compiler is changed, because it is the test that proves a change to the compiler did not change what the compiler does.

The 33 tests are run through the Riza compiler as well as the Python compiler, because the bootstrap test alone proves the two compilers agree on one program, the compiler's own source, and the suite proves they agree on everything else. The 17 operation tests run through R1 and expect the same answers: ADD still gives 5, add of 3 and 4 still gives 7, the hello loop still prints `hello` three times, the branch still prints `done`. The 7 refusal tests run through R1's checker and expect the same refusals, naming the same lines. The 6 validity tests run on R1's output, because R1 must produce a valid file. The 3 round-trip tests run on R1's output before the optimizer, the way section 12.1 said the round trip is a property of the compiler's middle form. Both compilers, same suite, same expected results. A test that passes through one compiler and fails through the other names the piece that differs, the way the bootstrap comparison names the byte that differs.

The test runs on the target PC, the way section 2.5 demands, and it runs on every change to the compiler. A compiler that changes must prove itself again, because a change to the compiler is a change to every program the compiler builds. The tester in Chapter 20 runs only what changed, so the suite stays fast as it grows, but the bootstrap test runs on every change to the compiler itself, without exception, because the compiler is the one program every other program passes through, and a change to it is a change to everything downstream. Section 3.1 set one limit on the build itself, and it applies here: a compile that takes an hour is a compile nobody runs twice, so the bootstrap test must run fast enough that running it is not a chore, and the compiler is small enough to be fast, the way section 11.2 designed it.

Say plainly what the bootstrap test does not prove, because the limits are as much a part of the design as the test itself.

The first limit is the sharpest: agreement is not correctness. The bootstrap test proves the two compilers agree. It does not prove either one is right. If both compilers shared the same bug, the bootstrap test would pass, because both would produce the same wrong output, and the comparison would find nothing to disagree about. The test that proves the compiler is right is the 33 tests from section 11.3, because they test behavior against results computed by hand, not against another compiler's output: ADD gives 5 because 2 plus 3 is 5, the hello loop prints `hello` three times because the loop runs three times, the branch prints `done` because 20 is not less than 18. The hand counts in Chapters 4, 7, 8, and 9 are the ground truth the tests rest on, and a bug in the design would show up there, where the reader can count it, not in the comparison, where two copies of the same bug agree with each other. In 1984, Ken Thompson showed the hard version of this point: a compiler can carry a change into the programs it builds, and a self-hosted compiler can carry it into itself, so that the change survives even when the source is clean. The book's answer is the independent tests, and the hand counts behind them, because a test that compares a compiler against its own output can only prove agreement, and a test that compares a compiler against a hand-computed answer can prove correctness.

The second limit is time. The bootstrap test proves the compiler at one moment. A change to the compiler needs the test again. A port proved in March proves nothing about a compiler changed in April, because the April compiler is a different program, and a different program needs its own proof. That is why the test runs on every change, and why it stays in the suite: the proof is not a certificate the compiler earns once and keeps. It is a test the compiler passes every time it changes, or it goes back, the way section 3.3 said a chapter that fails the test goes back.

The third limit is scope. The comparison proves the two compilers agree on the compiler source. The 33 tests prove they agree on everything else. Both are needed, and neither alone is enough. A bootstrap test without the suite would prove agreement on one program and nothing about the rest. A suite without the bootstrap test would prove both compilers are right on the tested programs and nothing about whether the port changed the compiler itself. Together they prove the port: the Riza compiler does what the Python compiler does, on the compiler's own source and on every program the suite covers.

The chapter counts as done when the bootstrap test passes on the target PC. That is the chapter's own done condition, stated here so the reader can check it, and it is part 5 of section 3.3: anything the book says runs on the target machine has been run there, or is marked plainly as waiting for the real-PC run. Until the bootstrap test has run on the target PC, the port is a design waiting for its proof, and the book says so. When it passes, the ladder is down, and the system stands on its own: Riza programs built by a Riza compiler, running on a Riza loader, with no Python anywhere in the chain. The next chapter builds the build tool, which runs the Riza compiler with one command, so that building a program is one act, not a sequence of steps the programmer must remember.

The self-hosted compiler is the compiler written in the language it compiles, and it is the point the ladder was built for: the port rewrites the compiler in Riza, piece by piece, parser, checker, middle-form producer, optimizer, file writer, each piece tested against the Python version before the next one starts, with the language, the design, and the checks unchanged, and only the host language different. The bootstrap test proves the port: the Python compiler builds the Riza compiler as R1, R1 builds itself as R2, and the two files are compared byte for byte, with the first differing byte naming the place to look, and the three counted programs built identically by all three compilers, 46, 72, and 73 bytes. The test joins the suite, making 34 tests, and it runs on the target PC on every change to the compiler, because a compiler that changes must prove itself again. The limits are stated in the open: agreement is not correctness, the test proves the compiler at one moment, and the comparison covers the compiler's own source while the suite covers the rest. The ladder is down. Chapter 14 builds the tool that runs the compiler with one command.
