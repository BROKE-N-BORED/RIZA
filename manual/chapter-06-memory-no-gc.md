# Chapter 6: Memory without a garbage collector

Chapter 5 defined the values. This chapter says where they live, and when they are freed.

Section 1.3 asked the hard question about memory. A running program keeps its data in two regions: the stack, a small fast region where short lived values live, and the heap, the large region where everything that must outlive one function call lives. Stack memory frees itself when a function returns, with no decisions to make. Heap memory is the problem. Free it too early and the program crashes. Never free it and the program grows until the machine runs out of memory. Today's answer is a garbage collector: a background worker that walks all of memory looking for what is done with, and reclaims it. That worker costs time, it costs CPU, and it stops the program while it works. Section 1.3 counted those costs, and the worst of them was a pause of 2.2 seconds.

This chapter gives a different answer. The program's own structure says when memory is done. Every value has an owner, and the owner frees it when it is done, right then, with no scan and no delay. Values that live and die together share one stretch of memory and are freed in a single act. Memory lives in three places, one for each lifetime. And when the machine runs out, the failure is clean, visible, and handled, not hidden.

There are four sections. The first names the rule: ownership, in plain words. The second covers arenas, where a group of values is freed together. The third names the three places memory lives: stack, heap, and static. The fourth states what happens when memory runs out, in what order.

One warning, stated up front the way Chapters 4 and 5 stated their own. This chapter designs the memory rules. It does not build the compiler that enforces them. That is Chapter 11. The ownership rule is checked before the program runs, by the compiler, and this chapter says what the compiler checks. The chapter also claims no measured improvement on real hardware, so no scoreboard table is due. The numbers here are arithmetic on the chapter's own examples, counted by hand, and the pause figures are callbacks to the sourced test in section 1.3. The measured proof comes in Chapter 31, on the real PC, and the comparison against today's stack comes in Chapter 32.

## 6.1 Ownership in plain words

The rule is one sentence: every value has exactly one owner.

The owner is the part of the program responsible for that value's memory. A value is made by some part of the program: a function that builds a list, a step that reads a file, a line that opens a window. The part that made it owns it. Ownership is a responsibility, not a possession. It means one thing: when the owner is done with the value, the owner frees its memory, right then, with no scan and no delay. The memory goes back the moment it is done, because the owner says so, and the owner is the only one who can say so.

Think of a library book. A book has a card in a pocket, and the card has one name on it: the name of the person who borrowed the book. That person is responsible for bringing it back. The library does not send someone to walk the streets looking for its books. It knows who has each one, because the card says so. Memory works the same way. Every value has one name on its card, and the name says who frees it. There is no search, because there is nothing to search for. The answer is written on the card.

Ownership can be handed over. The name on the card changes, and the value stays exactly where it is. Nothing is copied. A function that builds a list can hand the list to the part of the program that will use it, and the handover is the whole act: the old owner is done, the new owner is responsible, and the list itself never moves. The handover is visible in the code, the way section 5.4 demands: a line that hands a value over says so, and the cost of the handover is nothing, because nothing was copied and nothing was moved. The only thing that changed is the name on the card.

Ownership can also be lent out, and lending is different from handing over. A function that needs to read a list without keeping it can borrow the list: the owner lends it, the borrower uses it, and the loan ends when the borrower is done. The name on the card never changes. The borrower cannot free the list, because the borrower does not own it. The borrower cannot keep the list past the loan, because the loan has an end. Lending a book to a friend works the same way: the friend reads it and gives it back, and the library card still has your name on it. The owner stays the owner throughout.

Two rules follow, and they are the whole discipline. The first is that ownership is never shared by accident. Two owners would mean two frees, and freeing the same memory twice is a crash, because the second free hands back memory that no longer belongs to the program. So there is exactly one owner, and handing over means the old owner gives up the name at the same moment the new owner takes it. The second rule is that ownership is never left to nobody. A value with no owner is a value nobody frees, and memory nobody frees is memory that leaks, growing until the machine runs out. So every value has an owner from the moment it is made until the moment it is freed, and there is no gap in between.

Ownership forms a tree, not a circle. A value's owner sits above it, and the owner of the owner sits above that, up to the program itself. A circle would mean a value owns itself, directly or through a chain, and a circle has no end, so nothing in it would ever be freed. Section 1.3 named this problem: groups of objects that point at each other keep each other's counts above zero forever, which is why Python needs a tracing collector as backup for its reference counting. Ownership refuses the circle at the start. The compiler will not accept a program where a value owns its own owner, so the problem the tracing collector exists to solve never arises.

Now the contrast with the collector, because the contrast is the reason this chapter exists. A garbage collector is a background worker. It does not know what is done with. It finds out by walking all of memory, following every pointer from the live roots, marking what it can reach, and reclaiming the rest. That walk takes time, and while it walks, the program must stop, or the picture changes under it. Section 1.3 gave the numbers from a test published in February 2026 by Daniel Lemire, a small program that built a 1000 element linked list in a loop, deliberately stressing the cyclic collector. The worst pause was 2.2 seconds on Python 3.12 on Linux, 320 milliseconds on Python 3.14 on a Mac, and the same algorithm in Go peaked at 33 to 50 milliseconds. Read the test fairly, the way section 1.3 did: it was built to stress the collector, and ordinary programs see smaller pauses. But the pause is unbounded by design, it arrives without warning, and it arrives exactly when the program is busy allocating, which is when it can least afford to stop. Ownership has no pause, because there is nothing to stop for. The program never has to find out what is done with. It already knows, because the owner says so.

The checking happens before the program runs, and that is what makes the whole design affordable. The programmer writes who owns what, and the compiler checks it. A program that frees a value twice is refused. A program that uses a value after its owner freed it is refused. A program that leaves a value with no owner is refused. The refusal happens at build time, when the program is compiled, not at run time, when the user is waiting. The check costs the program nothing while it runs, because it already happened, once, when the program was built. That is the same shape as section 2.2: the work of understanding the program is done one time, by the programmer's tools, and never repeated by the machine that runs it. A garbage collector pays its cost every time the program runs. Ownership pays its cost once, at build time, and then the program runs free of it.

The honest counterpoint is that ownership costs the programmer some thought. The programmer must decide who owns each value, and must say so in the code. A garbage collected language lets the programmer skip that decision and pay for it later, in pauses and CPU and memory. The book's answer is the same as section 5.4's: the line is the price of knowing, and the price is worth paying. The programmer writes the program once. The user runs it every day. A decision the programmer makes once, in the open, is cheaper than a background worker the user pays for on every run, in RAM, in time, and in power.

## 6.2 Arenas: allocate together, free together

Some values live and die together. A step that reads a file builds a buffer for the file's bytes, a set of line values, a count, and a result. When the step ends, every one of those values is done at the same moment. Freeing them one at a time is honest work, but it is work the program does not need to do. They were born together, they die together, and they can be freed together.

An arena is one stretch of memory for a group like that. The program asks for the arena once, hands out pieces of it to the values in the group, and frees the whole arena in a single act when the group is done. The word arena is used because it is a space where work happens, and when the work is over, the whole space is cleared at once. One ask, one free, for the whole group.

Work through one example by hand, a step that reads a file of 12 lines and counts the words. The step builds 14 values. First, one buffer holding the whole file: 12 lines at 20 bytes each is 240 bytes. Second, 12 line records, one per line, each holding a 4-byte start position and a 4-byte length, so each record is 8 bytes and the 12 records together are 96 bytes. Third, one count of the words, which cannot be larger than the number of bytes in the file, 240, because each word needs at least one byte, so the count fits in 1 byte. Add them up: 240 plus 96 plus 1 is 337 bytes, in 14 values.

Without an arena, the step asks for memory 14 times, once per value, and frees it 14 times, once per value. That is 28 acts of bookkeeping for one step of work. With an arena, the step asks once, for 337 bytes, hands out the pieces, and frees once when the step ends. That is 2 acts. The saving is 26 acts, and the saving grows with the size of the group, because every value added to the group costs nothing extra to free.

|  | Asks for memory | Frees | Total acts |
| --- | --- | --- | --- |
| One value at a time | 14 | 14 | 28 |
| One arena for the group | 1 | 1 | 2 |

The arena also gives the cache a packed layout for free, which section 5.3 showed is the layout that matters. The arena starts on a cache line boundary, by design, so the 12 line records sit together in 96 bytes, which is exactly 2 cache lines: 64 bytes in the first line, 32 in the second. Reading all 12 records costs 2 loads. If the records had been scattered, one per line, the same 12 records would cost 12 loads. The arena packs them by construction, because the pieces are handed out one after another from a single stretch. The programmer gets the packed layout by using the ordinary shape, the way section 5.3 said the list already gives it.

Say plainly when arenas fit and when they do not. An arena fits a group with one lifetime: one file read, one request, one frame of work, one pass over a list. The test is simple: do all the values die at the same moment? If yes, they belong in one arena. An arena does not fit a value that must outlive the group. A result the caller keeps, a list the program holds onto, a name that lives past the step: those belong to an owner, under the rule in section 6.1, not to the arena. Putting a long lived value in a short lived arena would free it too early, and the program would use memory that no longer belongs to it. The arena is for the group. The owner is for the survivor.

An arena can grow, and growing is a visible act, the way section 5.4 demands. If the group turns out bigger than the arena, the program asks for a bigger stretch, copies the contents into it, and frees the old one, and the line that does it says so. Growing is a copy, and the copy costs time and memory, so the program does not grow an arena in silence. The programmer who grows an arena in a loop sees the growth in the code, and can decide whether the loop is the right shape. The same rule as the list in section 5.2: the copy is visible, not hidden.

Arenas and ownership work together, and the combination is the whole design. The arena itself is owned: one owner holds the arena, and the arena holds the group. Everything inside the arena belongs to the arena's lifetime, and the arena's owner decides when that lifetime ends. Ownership says who frees. The arena says how many values one free covers. Together they mean the program never pays for a background worker, and never pays for a dozen frees where one will do.

## 6.3 Stack, heap, and static

Memory lives in three places, and the place a value lives in is decided by how long the value lives. A value that lives as long as one function call lives on the stack. A value that lives as long as its owner says lives on the heap. A value that lives as long as the program runs lives in static memory. Three lifetimes, three places, and the programmer picks the place that matches the lifetime.

The stack is a pile. A function call puts its values on top of the pile, and when the function returns, its values come off the top. The pile in section 4.4 is a stack: operations put values on top, take values off the top, and put results back. The call stack works the same way, one pile per chain of function calls. Freeing on the stack is the cheapest act in the whole system, because it is just moving a pointer back: the pointer that marks the top of the pile moves down past the values that are done, and those values are forgotten in a single act. No decisions, no search, no scan. A function that returns frees everything it built, at once, by moving one pointer.

The stack is small, the way section 1.3 said: a small, fast region, against the heap's large region. So the stack holds small, short lived values: the numbers a function works with while it runs, the count in a loop, the result of a calculation on its way to somewhere else. The `count` in the worked example of section 4.4 is a stack value: it is made when the loop starts, it changes with each pass, and it is done when the loop ends. A big value does not belong on the stack. A list of ten thousand records, a file's whole contents, a window's pixels: those belong on the heap, where there is room for them. The compiler knows the size of every value, from Chapter 5, so it can refuse a value too big for the stack before the program runs, instead of letting the program find out by crashing.

The heap is the large region, and it holds the long lived owned values. A list that outlives one function call lives on the heap. A file's contents, held while the program works through them, live on the heap. A record the program keeps while the user edits it lives on the heap. Heap values are freed when their owner says so, right then, under the rule in section 6.1. There is no scan and no delay: the owner is done, the memory goes back. Arenas live on the heap too: an arena is one heap stretch, handed out in pieces, freed in one act. The heap is where ownership does its work, because the heap is where values outlive the function that made them, and something must decide when they are done. That something is the owner.

Static memory holds the program's own data, the data that lives for the whole run. The name table from Chapter 4 lives here: the names and strings of the program, stored once, read by number, needed from the first line to the last. Constants live here: numbers and text that never change. The opcode dictionary lives here: the shared codebook of operations, the same for every program. Static memory is loaded once, with the program, in the data section and the dictionary section of the binary file, which Chapter 9 defines. The loader knows the size of each section from the file header, so there is no surprise: the static memory a program needs is stated in the file, counted at load time, and held until the program ends. It is freed as part of clean shutdown, which Chapter 15 designs: when the program ends, its static memory goes back with everything else.

Here are the three places side by side:

| Place | What lives there | When it is freed | Cost of freeing |
| --- | --- | --- | --- |
| Stack | Short-lived values tied to one function call | When the function returns | Moving a pointer back, one act |
| Heap | Long-lived owned values, arenas | When the owner says so | One act per value, or one act per arena |
| Static | The program's own data, name table, constants | When the program ends | Nothing until shutdown |

The sizes from Chapter 5 make the cost of each place countable. A 4-byte record on the stack costs 4 bytes. A list of 10,000 4-byte records on the heap costs 40,000 bytes, because 10,000 times 4 is 40,000. A name table of 200 names costs the sum of its entries, counted the way section 4.3 counts them. The program can add up its memory the way it adds up its bytes, because every value has a stated size and every place has a stated rule. Nothing is free, nothing is secret, and the arithmetic is checkable by any reader with a pencil.

The three places are not a ranking of good and bad. Each fits a lifetime, and the programmer picks the place that matches. A value that lives for one call goes on the stack, because the stack frees it for free. A value that lives for an owner goes on the heap, because the heap holds it until the owner is done. A value that lives for the whole run goes in static memory, because it is never freed until the program ends. The wrong place is a mistake the compiler can catch: a value on the stack that outlives its function, a value on the heap with no owner, a value in static memory that changes. The compiler checks the pick, the way it checks ownership, before the program runs.

Each process gets its own stack and its own heap, so one program's memory is not another program's memory. Chapter 24, on processes and scheduling, starts and stops processes, and when a process stops, its stack and heap go back to the system. That is the boundary ownership does not cross: ownership is the rule inside one program, and Chapter 24 is the rule between programs.

## 6.4 Out of memory: what happens, in what order

On an 8 GB machine, running out of memory is real. The graphics takes its share from the same memory, the system takes its share, and the rest is the program's. A program that asks for more than what is left will not get it, and this section states what happens then, in what order, so that no reader has to guess and no program has to improvise.

The order is four steps.

1. The program asks for memory, stating the size. Sizes are known, from Chapter 5, so the ask is exact. A list of 10,000 4-byte records asks for 40,000 bytes, not "some memory." The program asks for what it needs and no more, because the size is part of what the value is.

2. The request fails cleanly. The program gets a clear no, not memory, not a crash, not a hang. The failure is a fact the program is told, in the open, at the moment it happens. Nothing is half done: no memory is handed over, no value is left half built, no other part of the program is disturbed.

3. The failure comes back as an error the program can see and handle. Chapter 7 describes errors as values, not crashes: an error is a value the program holds, like any other value, and decides what to do with. Out of memory is an error of that kind. The program receives it, reads it, and chooses. There is no exception thrown across the program, no jump to a handler somewhere else, no hidden control flow. The error arrives where the ask was made, and the program deals with it there.

4. The program decides what to do. It can free something it no longer needs and try again. It can retry smaller, asking for less and doing the job in pieces. It can save its work and stop cleanly, the way Chapter 15 designs shutdown: save what matters, close the files, exit with the error stated. The choice belongs to the program, because the program knows what its work is worth and what can be given up. The system does not choose for it.

Say plainly what the system does not do. It does not pretend the memory exists, handing the program a pointer to memory that is not there. It does not kill another program in secret to make room, because killing another program's work without asking is hidden work, and section 2.4 forbids hidden work. It does not freeze and hope, leaving the user staring at a screen that has stopped responding. Each of those is a way of hiding the failure, and the failure is not hidden. It is reported, in the open, to the program that asked, and the user can ask the system why, the way section 2.4 promises.

A program can also plan ahead, because sizes are stated. A program that needs a list of 10,000 4-byte records knows before it asks that the list costs 40,000 bytes. It can ask the system how much memory is free, compare the two numbers, and decide whether the job fits before it starts, instead of finding out halfway through. A program that checks first is a program that fails early and cleanly, with its work still safe, instead of failing late, with half a job done and nothing saved. The check is cheap, because the sizes are already known. The program does not need to measure anything. It needs to add.

The kernel's side of the story belongs to Chapter 25. This section is the program's side: what one program does when its ask fails. Chapter 25 is the machine's side: what happens when the whole machine is out, who owns what, and how the kernel hands out memory between programs without waste. The two sides meet at the ask: the program asks, the kernel answers, and the answer is either memory or a clean no. Nothing in between.

One honest note closes the section. Running out of memory is a failure, and rule 7 of section 1.5 says a loss is reported as a loss. A program that runs out has asked for more than the machine has, and the honest response is to say so and stop cleanly, not to hide it. The user sees the error, in plain words, and knows the program ran out of room. A frozen screen tells the user nothing. An error tells the user what happened, and what happened is the truth. The book does not dress a failure up as anything else.

The memory rules are set now: every value has one owner, and the owner frees it when it is done. Values that live and die together share an arena and are freed in one act. Memory lives in three places, one for each lifetime, and the compiler checks the pick. And when memory runs out, the failure is clean, visible, and handled. The next chapter says how the program is put together around those values: functions, flow, and errors, starting with calling and returning, where ownership is handed over and borrowed every time a function runs.

---

Memory without a garbage collector rests on one rule: every value has exactly one owner, and the owner frees it the moment it is done, with no scan, no background worker, and no pause. Values that live and die together share an arena: one ask, one free, for the whole group, and the cache gets a packed layout for free. Memory lives in three places, stack for one function call, heap for an owner's lifetime, static for the whole run, and every value's size is stated, so the cost of each place is countable. When memory runs out, the request fails cleanly, the failure comes back as an error the program can see and handle, and the program decides what to do, in the open, with nothing hidden. The compiler checks all of it before the program runs, so the checking costs nothing while the user is waiting.
