# Chapter 24: Processes and scheduling

Part 6 began with the kernel: Chapter 22 designed the small core at the center of the system, what it does and what it does not do, with no layers for the sake of layers. Chapter 23 designed the boot: the firmware, the bootloader, and the first program, the shell, whose prompt is the first thing the user sees. But a machine that runs one program is a machine doing one thing at a time, and the user does more than one thing. This chapter designs what comes after the first program: how the kernel starts and stops programs in general, how it names them so one can be told from another, and how it shares the two cores fairly between them.

There are two sections. The first designs starting and stopping, with one start and one stop worked through. The second designs fair sharing on 2 cores, with the turns counted.

One warning, stated up front the way Chapters 4 through 23 stated their own. This chapter designs processes and scheduling. It does not build them. No scheduler exists yet, and no claim in this chapter says one does. The chapter claims no measured improvement, so no scoreboard table is due, and no time is claimed anywhere, because no sharing has been measured on the target machine. The numbers here are arithmetic on the chapter's own examples, counted by hand. The measured proof comes in Chapter 31, on the real PC.

## 24.1 Starting and stopping

Start with the job, in one sentence. A running program is a program the kernel has loaded and not yet finished, with its own pile, its own static memory, and its own place in the kernel's record.

A program on the disk is a file. A running program is that file loaded, checked, placed, translated, and started, the way section 15.1 designed it, and not yet finished, the way section 15.2 will finish it. While it runs, it holds its own memory: its own pile on the machine's stack, the way section 10.3 described, its own slots in static memory, the way section 6.3 described, and its own name table and function mapping, held for the run. Two programs running the same file are two running programs, not one: each has its own pile, its own slots, and its own place in the record, and what one does with its values does not touch the other's.

Chapter 22 left the naming open. Section 22.1 said it plainly: how the kernel names a running program, so the program that asked for it can tell one running program from another, is this chapter's design. Here it is.

The kernel names a running program with a number. The numbers are handed out in order, starting from 1. The shell is number 1, fixed by the boot, because it is the first program the kernel starts, the way section 23.2 designed it, and every program after it takes the next number in line. The number 0 is never handed out: 0 means no program, the way code 0 means no error in section 16.3, so a record that names 0 as a starter means no program started it, and a call that hands back 0 means no program was started.

The number is 4 bytes. Section 5.1 fixed the sizes: one byte counts to 255, two bytes count to 65,535, four bytes count to about 4.3 billion. The numbers run from 1 to 4,294,967,295. Say why 4 bytes and not 2. Two bytes would hold 65,535 numbers, and a machine that starts one program a second would use them up in about 18 hours: 65,535 seconds divided by 3,600 seconds in an hour is 18.2 hours. A long day of short programs would run the numbers out. Four bytes hold about 4.3 billion numbers, and at one start a second they last about 136 years, the same count section 16.2 gave for a 4-byte count of seconds. No boot in this book reaches the end of the numbers, but the limit is real even when it is far away.

The kernel counts up and never reuses a number while the machine runs, until the count wraps. When a program ends, its number is not handed to the next program, because a number that meant one program yesterday and another today is a number the user cannot trust in the log. When the count reaches the top, 4,294,967,295, it wraps, and the kernel hands out the smallest number no running program holds. Two running programs never share a number: the kernel checks before it hands one out.

The kernel keeps a record of every running program, in the kernel's memory, the record section 22.1 said the kernel keeps. One entry per running program, with five fields:

| Field | Bytes | What it holds |
| --- | --- | --- |
| Number | 4 | The running program's number |
| File | 1 plus the name | The file's name, a length byte and the characters, the shape section 4.3 fixed |
| Started by | 4 | The number of the program that started it, 0 for the shell, which the boot started |
| Memory held | 8 | The bytes the program holds, counted, updated as the program runs |
| State | 1 | 0 for waiting, 1 for running |

When a program ends, its entry is removed, and the bytes go back. Count one entry by hand, for the hello loop: the number is 4 bytes, the file `hello` is 5 characters plus the length byte, 6 bytes, the starter is 4 bytes, the memory held is 8 bytes, and the state is 1 byte. Four plus 6 is 10, plus 4 is 14, plus 8 is 22, plus 1 is 23 bytes. The memory the program holds is a count in the record, not the memory itself: the record holds how many bytes, and Chapter 25 designs how the kernel tracks which runs those bytes are.

Now say how starting works, following the worked start in section 22.1, with the naming added. A program asks the kernel to start another program, by calling the kernel's start routine by number, the way a program calls a core-library routine by number from section 16.1, and naming the program file.

The kernel runs two checks before the loader runs, in order, the way section 22.1 counted them. First, the file exists. The kernel asks the filesystem service for the file, and the service says it is there. A file that is not there ends here, with an error, code 1, file not found, and nothing starts. Second, the permission data allows the start. The kernel reads the data Chapter 29 designs, and the data says the asking program may start this program. A start the data forbids ends here, with the refusal reported in plain words, and the error code for it is Chapter 29's to fix. Both checks pass, and the loader runs.

The loader's eight steps run, by the kernel, the way section 15.1 designed them: read the header, run the first four checks, read the sections, run the last two checks, place the sections, translate the middle form, set up the memory, and jump to the entry point. If the loader's steps fail, at any step, the start fails with them: a file that fails a validity check hands back an error, code 8, wrong kind, the way section 22.1 counted it, and no memory is placed, the way section 9.4 requires. A start that cannot get the memory it needs fails cleanly with an error, code 4, out of memory, the way section 6.4 designed it: the ask, the clean no, the error the program can see, and the program's choice. The start call hands back a number or an error, never both, the way section 7.3 designed errors as values.

When the loader's steps pass, the kernel writes the record entry and hands out the next number, and the start call hands the number back to the program that asked. The record is written only when the loader passes, because a program that never started needs no record and no number.

Now work one start and one stop through, with the naming counted. The asking program is the tester from section 20.2, running as number 2, and the program it asks for is the hello loop from section 4.4, as a complete file of 72 bytes, the way section 9.2 counted it. Two programs are running when the example begins: the shell, number 1, and the tester, number 2.

The tester calls the kernel's start routine and names the program file: `hello`. The kernel runs its two checks. The file exists, and the permission data allows the start. Both pass. The loader's eight steps run, the way section 22.1 counted them for the hello loop: 3 reads, 72 bytes, 6 checks passed, 14 operations walked, 23 native instructions written, 1 slot set up for `count`. The kernel writes the record entry and hands out the next number: 3. The start call hands 3 back to the tester. The hello loop is running as number 3, started by number 2.

The kernel's record now holds three entries: the shell, 23 bytes, the tester, 24 bytes, and the hello loop, 23 bytes. The tester is 24 because its file name, `tester`, is 6 characters: 4 plus 7 is 11, plus 4 is 15, plus 8 is 23, plus 1 is 24. Three entries, 23 plus 24 plus 23 is 70 bytes.

The kernel writes one line to its log, the way section 22.2 designed it: `1794700800 started hello 3`. The line is 26 characters plus the newline, 27 bytes. Chapter 22 counted this line at 25 bytes, before the naming was fixed. The number adds 2 bytes, a space and the digit, and the chapter says so plainly. The boot log Chapter 23 counted changes the same way: the shell's started line now carries its number, `1794700800 started shell 1`, 26 characters plus the newline, 27 bytes, so the four boot lines are 114 bytes, not 112.

The hello loop runs. It prints `hello` three times, and it reaches END. END becomes `call finish`, the way section 10.3 designed it, and the finish routine's five steps run, by the kernel, the way section 15.2 counted them: flush the output, nothing to flush; close the files, none open; free what the program owned, the pile released whole; release the static memory, the name table, the function mapping, and the slot for `count` go back; report the exit, in plain words, to the tester that asked for the program. The report names the number: program 3 ended well. The kernel removes the record entry, 23 bytes go back, and the number 3 is not handed out again until the count wraps. The kernel writes one more line to its log: `1794700800 ended hello 3 well`, 29 characters plus the newline, 30 bytes. Two lines, 27 plus 30 is 57 bytes, for the whole act, from the start to the report.

Now the totals, the whole start and stop, from the request to the report.

| Work | Count |
| --- | --- |
| Kernel calls | 1, the start call naming `hello` |
| Kernel checks | 2, the file exists and the permission data allows it |
| Number handed out | 3, the next number in line |
| Loader steps | 8, the loader's eight steps from section 15.1 |
| Finish steps | 5, the finish routine's five steps from section 15.2 |
| Steps in all | 16: 1 plus 2 is 3, plus 8 is 11, plus 5 is 16 |
| Reads | 3, the header, the code, the dictionary |
| Bytes read | 72, the whole file |
| Checks in all | 8: the kernel's 2, and the validity checks' 6 |
| Native instructions written | 23, from 14 middle-form operations |
| Record entry | 23 bytes, written at the start, removed at the end |
| Log lines | 2, 57 bytes: 27 for the start, 30 for the end |

Read the total honestly, because rule 7 of section 1.5 says to report the number that loses too. The naming costs 2 bytes on each log line, and 23 bytes of record for the run. A kernel that kept no record would save 23 bytes and lose the ability to say what is running. The book keeps the record.

A program ends in three ways, and each one is designed, because an ending the book does not design is an ending the user cannot trust.

First, it ends well. The program reaches END, the finish routine runs its five steps, and the report goes to whoever started the program, naming the number. The hello loop above is the worked example: program 3 ended well, and the tester heard it.

Second, it ends on an error. The error travels up the chain of calls, through the same return path as any value, the way section 7.3 designed it, and the program gives up cleanly, the second of the three ways section 7.3 named. The finish routine runs the same five steps, in the same order, the way section 15.2 designed them, and the report names the error and the number. Work it through on the word counter from section 16.1, started as number 4, with its input file missing. The counter reads the input, gets error code 1, file not found, prints the error, and ends. The finish routine runs: 0 bytes flushed, 0 files closed, the error value freed, the static memory released, and the report goes to the tester, naming the error and the number. The kernel writes one line to its log: `1794700800 ended counter 4 error 1`, 34 characters plus the newline, 35 bytes.

Third, it is stopped from outside. A program asks the kernel to stop a running program, by number, calling the kernel's stop routine, the way it calls the start routine. The kernel checks the permission data first, the way it checks before a start, and Chapter 29 designs the data and the code for a refused stop, the way it fixes the code for a refused start. If the stop is allowed, the kernel stops the program at once. The finish routine does not run, and the book says so plainly, the way section 15.2 said a program killed from outside gets no clean shutdown. The files the program had open are not flushed, and the bytes still waiting in memory are lost. Files already closed are safe. The kernel takes back the memory the record names, and releases the files without flushing them. The report goes to whoever started the program, naming the number and saying the program was stopped. The kernel writes one line to its log: `1794700800 stopped hello 3`, 26 characters plus the newline, 27 bytes.

Say how the user stops a program, because a stop call no one can reach is a stop call that does not exist. The shell gains a command, `stop`, which names a number: `stop 4` stops program 4. The shell calls the kernel's stop routine with the number, and reports the result in plain words. The command is added the way section 21.1 said a command is added: one routine, one entry in the command table. The table gains one entry, 15 commands, and grows by 6 bytes, 4 for the name `stop`, 1 for the length byte, and 1 for the routine number, from 95 bytes to 101 bytes. The user reads the number from the kernel's log, where every start and every end carries it, or from the list of running programs, the way section 24.2 designs it.

The `stop` command needs a number from text, and no routine turns text into a number, so this chapter names one. The routine is `number_of`, in the text routines from section 16.1, the complement of `text_of`, which turns a number into text. It takes text holding whole digits and hands back the number. Text holding anything but digits gives an error, code 8, wrong kind. A number too big to hold gives an error, code 5, number too big. The library grows from 34 routines to 35. Work the command through: the user types `stop 4`. The shell prints the prompt, 1 call to print, reads the line, and splits it, 1 call, giving `stop` and `4`. The routine turns `4` into the number 4 with `number_of`, 1 call, and asks the kernel to stop program 4, 1 kernel call. The kernel stops it. The shell reports it in plain words, 1 call to print: `Stopped program 4.` The command made 4 library calls and 1 kernel call: 1 to print the prompt, 1 to split, 1 to `number_of`, and 1 to print the report.

One honest note about stopping the shell itself. The user can type `stop 1`, and the kernel stops the shell, the way it stops any program. The shell ends without a clean shutdown, and the kernel starts it again, the way section 23.2 designed it, because a machine with no shell has no way for the user to tell it anything. Stopping the shell is allowed, and it is pointless, and the chapter says both.


## 24.2 Fair sharing on 2 cores

Start with the job, in one sentence. Two cores run two programs at once, the rest wait their turn, and every waiting program gets a turn.

The target machine has 2 cores, from section 3.1, and a program runs on one core at a time. When two programs are running, a third waits. Section 3.1 said it plainly: Chapter 24 works inside this ceiling, fair sharing on 2 cores, not a scheduler written for a server. This section is that sharing.

Say what fair means, in plain words, before designing it. Fair means three things. Every waiting program gets a turn, in the order it asked. No program takes a core and keeps it while another waits, once its turn is up. And a program that waits for something, a file, a key, the disk, gives its core to a program that can run, because a core held by a program that cannot run is a core doing nothing.

The kernel keeps a list of programs waiting for a core, in the order they asked. When a core is free, the program that has waited longest runs next, the one at the front of the list. A running program keeps its core until one of three things happens: it ends, it waits for something, or it has run long enough that a waiting program's turn has come.

Say what "long enough" means, because a rule with a hidden number is hidden work. The turn length is 1 second. That is a design choice, stated here, not a measured number: no sharing has been timed on the target machine, and Chapter 31 measures whether a 1-second turn is right or whether another length serves better. The kernel counts the time with `now`, from section 16.2, which gives the seconds since the start of 1970 and does not fail, because the system always has a clock. A turn starts when a program takes a core, and it ends when `now` has moved 2 past the count when the turn started. The count is 2, not 1, because a turn that started late in a second would end almost at once if the count were 1, and a turn must last at least 1 full second. Because `now` counts whole seconds, a program's turn is the rest of the starting second plus one full second: between 1 and 2 seconds of real time, depending on where in the second the turn began. The book states that plainly, because a turn that is 1 second on the clock is not 1 second on the wall.

Say when the kernel checks the turns, because a check that never runs is a rule that never bites. The kernel checks when a program calls it, when a device answers, and when the clock's second changes. Each check asks the same question: has any running program's turn ended, with a program waiting for a core? If the answer is yes, the running program goes to the back of the waiting list, and the program at the front takes its core. If no program is waiting, the running program keeps its core, because a turn ends for a waiting program, not for the clock alone. How the clock's second changing wakes the kernel is the clock driver's work, in Chapter 27, and this chapter does not design it.

A switch between programs is not a pause. The kernel has no garbage collector, so nothing sweeps the heap while the machine waits, the way section 1.3 measured in Python: 2.2 seconds on a linked-list test, against 33 to 50 milliseconds in Go, because the collector stops the world to count the living. In Riza, the program's values sit on its pile and in its static memory, the way section 10.3 described, and the switch moves the core from one program's pile to another's, between operations, never in the middle of one. The switch is a small act, and the book does not time it, because Chapter 31 measures it.

Both cores share one waiting list, and only one core changes the list at a time, so two cores cannot hand out the same turn twice. How one core waits for the other is Chapter 25's design, and this chapter does not design it.

Now work one sharing through, the way section 24.1 worked one start and one stop through, with the turns counted. Three programs and the shell are in the scene, on two cores, and the window runs from the moment the tester starts the two programs until the tester ends. The shell, number 1, is running the build on core 1, and it holds that core when the window opens. The tester, number 2, holds core 2, and it starts the hello loop and the word counter, the way section 14.1 said the build tool runs the tests as step five of the build. The hello loop is number 3, and the word counter is number 4.

The tester starts the hello loop. The hello loop asks for a core, and no core is free, so the hello loop waits, at the front of the waiting list. The tester starts the word counter. The counter asks for a core, and no core is free, so the counter waits, behind the hello loop. The tester has started both programs, and it waits for their reports, so it gives core 2 up. The program that has waited longest is the hello loop, so the hello loop takes core 2.

The hello loop prints `hello` three times and ends well. Core 2 is free. The program that has waited longest is the counter, so the counter takes core 2. The tester's report is ready, so the tester asks for a core, and no core is free, so the tester waits, at the front of the waiting list. The shell is still running the build on core 1.

The shell's turn ends: `now` has moved 2 past the count when the shell's turn started, and the tester is waiting. The shell goes to the back of the waiting list, and the tester takes core 1. The tester records the hello loop's result, and its work for now is done: it waits for the counter's report, so it gives core 1 up, and the shell, which has waited longest, takes core 1 again, for its second turn.

The counter asks the disk for its input file, and it waits, so it gives core 2 up, and core 2 sits idle, because no program is waiting. An idle core sits idle: the kernel does not fill it with busy work. The disk answers, and the counter takes core 2 again, for its second turn, the core it ran on before, because the kernel gives a waiting program the core it ran on last, when that core is free. The counter counts the words, writes the counts, and ends well. The tester's report is ready, so the tester asks for a core, and core 2 is free, so the tester takes core 2, for its third turn, the core it ran on first, because core 1 is busy with the shell. The tester records the counter's result, and it ends well, and the window closes. The shell is still running the build on core 1.

Now the turns, counted. The shell ran twice: once before the tester's turn, once after. The tester ran three times: once to start the programs, once for the hello loop's result, once for the counter's result. The hello loop ran once, and it ended. The word counter ran twice: once before the disk, once after. Eight program turns in all: 2 plus 3 is 5, plus 1 is 6, plus 2 is 8. The core assignments match: core 1 ran the shell, the tester, and the shell again, 3 assignments; core 2 ran the tester, the hello loop, the counter, the counter again, and the tester, 5 assignments; 3 plus 5 is 8.

Four programs waited for a core: the hello loop waited once, the counter waited once, the tester waited once, and the shell waited once. One core sat idle, once: core 2, while the counter waited for the disk. Two programs returned to the core they ran on before: the shell to core 1, and the counter to core 2. One program moved cores twice: the tester, from core 2 to core 1 and back to core 2, because the core it ran on last was busy each time it woke. The preference for the last core is a preference, not a promise: a busy core is a busy core, and the waiting program takes the core that is free.

Say why the preference exists. A program that keeps its core keeps its cache warm, the way section 5.3 described it: each core holds 96 KB of cache, 32 KB for data and 64 KB for instructions, and a program that runs on the same core finds its own instructions still in that cache. A program that moves cores starts cold.

Say what the kernel does not do, because the sharing rule is as much about the refusals as the acts. It does not guess which program matters more. No program has a priority, and no program jumps the list. It does not reorder the list by a program's size, its age, or its file. The order is the order they asked, and the kernel does not second guess it. It does not run a program in the background the user did not ask for. A program runs because someone asked, and the kernel does not ask on its own. And it does not fill an idle core with work the user did not ask for, because an idle core costs nothing to keep.

Now the program that never ends, the loop whose test never fails, from section 7.2. A loop that runs forever runs its turn, goes to the back of the waiting list, and takes its turn again, because its turn ends on time whether the program asks for anything or not. The other programs get their turns in between, because the runaway holds one core for one turn at a time, never both cores, never past its turn. The shell gets its turns, and the user can stop the runaway program from the shell, typing `stop` with the number, the way section 24.1 designed it. The stop is from outside, and the finish routine does not run, and the book says so in both sections, because a runaway stopped from outside loses its unflushed bytes the same way any program stopped from outside does.

Say how the user sees what is running, because a sharing the user cannot see is a sharing the user cannot trust. The kernel's log holds the starts and the ends, the way section 17.1 designed it, each line carrying the number. And the shell can ask the kernel for the list of running programs, calling the kernel's running routine, the kernel's own call, not a new core-library routine. The call hands back a list, one entry per running program, each entry holding the number, the file's name, and the state, running or waiting. The shell gains a command, `running`, which asks for the list and prints one line per program, then a total line. The table gains one entry, 16 commands, and grows by 9 bytes, 7 for the name `running`, 1 for the length byte, and 1 for the routine number, from 101 bytes to 110 bytes. Work the command through, on the scene above, when the tester has started the two programs and the counter is still waiting: the user types `running`. The shell prints the prompt, 1 call to print, reads the line, and splits it, 1 call, giving `running`. The routine asks the kernel for the list, 1 kernel call, and prints one line per program, 4 calls to print: `1 shell running`, `2 tester waiting`, `3 hello running`, `4 counter waiting`, then the total line, `4 programs`, 1 more call to print. Seven library calls and 1 kernel call: 1 to print the prompt, 1 to split, and 5 to print the lines.

The tests grow, the way they grew in every chapter since Chapter 11. Eight new tests belong to this chapter: four for starting and stopping, and four for fair sharing. The starting tests cover the naming, the two checks, the three endings, and the record. The sharing tests cover the waiting list, the turn, the same-core preference, and the runaway. One test belongs to the new routine, `number_of`. The suite grows from 128 tests to 137: 128 plus 8 is 136, plus 1 is 137. The library grows from 34 routines to 35.

This chapter passes the done test from section 3.3, part 5: nothing here claims to run on the target machine, because nothing here is built, and the measured proof is Chapter 31's work, on the real PC. What this chapter fixes is the naming and the sharing, stated plainly enough that Chapter 31 can measure them: the numbers are 4 bytes, the shell is 1, the turn is 1 second, the list is in the order they asked, and the kernel does not guess.

---

Starting and stopping, then, are three acts and one naming. A program starts by one call, two checks, and the loader's eight steps, and the start call hands back a number, in order, from 1. A program ends well, or on an error, or from outside, and the report goes to whoever started it, naming the number. Fair sharing is one list, in the order they asked, and one turn, 1 second, counted with `now`, and the kernel does not guess which program matters more. The record is 23 bytes per program, the log lines carry the numbers, and the user can see what is running and stop what should not run. That is the whole of it, and the next chapter designs the memory the record counts.
