# Chapter 31: Tests on the real PC

Every chapter before this one designed something and ended the same way: the design counts as done when it runs on the target PC, and until then its claims are marked plainly as waiting for the real-PC run. Thirty chapters of waiting end here. This chapter is the run they were waiting for, or rather, it is the run's design: the tests, the way each number is taken, and the lines that say what counts as a fail, all fixed in advance, before any number exists. The lines are fixed in advance on purpose. A fail line drawn after the numbers are known is a line drawn around the numbers, and it proves nothing. Drawn now, the numbers cannot be argued with when they come.

One hard honesty stands at the front, and the whole chapter stands on it. This chapter reports no results. It claims no time, no size, and no score, because the run happens on the built system, on the machine from section 3.1, and a result written before that run would be fiction wearing a number's clothes, the thing section 3.3 forbids. What this chapter fixes is everything except the numbers: what is tested, how it is measured, how many times, what is written down, and what counts as a fail. When the run happens, the numbers go into a record this chapter designs, and the chapters that deferred their proof get their verdicts from it. This chapter's own claims wait for the same run, the same as every chapter before it.

The record is designed here, because the run needs somewhere for its numbers to live. The tester from section 20.2 writes one record per run, a plain text file kept with the system, named with the count `now` gives at the run's start so no run overwrites another. The record holds one line per test: the test's name, the chapter that owns the thing tested, the measured numbers with their method, and the verdict, pass, fail, or not measured. Header lines name the machine, the image the run ran on, and the build's report from section 30.2 that the sizes are checked against. A later run can then be compared against an earlier one, line by line, which is what Chapter 32 needs: section 32.2's rule is score before, score after, every time, and the before and the after both live in records like this one. Without the record, a number from one run cannot be compared with the next, and comparison is the whole point of taking it.

There are two sections. The first designs the three tests: the boot test, the tools test, and the daily use test, with the measurement method fixed once for all of them. The second fixes what counts as a fail, line by line, and what happens after one.

## 31.1 Boot test, tools test, daily use test

Start with the job, in one sentence. The run takes the installed system on the target machine and checks every promise the book made about it, by hand and by program, and writes down what it finds.

First the method, fixed once for the whole chapter, because a method invented per test is a method tuned per result. The system's own stopwatch is the shape section 16.2 fixed: read the time with `now`, run the work, read the time again, and subtract with `elapsed`. Chapter 16 said it in so many words: read the time, run the routine, read the time, subtract, and this chapter uses that shape to measure the routines themselves, the starts, the calls, and the services.

Whole seconds are too coarse for small acts, and the book says so in the open. `now` counts whole seconds, so one ask to the kernel, one switch between programs, one library call, all finish inside a single second and read as nothing. Small acts are measured by the loop method, fixed here. The act runs a counted number of times inside a loop, and the loop's whole time is read by the stopwatch shape. The same loop is then run empty, with the act left out, and its time is read too. The empty loop's time is subtracted, and what is left is divided by the count, and the quotient is the act's share. Work the arithmetic through once, on the method's own numbers. Say the loop runs the act 100,000 times. Say the full loop reads 14 seconds and the empty loop reads 4. The acts took 14 minus 4, which is 10 seconds, over 100,000 runs. Ten divided by 100,000 is 0.0001 seconds per act, a tenth of a thousandth part of a second each. Those two readings, 14 and 4, are the shape of the method, not measurements: no act has been timed yet, and the chapter presents them only so the subtraction and the division are on the page where a reader can check them. The real readings come from the run, and the record holds the count, both readings, and the quotient, so the arithmetic can be checked there too.

Every timed measurement is taken more than once, and the rule is fixed here as a design choice. Each timed measurement is taken 5 times, the count section 1.5 already used for its medians. All 5 runs go in the record. The verdict uses the middle run, the third when the five are put in order, because one run can be a fluke, a disk busy with something else or a core still warm, and the middle run is the honest one: two runs were faster and two were slower, and it is neither the best day nor the worst. The slowest run is reported too, the way section 1.5 requires, because the slowest run is what the user feels on a bad day. A measurement that cannot be taken at all, because a tool is missing or the stopwatch is too coarse even for the loop, is recorded as not measured, and section 31.2 fixes what that means: it is never a pass.

Say who runs what, because the three tests divide by hand. The tester runs what a program can run: the suite, the timed loops, the checks that compare bytes and counts. The boot test and the daily use test need the user's hands: a finger on the power switch, an eye on the screen, a person typing at the prompt. The record says who ran each line, the tester or the user, so a line nobody ran cannot hide among the lines somebody did.

One more rule covers the whole run, from section 3.1 and rule 1 of section 1.5. The run happens on the target machine, the HP All-in-One with the Ryzen 3, the 8 GB, and the spinning drive, and on no other machine. A faster machine would flatter every number and prove nothing about the machine the system is built for. While a test runs, the machine does nothing else: no second job, no other program working in the background, because a number taken on a busy machine is a number about the busyness, not about the work.

Now the boot test, which runs first, before any other test, because everything else needs a machine that boots. One thing is said plainly about the order of the book itself: the tests run on an installed image, the image Chapter 30 designed, put on the machine the way Chapter 33 will design the install. This chapter designs the tests and Chapter 33 designs the install, and the run needs both, so the run waits for both, and the chapter does not pretend otherwise.

The boot test does one thing: the machine is powered on from cold, off and untouched, and nothing is touched again until the shell's prompt appears. Cold means cold: the machine was off, the disk holds nothing in memory, and every read the boot makes comes off the spinning drive, the slow case section 1.4 warned about and refused to quote without measuring.

What is measured is the whole wait, from power to prompt, and it is timed two ways that check each other. The first way is an outside timer: a clock the user already has, a phone or a watch, started at the power switch and stopped at the prompt, costing nothing, the way section 3.2's hard $0 requires. The second way is the system's own account: the boot log's lines from Chapter 23, each stamped with the count from `now`. The two accounts cover different ground, and the chapter says exactly where each one stops. The inside account starts when the clock starts, which is the kernel's second setup act, so the firmware's own time, waking the machine and finding the bootloader, is outside it, and the bootloader's work before the clock is outside it too. The outside timer is the whole truth about the wait. The inside log is the breakdown: it says where the time went after the clock started, stage by stage, the kernel's read and load, the drivers starting, the shell's read and load, down to the prompt, following the reads Chapter 23 counted, so a slow stage is named in the record and not hidden inside a total. The record holds both: the outside total, and the inside stages beside it, and the gap between the total and the sum of the stages is the firmware's and the early bootloader's share, named as such, not lost.

The boot test also reads the small things back. The boot log's four lines are read from the log file once the filesystem service has opened it, and checked against the acts they name: the kernel started, the checks passed 6 of 6, the drivers started, the shell started. The shell answers the `running` command with itself alone on the list, one program, the way section 24.2 designed the list. And the cold boot is repeated, 5 times, the fixed count, with the middle wait as the verdict and the slowest wait reported beside it. A boot that does not reach the prompt is not a slow boot. It is a fail, and section 31.2 says what happens then.

The tools test comes next, and it is the largest of the three. Its first part is the suite itself: all 185 tests, run by the tester on the installed system with `test all`, so the tester's own rule about running only what changed is set aside and every test runs, in the order the chapters added them. Each test's verdict goes in the record under its own name and its owning chapter. The bootstrap test from section 13.2 runs among them, confirming on the installed system what Chapter 30's build already proved at build time: the compiler in the image builds itself and the output no longer changes. A suite that passes in pieces across thirty chapters has to pass whole, in one run, on the real machine, or the pieces were never the proof section 2.5 asked for.

The suite is not the whole of the tools test, because a tool can pass its tests and still be wrong in the hand. So every tool is also exercised as a tool, once, on counted inputs. The file tools and the text tools from Chapters 18 and 19 run through the shell, where Chapter 21 joined them: list a folder, copy a file, move it, delete it, search inside a file for a word, view a file, edit it, compare two files, each on inputs whose sizes are counted and recorded. The developer tools from Chapter 20 each do their one job once: the formatter formats a file that is not in canonical form, the checker checks a program with a known problem in it and must name the problem and its line, the debugger runs a program to a set point and shows the values beside the lines, and the tester runs the suite, which it is already doing. And the build tool builds one counted program from source to finished file, timed by the stopwatch shape, because a build is the heaviest ordinary job the tools do and its time belongs in the record.

Then the measurements the earlier chapters deferred, gathered here by name, each with its chapter and its method. This list is the chapter's debt ledger: every promise of the form Chapter 31 measures it, collected in one place so none of them can be quietly dropped.

The crash tests get their own paragraph, because Chapter 26 called them the filesystem's real test and they are the only tests in this chapter that can break something. A write runs in the order section 26.2 fixed: the new blocks first, never over the old; the folder entry last, in one act; the old blocks freed in the record only. The crash test cuts the power at each step of that order. The cut points are three, fixed here: during the writing of the new blocks, after the new blocks and before the entry, and after the entry has changed. The cuts are made on two files, a small file that fits in one block and a larger file that spans several blocks and more than one run, so the count is 3 cut points times 2 files, which is 6 cuts. After each cut the machine is restarted, the filesystem service rebuilds its free record the way section 26.2 designed, and three things are read back: the file itself, which must be its old version whole or its new version whole; the folder records, which must name nothing that is not there whole; and the rebuilt free record, which must agree with the folder records, run for run. All three readings go in the record for each of the 6 cuts. The power is cut by the user's hand at the switch, at the moment the test names, because a program politely stopping is not a crash, and the chapter will not call it one.

The daily use test is the third test, and it is the human one. The suite proves the system does what the chapters designed. The daily use test asks whether a person can use it, sitting at the shell from Chapter 21, doing ordinary work in an ordinary order. Its script is fixed here, short enough for one sitting, so that two runs of it, before and after a change, can be compared step by step. The machine does nothing else while it runs. The steps, in order:

1. Write a small program in the editor, a program of the user's own choosing at the size of the book's worked examples, and run it from the shell.
2. Build the same program with the build tool, from source to finished file.
3. Run one chapter's tests with the tester, the chapter the user names at the sitting's start.
4. Copy a folder of files with the joined file tools, then search the copies for a word the user names.
5. Start two programs at once and watch them share the two cores, the way section 24.2 designed the sharing.
6. Stop one of the two from the shell, with the `stop` command, and read the report it gives back.
7. Read the logs, the shell's and the kernel's, and find one named act in them: a start, a stop, or a refusal the sitting itself caused.

Each step is timed where a program can time it, by the stopwatch shape or by the tester, and the timings go in the record like any other line. But the record also holds the user's own account, in the user's words, and that account is part of the test, not a comment on it: what felt slow, what confused, what the user had to guess at, what they could not find. The reason is section 2.4's test, asked of the running system at last. Can the user see it? Can the user measure what it costs? Can the user turn it off? A system whose logs cannot be searched by the person who owns them, or whose refusal messages cannot be followed without the book open, has failed a test no timer runs. The daily use test is where that failure would show, and the user's words are the only instrument that can show it.

## 31.2 What counts as a fail

Start with the job, in one sentence. A fail is a promise the book made, broken on the machine the book named, and this section names each one before the run so the run cannot move the line.

The lines, one by one.

A boot that does not reach the prompt is a fail of the boot, full stop. It is not a slow result and it is not a partial pass. No other test runs until it is fixed, because every other test stands on a machine that boots, and numbers taken on a machine that only sometimes boots are numbers about luck.

Any test in the suite failing is a fail of the chapter that designed the thing tested. The record names the test, the chapter, what was expected, and what happened instead, with the measured numbers where the test has them, reported whole and not summarized away. A failure averaged into a percentage is a failure hidden, and this book does not hide them: 184 passes do not soften 1 fail, because the 1 fail is a place where the design, as written, is wrong.

A file in the built image that is bigger than its place is a fail of the layout in Chapter 30. The build should already have caught it, the way section 30.2 designed, and this run rechecks it from the build's report against the places, because an image that only fits by hope is an image that will not fit after the next fix.

The kernel's common path not fitting the 64 KB instruction cache is a fail of Chapter 22's design, stated that way on purpose. The cache is the machine's, from section 5.3, and it does not grow because the design wants it to. The fix belongs to the design: the common path gets smaller, or the design admits what it costs, in the open. Measuring the fit on a machine with a bigger cache would not be measuring this system.

A crash test that finds a file neither whole-old nor whole-new is a fail of Chapter 26's write order. So is a rebuilt free record that disagrees with the folder records, and so is a folder record naming a file that is not there whole. This is the most serious fail in the chapter, and the book says so plainly, because the filesystem's one promise is that a crash loses nothing already written. A system can be slow and be fixed. A system that mixes a file's versions has broken the promise its whole layout exists to keep, and the write order goes back to its chapter before anything else proceeds.

A refusal that hands back any code but 10 is a fail of Chapter 29. So is a guarded act that goes through when the act is not in the program's entry: a start, a stop, a talk, a read outside the folder, any of them. The second is the worse of the two, stated plainly: a wrong code is a wrong message, but an act that goes through is the permission design not working at all, and a security model that lets the forbidden act happen has failed at its one job. And with the record removed, if protection fails to stop a reach outside a program's own memory, that is a fail of Chapter 25 as well, because protection was never permission's to switch off.

Secret bytes that repeat, across asks in one run or across the restart, are a fail of Chapter 29's design, judged at exactly the strength that chapter claimed and no stronger. Chapter 29 said the claim is the shape: no seed, fresh noise, mixed sources, and no test proves bytes unguessable. So a repeat is a fail, because the shape broke. No repeat is not a proof of unguessability, and the record does not call it one: the line reads shape held, at the shape's strength, and nothing more is claimed in either direction.

A measurement that cannot be taken is recorded as not measured, and not measured is never a pass. This is a rule of the run, not a courtesy. A tool missing, a timer too coarse for the act even in a loop, a device not present on the day: the line says not measured, with the reason, and the run's verdict counts the line as open, not as passed. An unrun test is not a pass. A chapter whose proof is a not-measured line still waits for its proof, and the book says so rather than letting silence graduate into a claim.

Now say what is not a fail, because the line has two sides and both were fixed in advance. A number worse than the book hoped, but inside the design as written, is a result, not a fail. The 1-second turn may feel long in the daily use test. A service's first ask may cost what a program start costs, because starting a service is starting a program. The translation's share of a start may be larger than Chapter 10's shape suggested. None of those breaks a promise, because the designs stated their shapes and the shapes held. The numbers go in the record, the user reads them in the daily use account, and Chapter 32 judges them against today's stack, which is where better and worse live. A tie on a standard task is a result. A loss on one is a result. Rule 7 of section 1.5 fixed this before any of it was built: a loss reported as a loss, in the table, with the trade stated. This chapter's job is to produce the numbers honestly. Judging them is the next chapter's.

Say what happens after a fail, because a fail with no road back is only a complaint. The work goes back to the chapter that owns the design: a crash fail goes back to Chapter 26, a refusal fail to Chapter 29, a boot fail to Chapter 23. The fix is made in that chapter, in the open, the way Chapter 24 corrected Chapter 22's count and Chapter 30 corrected Chapter 26's, with the change and its reason written where a reader can see them, never as a quiet edit to code the book does not describe. The image is rebuilt by Chapter 30's build. Then the whole run repeats, all three tests, from the cold boot. A partial re-run after a fix proves only the fixed part, and the unfixed parts may have moved under the fix, so the book does not accept one. The new run writes a new record, and the two records stand side by side: the fail, the fix, and the re-run, each with its date and its numbers, which is section 32.2's score before, score after, applied to the book itself before it is applied to anyone else's stack.

The run's verdict, then, is a shape with five parts, and the run passes when all five hold. The boot reaches the prompt, in all 5 cold boots. Every test in the suite passes, all 185, each under its own name. Every crash test leaves every file whole, old or new, and the rebuilt record agrees with the folder records, at all 6 cuts. Every refusal answers code 10, and no guarded act goes through unallowed. And every measurement in this chapter's list has a number beside it, or an honest not measured with its reason. Anything less is not a pass with reservations. It is the run's true state, written in the record, and the chapters it names go back to work.

The test suite grows with this chapter. Eight new tests cover the run itself, the machinery the numbers pass through, because a method that is not tested is a method that is trusted, and this book tests what it trusts. Two cover the loop method: a loop around a counted act and the same loop empty give back the act's share by the subtraction and the division, on counts a reader can check; and a loop whose act is left out by mistake reads as the empty loop, so the method cannot invent a cost that is not there. One covers the repetition rule: 5 readings of one measurement are recorded whole, and the verdict taken from them is the middle one, with the slowest standing beside it. Two cover the results record: a run writes one line per test, each line holding the name, the owning chapter, the numbers, and the verdict; and a test that could not be run is written as not measured with its reason, and the record's verdict does not count it as a pass. One covers the boot test's two timers: the stages in the boot log and the named gap before the clock account for the outside timer's whole wait, with nothing counted twice and nothing missing. One covers the crash test's own rig: a cut made at a named point is recorded as that point, so a cut that lands late cannot be written up as the cut that was planned. And one covers the daily use script: the seven steps run in their fixed order, and the user's account is written into the record in the user's words, unedited by the tester. That is 8 new tests, and the suite grows from 185 to 193: 185 plus 8 is 193. Each test runs on the target PC, the way section 2.5 demands.

This chapter adds no new routines to the core library. The run uses the routines already named, `now` and `elapsed` above all, and the tester's reporting from section 20.2. The library stays at 39 routines, and the suite grows to 193 tests.

The chapter counts as done when the run it designs has been run on the target PC from section 3.1: the cold boot reached the prompt 5 times, the suite ran whole, the 6 crash cuts left every file whole, the refusals answered code 10, the measurements stand in the record with their numbers or their honest not measured, and the user's account of the daily use sitting is written in it. Until that run happens, this chapter's claims are marked plainly as waiting for the real-PC run, the way part 5 of the done test in section 3.3 requires, and this chapter waits like every chapter before it, by its own rule.

Chapter 32 benchmarks the whole stack against today's, on this machine: size, boot time, RAM, speed, and power, with the score before and the score after, every time, using this chapter's record as the after and Chapter 1's measurements, retaken the same way, as the before. Chapter 33 designs install, update, and recovery: the install this run needed before it could start, the updates that cannot brick the machine, and the recovery for the day a fail is not a wrong number but a machine that will not boot. Chapter 34 designs what comes after v1, and what to never add, and the fails and the honest losses in this run's record are its first inputs: what broke, what was slower than hoped, and what the user said at the prompt are where the next version's work begins.

---

The run is three tests and a set of lines, all fixed before any number exists. The boot test times the cold wait two ways that check each other, the outside timer for the whole truth and the boot log for the breakdown, five times, middle run for the verdict. The tools test runs the whole suite of 185 on the installed system, exercises every tool once in the hand, and collects every measurement the earlier chapters deferred: the translation's share of a start, the three optimizations off and on, the kernel's fit against its cache, the turn and the switch, the services' first asks, the refusals at code 10, the secret bytes' shape, and the crash tests cutting the power at each step of a write, 6 cuts, every file read back whole. The daily use test puts the user at the shell for one fixed sitting of ordinary work, and records the user's own words beside the timers. A fail is a promise broken and named by its chapter, a not measured is never a pass, and a number worse than hoped but inside the design is a result for Chapter 32 to judge, not a fail here. After any fail the work goes back to its chapter, the image is rebuilt, and the whole run repeats. No new routines join the library, and the suite grows from 185 tests to 193.
