# Chapter 26: Filesystem

Part 6 began with the kernel: Chapter 22 designed the small core at the center of the system. Chapter 23 designed the boot, Chapter 24 designed processes and scheduling, and Chapter 25 designed memory in the kernel: one record of runs, kept by the kernel, naming who owns what. This chapter designs the disk the same way: how files live on it, in blocks and runs, named by folder records, and what happens when the power fails mid-write.

Five promises from earlier chapters meet here. Section 23.1 left the kernel file's fixed place, and the way its size is recorded there, to this chapter. Section 23.2 left the shell's fixed place too, and fixed that the filesystem service starts when first needed, not at boot. Section 18.1 left path syntax here, and fixed that a move is a name change in the filesystem's record and the folder record is the truth, with no hidden index. Section 15.2 left file safety on power loss here. And section 22.1 fixed that the kernel asks the service for a file's bytes and never learns the disk's layout.

There are two sections. The first designs the layout on disk: the block, the fixed places, the folder record, the file's runs, the free record, and the path syntax. The second designs crash safety: the write order that keeps a file whole, and one write and two crashes worked through.

One warning, stated up front the way Chapters 4 through 25 stated their own. This chapter designs the filesystem. It does not build it. No disk holds this layout yet, and no claim in this chapter says one does. The chapter claims no measured improvement on real hardware, so no scoreboard table is due. The numbers here are arithmetic on the chapter's own examples, counted by hand. No time is claimed anywhere, because nothing here has been measured on the target machine. The measured proof comes in Chapter 31, on the real PC.

## 26.1 Layout on disk

Start with the job, in one sentence. Files live on the disk in blocks, laid out in long runs where they can be, named by folder records the service keeps, and the few places the machine needs before any filesystem exists are fixed at the start of the disk.

Start with the disk itself, from section 3.1. The target machine's drive is a spinning disk, and it holds 1 TB. One TB the way drives are sold is 1,000,000,000,000 bytes, and the book uses the sold number, stated plainly. Section 3.1 fixed how the disk likes to be read: it reads fastest in long sequential runs, so files are laid out in long runs, there are few files, and a program starts by reading, not by hunting.

The disk is read and written in blocks. A read takes whole blocks, a write writes whole blocks, and nothing smaller is ever asked for. The block size is fixed here, as a design choice: 4,096 bytes. Say why. A block has to be big enough that reading a file is a run of blocks the disk head reads moving forward, the long run section 3.1 wants, and small enough that a small file does not waste much: the most a file can waste is the unused tail of its last block, at most 4,095 bytes. A smaller block wastes less per file and names more pieces; a bigger block names fewer and wastes more on every small file. 4,096 bytes is the balance this book chooses, stated as a choice, not a measurement.

Count the disk in blocks. 1,000,000,000,000 divided by 4,096 is 244,140,625, exactly, with no remainder: 244,140,625 times 4,096 is 1,000,000,000,000. So the disk is 244,140,625 blocks, numbered from 0 to 244,140,624.

Now lay the disk out in order, from the start: the fixed places first, because the boot needs them before any filesystem exists to ask, then the filesystem's own records, then the files.

| Place | Blocks | Bytes | What it holds |
| --- | --- | --- | --- |
| Bootloader's place | 0 to 63 | 64 blocks, 262,144 bytes | The bootloader, stored as native code, the way section 23.1 designed it |
| Kernel's place | 64 to 1087 | 1,024 blocks, 4,194,304 bytes | A size record, then the kernel's file |
| Shell's place | 1088 to 1343 | 256 blocks, 1,048,576 bytes | A size record, then the shell's file |
| Top folder's entry | 1344 | 1 block | One folder entry, for the top folder |
| The general space | 1345 to 244,140,624 | 244,139,280 blocks | The folder records and the files |

Count the fixed places: 64 plus 1,024 is 1,088, plus 256 is 1,344, plus 1 is 1,345 blocks, and 1,345 times 4,096 is 5,509,120 bytes. The general space is what is left: 244,140,625 minus 1,345 is 244,139,280 blocks. Read that cost honestly, per rule 7 of section 1.5: the fixed places reserve those 5,509,120 bytes, of 1,000,000,000,000, whether the places are full or nearly empty, because a place that can move is a place the boot cannot find. The cost is stated, not hidden, the way section 2.4 requires, paid once, for a boot that never hunts.

The bootloader's place is the first 64 blocks. The firmware finds the bootloader where the system image put it: at block 0, the way section 23.1 designed it. The place is fixed at 64 blocks so it never moves: 262,144 bytes is room for the native bootloader, which carries the loader's eight steps, the translator, and the disk and screen drivers, the way section 23.1 counted them. The book claims no size for the bootloader: the place is room, stated as room, and Chapter 30 counts what the image puts in it.

The kernel's place settles the deferral from section 23.1. The place starts at block 64, a fixed block the bootloader knows. The first 8 bytes of the place are the size record: one 8-byte number holding the kernel file's size in bytes. The file's bytes start right after the record, at byte 8 of block 64, and run on in one long run. The bootloader asks the disk driver for the size at the place, reads that many bytes after it, moving forward, and runs the loader's eight steps on them. A size of 0 at the place means no file is there, and the driver answers so, the way section 23.1 designed the failure. Say why the bootloader reads the kernel this way and not through the filesystem: at that moment there is no kernel, no service, and no folder record has been read, so the bootloader needs nothing but the driver, the fixed block, the size at the place, and the bytes after it. The bootloader never reads the filesystem's layout, the way section 23.1 required.

The shell's place is the same shape, smaller: block 1088, an 8-byte size record, then the shell's file in one long run, 256 blocks of room. Section 23.2 said the kernel asks the disk driver whether the shell's file is at its fixed place, and the driver answers from the place's record: a size above 0 is a file there, a size of 0 is no file. The kernel then reads the shell's file the same forward way, and section 23.2 counted its reads: the header, the code, the data section holding the command table, and the dictionary.

After the fixed places comes the filesystem's own record of everything else: the folder records. A folder is a file of entries, one entry per file or folder inside it. The entry is the file-entry record from section 5.2, a name, a size, and a date, with the fields this layout needs added, the way section 2.2 puts binary records first:

| Field | Bytes | What it holds |
| --- | --- | --- |
| Name | 1 plus the characters | The file's or folder's name, a length byte and the characters, the shape section 4.3 fixed |
| Kind | 1 | 1 for a file, 2 for a folder |
| Size | 8 | The size in bytes; for a folder, the size of the folder's own entries file |
| Date | 8 | When the file last changed, the count of seconds from section 16.2 |
| Run count | 1 | How many runs of blocks the file sits in |
| Runs | 16 per run | Per run: the first block, 8 bytes, and the length in blocks, 8 bytes |

The size is 8 bytes because section 5.1 fixed that 8 bytes count to about 18.4 quintillion, so an 8-byte size names any file the disk can hold. The date is 8 bytes because it is the same count `now` hands back in section 16.2. The first run's first block is the file's first block. An entry's length is counted from its own first bytes: the name's length byte says how long the name is, and the run count says how many runs follow, so a reader walks a folder's entries one by one and stops at the folder file's size, which the folder's own entry in its parent names. Section 18.1's `list_folder` hands back the name, the kind, and the size from this entry, and hands back 0 for a folder's size, because a folder's size is the filesystem's business: the entry holds the real size, and the tool reports 0.

Count one entry by hand, for the hello loop's file from section 9.2, 72 bytes, sitting in one block. The name `hello` is 5 characters plus the length byte, 6 bytes. The kind is 1 byte. The size is 8 bytes, the date is 8 bytes, the run count is 1 byte, and one run is 16 bytes. Six plus 1 is 7, plus 8 is 15, plus 8 is 23, plus 1 is 24, plus 16 is 40 bytes.

The top folder has no parent to hold its entry, so its entry sits at its own fixed place, block 1344, with an empty name: a length byte of 0 and no characters. Count it: 1 plus 0 is 1, plus 1 for the kind is 2, plus 8 is 10, plus 8 is 18, plus 1 is 19, plus 16 for its one run is 35 bytes, in one block, the rest of the block unused. The top folder's entries file is a file like any other, found from that entry's runs. Every other folder's entry sits in its parent's entries file, and every file's entry sits in its folder's. There is one chain of records from block 1344 down to every file on the disk.

Now the file's own layout. A file is one long run of blocks where it can be, the way section 3.1 wants files in long runs. Work one through: a file of 10,000 bytes takes 3 blocks, because 2 blocks hold 8,192 bytes and 3 hold 12,288. Its entry names one run: a first block and a length of 3. The last block holds 10,000 minus 8,192, which is 1,808 bytes, and wastes 4,096 minus 1,808, which is 2,288 bytes. The waste is stated, not hidden: every file wastes the tail of its last block, and the hello loop's file wastes 4,096 minus 72, which is 4,024 bytes of its one block. What keeps the waste small in total is section 3.1's shape: few files, so few last blocks.

When a file grows past its run, the new part goes in a new run somewhere free, and the entry names both: a file is a short list of runs, read in order. Work one through: a file named `record` holds 5,000 bytes in two runs. The first run is 1 block, holding 4,096 bytes. The file grew by 904 bytes, and the new part sits in a second run of 1 block, holding 904 bytes, wasting 3,192. Count its entry: the name is 6 characters plus the length byte, 7 bytes, plus 1 for the kind is 8, plus 8 for the size is 16, plus 8 for the date is 24, plus 1 for the run count is 25, plus 2 runs at 16 bytes each, 32, is 57 bytes. One more run costs 16 bytes of entry. A file in many runs has a longer entry and a reader that jumps between runs, which is why the layout hands out long runs first and treats a second run as the exception, not the shape.

The standard tasks from section 1.5 sit on this layout. Searching a 10 MB text file: a file of 10,000,000 bytes takes 2,442 blocks, because 2,441 blocks hold 9,998,336 bytes and 2,442 hold 10,002,432. In one run where the free space allows, the search tool from section 18.2 reads it forward, holding one line at a time. Listing 10,000 files: a folder holding 10,000 entries of 40 bytes each is an entries file of 400,000 bytes, which is 98 blocks, because 97 blocks hold 397,312 bytes and 98 hold 401,408. The list tool reads the folder when asked, the way section 18.1 fixed it: reading the folder is reading those 98 blocks in order. Chapter 31 times both tasks on the real PC, and Chapter 32 compares them against today's stack.

Now the free record: which blocks in the general space are free. It is kept in the same shape as the memory record from section 25.1: runs with a start and a length. Each entry in the free record is one free run: a first block, 8 bytes, and a length in blocks, 8 bytes, 16 bytes per entry. The owner and kind fields from section 25.1 are not carried over, because every run in this record is free by definition. Say why the same shape serves both, because it is section 2.3's one shared form at work: memory and disk are both handed out in runs, taken back in runs, and joined with their free neighbours in runs, so one shape, one walk, and one set of rules serve both records alike. The service hands a run out the way the kernel does in section 25.1: the first free run big enough, split at the low end. Taking blocks back joins free neighbours, the way section 25.1 joins memory runs, so the free space gathers itself back into whole runs instead of filling with small pieces. Nothing is copied and nothing is swept while programs wait: the join is a record change, not a pass over the disk, and no collector stops the world to count the living, the way section 1.3 measured. The one counting pass happens at the service's start, before it answers anything, and section 26.2 designs that start.

The free record is not stored on the disk as a second copy of the truth. It is rebuilt by the service at every start, by reading the folder records, and section 26.2 fixes that as the design and counts its cost. While it runs, the service keeps the free record in its own memory, in its own runs, and changes it as blocks are handed out and given back. The folder records are the truth; the free record is derived from them, the way section 18.1 fixed that the folder is the truth and there is no hidden index.

Now path syntax, settling the deferral from section 18.1. A path is folder names joined by a mark, and the mark is fixed here: `/`. A path that begins with the mark starts at the top folder; one with no mark at the start starts at the folder the program is in. A name alone, with no mark in it at all, names a file or folder in the folder the program is in. The shell starts in the top folder, stated as a design choice: the shell's file sits at a fixed place, not in a folder, so the top folder is where its names begin.

Work one path through: the shell's log file, `logs/shell.log` from section 21.1, named by path from the top as `/logs/shell.log`. The service starts at the top folder's entry, block 1344, reads the top folder's entries file, and finds the entry named `logs`, kind 2, a folder, 39 bytes counted the way hello's entry was counted above. The service reads the `logs` folder's entries file and finds the entry named `shell.log`, kind 1, a file, and that entry's runs name the log file's blocks. Two entries read, one per folder on the path, and the file is found. Named `logs/shell.log` from the top folder, the shell's own naming, the same file is reached by the same two entries. And the log file lives where section 17.1 put it: in a `logs` folder beside the program.

Now say how the service answers the system's questions. The filesystem service is a program, the way section 22.1 designed it: it starts when first needed, not at boot, the way section 23.2 fixed it, takes the next number in line the way section 24.1 hands numbers out, and holds its own runs the way section 25.1 hands runs out. Its own file sits at a fixed place too, the way section 23.2 said, because the kernel must find it before any filesystem exists to ask; Chapter 30 fixes that place and counts it with the rest when the image is built. It owns the disk's records the way the kernel owns the memory record, section 6.1's ownership applied to the disk: the service is the one writer of the folder records, so two programs can never change the same entry at once. Programs reach the records through the core library's file routines from section 16.1, `open_file`, `read`, `read_lines`, `write`, `write_line`, `flush`, and `close`, and the folder routines from section 18.1: the routines ask the service, and the service does the work. The kernel asks the service too, and never learns the disk's layout, the way section 22.1 required.

The kernel's first question is section 24.1's start check: does this file exist? The service walks the path, one folder at a time, and answers: the file is there, or an error, code 1, file not found, the way section 7.3 designs errors as values and section 16.3 fixes the codes. The kernel's second question is section 22.1's ask: hand over a file's bytes. The service reads the folder record, finds the entry, and reads the file's runs in order, in long runs, forward, the way section 9.3's loader reads a file: no hunting, no jumping back. When a program reads a file, the bytes land in a heap run the program asked for, the way Chapter 25's closing said, and the way the copy tool from section 18.1 holds a whole file in memory. The errors are the codes from section 16.3: code 1, the file is not there; code 2, the file cannot be read; code 3, the disk is full, which on this layout means no free run is big enough for a write, the disk's side of the clean no section 6.4 designed for memory.

Work one read through: the hello loop's 72-byte file, read by the service for the loader, in the scene from Chapter 24, where the tester starts the hello loop. The kernel asks the service for the file's bytes. The service reads the folder's entries file first: the folder holding `hello` is small, few files the way section 3.1 keeps them, and its entries fit in 1 block. The entry for `hello` is the 40 bytes counted above, naming 1 run of 1 block. The service reads that block, 1 more block, and hands the 72 bytes to the kernel for the loader's eight steps. Two blocks read, 8,192 bytes off the disk, to deliver a 72-byte file. Read that honestly, per rule 7 of section 1.5: the disk moves in blocks, so a small file costs its whole block, and a folder costs its whole block too. That price is part of the startup cost section 1.4 counted: a program pays for the reads before its first operation runs. Chapter 31 measures what the reads cost in time on the real PC, the way section 2.5 demands.

Say what the layout does not do, because the refusals are the design. There is no hidden index: the folder record is the truth, read when asked, the way section 18.1 fixed it, and no second structure shadows it. There is no second copy of the records: the folder entries are kept once, and the free record is rebuilt from them, not stored beside them. There is no background work: the service answers when it is asked, and the one piece of work it does unasked, rebuilding the free record, happens once at its start, in the open, and section 26.2 counts it. And the records are stated, not hidden, per section 2.4: every field named, every byte counted, in this chapter.

## 26.2 Crash safety in plain words

Start with the job, in one sentence. When the power fails in the middle of a write, every file on the disk is either its old version whole or its new version whole, never a mix, and no folder record names a file that is not there whole.

Say what a crash is, in plain words. A crash is the machine stopping while a write is half done: the power fails, or the machine stops for any reason, between one part of a write and the next. The disk keeps whatever reached it. So after a crash, the disk can hold a mix: the new version's blocks written, the folder entry still naming the old version, the old blocks not yet freed. Section 15.2 fixed the shape of the problem: a machine that loses power gets no clean shutdown, no finish routine runs, and file safety on disk is this chapter's design.

The rule, in plain words, is one sentence: a file is either the old version whole or the new version whole, never a mix, and the folder record never names a file that is not there whole.

How it is done is an order, in three steps, and the order is the whole design. First, write the new version's blocks, in free blocks, never over the old version, which stays exactly where it was, untouched, until the new version is complete on the disk. Second, write the folder entry last, in one act, naming the new blocks and the new size. The entry is small, it sits inside one block of the folder's entries file, and writing that block is one act, the smallest act the disk does. The entry changing is the moment the new version becomes the file. Third, free the old blocks: the service marks them free in its free record, and they join their free neighbours. Nothing is written to the disk for the freeing: the entry no longer naming the old blocks is the whole of it, because the free record is derived from the folder records.

The build tool from section 14.1 already works in this shape at its own level: write under a temporary name, run the tests, move into place only on pass. This section is the same shape one level down, in the filesystem itself, so the move is safe all the way down.

Work one write through: the edit tool from section 19.1 saving a changed `notes.txt`. The file holds 31 bytes, and the edit replaces its second line, making a new version of 27 bytes, the numbers section 19.1 counted. At the tool's level, the edit writes the new text under a temporary name and moves it into place only when the write succeeds, `move_file` replacing the destination, the way section 19.1 fixed it. At the filesystem's level, the same acts run in this section's order. The service hands out 1 free block for the new version, and the new 27 bytes are written into it: 1 block written, and the old `notes.txt` still sits whole in its own block, named by its entry, untouched. The temporary file's entry is written into the folder's block: 1 block written. Then the move: the service writes the folder's block once more, in one act, with the entry for `notes.txt` now naming the new block and the new size, 27, and the temporary entry gone. That one write is the moment the new version becomes `notes.txt`. Then the old block is freed, in the free record only, no write. Count the write: 3 blocks written in all, 1 for the new version's bytes, 2 for the folder's block, and 0 for the freeing.

Work the first crash through. The power fails after the new version's blocks are written, but before the entry changes. On the next start, the service rebuilds its free record from the folder records, and the records say what the disk holds: the entry for `notes.txt` still names the old block and the old size, 31, so the file is the old version whole, exactly as it was before the edit began. Where the new version sits under a temporary name, the temporary file is a file the user can see, holding the new text, to move into place or delete. Where a write had put new blocks down with no entry naming them yet, the rebuild counts those blocks free again, and they are handed out for other work. Nothing is lost but the edit that never finished, and no file is a mix.

Work the second crash through. The power fails after the entry changes, whether before the old blocks are freed or after: it makes no difference, because the freeing writes nothing to the disk. On the next start, the entry names the new block and the new size, so the file is the new version whole, 27 bytes. The old block is named by no entry, so the rebuild counts it free.

Now say how the service knows, on its next start, what state the disk is in, because a rule that cannot be checked after a crash is a rule that holds only while the power stays on. Two designs were open. The free record could be stored on the disk, written last after every change, and checked at the start. Or the free record could be rebuilt at every start by reading the folder records. This chapter fixes the second one, stated plainly. The reason is section 18.1's rule: the folder records are the truth. A stored free record is a second copy of what the folder records already say, and a second copy can disagree with the truth, above all after a crash, which is exactly when it would be read. The rebuilt record cannot disagree, because it is read off the truth itself: the service starts with one free run covering the whole general space, blocks 1345 to 244,140,624, then walks every folder from the top folder down, and cuts out every run any entry names. What is left is free, by construction, including the blocks of every write that never finished.

Count the rebuild's cost honestly, per rule 7 of section 1.5. The service reads every folder's entries file once, at its start, before it answers anything. On the disk this chapter has worked with, that is 2 folders, and 2 blocks read, one per folder's entries file. A disk with more folders pays more: the cost is the folder files' blocks, all of them, once per start. That is the price of having no second copy to trust, paid once, at the start, in the open, not as a pause in the middle of work. Chapter 31 measures the service's start on the real PC.

Say what crash safety costs while a write runs, honestly, per the same rule. A changed file is written twice in space while the write runs: the old version's blocks are held until the entry changes, and the new version's blocks are written beside them, so the edit above held 2 blocks for a 1-block file, until the move freed the old. The entry write is one extra write: the folder's block is written to change the entry, on top of the file's own blocks. And no time is claimed for any of it: what the extra writes cost in time is Chapter 31's measurement.

Say what is NOT promised, stated as plainly as the rule. A file the program never flushed is not promised. Section 15.2 fixed it: the finish routine flushes, every open file's waiting bytes go to disk, and a program killed from outside loses what it never flushed. The filesystem keeps safe what reaches it in this section's order; bytes still waiting in a program's memory never reached the disk, and no layout on the disk can keep what it never received. And the disk itself failing is not a crash this chapter covers: a disk that dies takes its blocks with it, old versions and new alike, and keeping copies on other disks is not designed here.

Four cover crash safety: a write puts the new blocks down before the entry changes; a crash before the entry change leaves the old version whole and the unnamed blocks free; a crash after the entry change leaves the new version whole; and a rebuild after a half-finished write frees the blocks no entry names. The filesystem is one chain of records and one write order. The disk is 244,140,625 blocks of 4,096 bytes. The fixed places come first: the bootloader in blocks 0 to 63, the kernel's file behind its size record in blocks 64 to 1087, the shell's file behind its size record in blocks 1088 to 1343, and the top folder's entry in block 1344. Every file and folder after that is named by an entry in its folder's entries file: name, kind, size, date, and a short list of runs, 40 bytes for the hello loop. A file is one long run where it can be, and more runs when it grows. The free record is the memory record's shape, start and length, rebuilt from the folder records at every start of the service. A path is names joined by `/`, from the top or from the folder the program is in. And a write is three steps in order: the new blocks first, never over the old; the entry last, in one act, and that act is the moment the new version becomes the file; the old blocks freed after, in the record only. So a crash leaves every file whole, old or new, and nothing named that is not there. No new routines join the library, and the suite grows from 145 tests to 153.
