# Chapter 10: The shared middle form

Chapter 9 defined the file: a 33 byte header, a code section, a data section, and a dictionary section. The code section holds the program itself, the operations from the dictionary, in order, in one run. But what exactly are those operations, and how does the machine turn them into its own instructions? This chapter answers those questions. It defines the middle form: the shared form from section 2.3, the one form every part of the system reads.

The middle form is the program as a list of simple steps. Each step does one small thing: put a value on the pile, add two numbers, compare two values, jump to another step, call a function, print a value. Each step is one operation from the dictionary, written in the dictionary's short codes, with its operands right after it. Nothing complicated lives in the middle form. Anything complicated is built from simple steps, not added to them. The reader has already seen it, in the worked examples of sections 4.4 and 7.2. This chapter names it, defines its operations, and shows the step by step path from middle form to the machine's own instructions.

There are three sections. The first says why one middle form serves the language, the tools, and the operating system. The second names the operations and the layout: what the steps are, grouped by what they do, and how they sit in the code section. The third works the hello loop from section 4.4 through the translation to native machine code, operation by operation, and counts the steps.

One warning, stated up front the way Chapters 4 through 9 stated their own. This chapter designs the middle form. It does not build the compiler that writes it. That is Chapter 11. The full formal spec, every operation and every byte in the order it appears, is Appendix C, and the full operation list with final codes is Appendix A. This chapter designs the shape and the groups, and proves the translation on one complete small program. The chapter also claims no measured improvement on real hardware, so no scoreboard table is due. The numbers here are arithmetic on the chapter's own example, counted by hand. The measured proof comes in Chapter 31, on the real PC, with the comparison against today's stack in Chapter 32.

## 10.1 Why one middle form for language, tools, and OS

Section 2.3 made the promise: one shared form from top to bottom. This section says why the promise matters, and what it costs.

Start with what happens today, because section 1.2 already counted it. A program today sits on layers: the app, the runtime, the operating system, the drivers. Each layer has its own form for the same ideas. The language has its tree. The compiler has its own form. The runtime has its bytecode. The operating system has its own structures. The shell has another form still. And every boundary between layers translates between forms: data is copied, checked, and converted at each crossing. Section 1.2 followed one keystroke through that stack, driver to kernel to display server to toolkit to runtime to app and back down again, and counted a string copied four or five times before it reached the screen. Each copy exists because each layer keeps its own private copy of the world in its own private format. The translation is not a detail. It is the work the machine spends most of its time doing.

The middle form removes the translation by removing the boundaries it crosses. In Riza, there is one form, and every part of the system reads it. The compiler writes it, the way Chapter 11 describes. The parser in the editor produces it from the programmer's text, the way section 8.2 described. The loader runs it, the way Chapter 9 describes. The debugger traces it, the way Chapter 17 describes. The shell executes it as scripts, the way Chapter 21 describes. The operating system schedules it, the way Chapters 22 and 24 describe. The formatter reads it and the tester runs it, the way Chapter 20 describes. A program is written once, turned into the shared form once, and then every tool in the system works on the same form. Work done once is done once.

Say plainly what one form buys. One form means one set of tools. A tool that understands the middle form understands every program in the system, because every program is in that form. The formatter does not need a parser for each language. The tester does not need a runner for each runtime. The debugger does not need a separate view of the program's state, because the state is already in the form the tool reads. Each tool is smaller, because it does one job on one form instead of many jobs on many forms. And each tool improves every program at once, because there is only one form to improve.

One form also means one set of checks. The validity walk in section 9.4 checks the middle form once, at the door, before the program runs, and because every layer reads the same form, that one check serves every layer. No layer re-checks the work, because the work arrives in a shape it already trusts. The check is done once, the way the translation is done once.

Why sharing matters more than cleverness is the key point, and section 2.3 stated it first. A clever middle form used by one layer saves that one layer. A plain middle form shared by all layers removes the translation tax at every boundary in the system. The win is not in the form itself. It is in the boundaries removed. Most of the effort in today's stack is spent crossing boundaries between forms: serializing, parsing, converting, copying, checking. Remove the boundaries and the effort goes away with them, even if the shared form itself is nothing special. The shared form does not need to be brilliant. It needs to be good enough for every layer and shared by all of them.

Be honest about the constraint, because it is real, and section 2.3 named it first. One form must serve every layer, so it cannot be tuned for one job alone. A form designed only for the compiler could be rich and expressive. A form designed only for the kernel could be minimal and fast. The shared form has to be both simple enough for the kernel and rich enough for the compiler, and that tension is the design problem. The answer is not to make the form large enough to cover everything, because a large form is a complicated form. The answer is to make the form small and to build complicated things from small steps, the way the middle form already works. A loop is two jumps and a test. A function call is a jump and a return. A list walk is a load, an add, and a jump back. The small steps compose. The form stays small, and the programs built from it can be as large as they need to be.

One more gain belongs here, because it is the gain that pays for the whole design over time. The optimizer in Chapter 12 is written once, on the shared form, and it benefits every program in the system. An improvement to the translator improves every program at once, because every program is translated the same way. A fix to the validity check fixes every program at once, because every program is checked the same way. In today's stack, an improvement to one layer's form helps one layer, and the other layers must be improved separately, each in their own form. In Riza, there is one form to improve, and improving it improves everything.

## 10.2 Middle form ops and layout

The middle form is a list of steps. This section names the steps, grouped by what they do, and says how they sit in the code section. The operation code values shown here are the illustrations from sections 4.2 and 7.1, clearly marked as such, the way those chapters marked them. The final codes come from measured frequency and live in Appendix A.

The steps fall into six groups, plus the step that ends the program.

Loads put a value on the pile. There are four of them, one for each place a value can come from. LOAD_CONST puts a small number on the pile, riding inline right after the operation, the way section 4.3 described: a number like 3 or 100 is already short, so it rides in the code itself. LOAD puts a named value on the pile, from the slot where the name lives, named by its name table number. LOAD_STR puts a string on the pile, from the name table, by entry number. And LOAD_DATA puts a static value on the pile, from the data section, and it answers the question Chapter 9 left to this chapter.

How code addresses data-section values is by position in the data section, the way names are addressed by number in the name table. A LOAD_DATA operation carries a position, counted in bytes from the start of the data section, starting at 0, the same way positions are counted everywhere else in this book. At that position sits a value, and the value starts with one byte saying what kind of value it is, the type byte from section 9.2, followed by the value itself, in as many bytes as its type takes. The operation reads the type byte, knows the kind and the size, and loads that many bytes onto the pile. The loader already checked that every value in the data section fits the kind its type byte names, the way section 9.4 describes, so the translator trusts the type byte the way it trusts the operation code: both were checked at the door, before the program ran. A value in the data section is addressed by where it sits, and its type byte says what it is. No second mechanism, no separate table, no hidden lookup. In the illustrations in this chapter, LOAD_DATA is `12`, following the load family from section 4.2, where LOAD_CONST is `10` and LOAD_STR is `11`. It is an illustration, not the final code, the way the values in section 4.4 were illustrations.

Stores take a value off the pile and put it somewhere. STORE takes the top value off the pile and stores it in a named slot, named by its name table number, the way section 4.4 showed: `count = 0` is a LOAD_CONST followed by a STORE. The slot is fixed: each name has one slot, and the slot holds the name's current value. A store overwrites what was there. The value moves from the pile to the slot, and the pile has one fewer value on it.

Arithmetic and comparison work on the pile. An arithmetic operation takes values off the top of the pile, does its work, and puts the result back. ADD takes two values off and puts their sum back. SUBTRACT, MULTIPLY, and DIVIDE do the same for their own work. A comparison takes two values off and puts back a true or false: LESS_THAN puts back true if the first value is less than the second, the way section 4.4 showed, and EQUAL puts back true if the two values are the same. The pile is the workbench: values go on, work happens, results come back, and the next operation finds its values where the last one left them. A comparison's result is a true or false value, one byte holding 0 or 1, the way section 5.1 defined it, and the jumps read that byte to decide which way to go.

Jumps move the program to another position in the code. JUMP goes to a position, unconditionally, forward or back. JUMP_IF_FALSE goes to a position only if the top value on the pile is false, and takes that value off the pile as it decides. The target is a position in the code section, counted in bytes from the start of the code, starting at 0, the way sections 4.4 and 9.2 counted them. A branch is a jump forward, past the code that runs when the test is true. A loop is a jump back, to the test. The two are one mechanism, and the mechanism is the jump. A jump to a position outside the code section, or to the middle of an operation, is a broken file, and section 9.4 catches it at the door.

Calls and returns move between functions. CALL names a function by number, the way section 7.1 described, and the machine jumps to the function's code, with the function's values already on the pile. The function mapping in the dictionary section says where each function's code starts, the way section 9.2 defined it. RETURN puts the function's result on the pile and jumps back to the caller, and the function's own values are freed in a single act, by moving the stack pointer back, which is what section 6.3 meant when it said stack memory frees itself when a function returns, with no decisions to make. A call is one operation in the code, CALL followed by one byte naming the function. A return is one operation, RETURN, with no operand. The cost of a call is visible, and it is small: the jump, the values, the work, the return.

The last group touches the world. PRINT takes the top value off the pile and prints it. The rest of the group is the core library's work, which Chapter 16 defines: reading a file, writing a file, asking the time, and the rest. These operations are calls into the library, not separate operations for every device and every act, because the middle form stays small by letting the library do the work. A middle form with an operation for every device would grow with every device, and a growing form is a complicated form. The form has one way to call the library, and the library has the rest. The world-touching operations are the only ones that reach outside the program, and they are the only ones whose cost the translator cannot count from the operation alone, because the cost lives in the library routine, not in the step. Section 10.3 says how a call into the library translates.

The last step ends the program. END stops the run, and section 10.3 says what it becomes in the machine's own instructions.

Now the layout: how the steps sit in the code section. The steps sit in order, one after another, with each step's operands inline right after its operation code: a load is followed by the number saying what to load, a jump by the number saying where to jump to, a call by the number saying which function to call. The number of operands an operation takes is fixed by the operation itself, the way section 4.2 said, so a reader always knows how many bytes to read after the code. Positions are counted in bytes from the start of the code section, starting at 0, the way sections 4.4 and 9.2 counted them. There is one way to name a place in the code, and every part of the system uses it.

Each operation code says its own length, the way section 4.2 designed it. The first byte says whether the operation is one byte, two bytes, or in the long tail, and the operation itself says how many operand bytes follow. So a reader can walk forward through the code one operation at a time, without a table and without guessing. That walk is the validity walk in section 9.4, and it is also the walk the translator makes in section 10.3, and the walk the debugger makes in Chapter 17. One walk, three uses, because the form is self describing.

Types and sizes travel with the operations, and that is what makes the translation in the next section mechanical instead of guesswork. A load says what kind of value it loads: for a data-section value, the type byte at its position says the kind and the size; for a constant, the operation code itself says the size; for a name, the compiler knows the type from the definition, because the types are checked at build time, the way Chapter 5 describes and Chapter 11 enforces. An arithmetic operation knows the sizes of the values it works on, because the values on the pile carry their types with them. The translator never has to guess what kind of value it is moving, because the kind is stated, in the operation or in the value. That is the rule from section 5.4, applied to the middle form: nothing is hidden, and the cost of a step is visible in the step itself.

One honest note about what this section does not do. It names the shape and the groups. It does not list every operation, because the full operation list, with final codes from measured frequency, is Appendix A, and the full formal spec, every operation and every byte in the order it appears, is Appendix C. A chapter that listed every operation now would be guessing at the list, and Chapter 3 forbids guessing. What this section fixes is the shape: six groups plus the end, operands inline, positions from 0, lengths self describing, types travelling with the operations.

## 10.3 Middle form to native, step by step

Translation is the step from the middle form to the machine's own instructions. The machine is the Ryzen 3 3250U, and its own instructions are x86-64 instructions: move, add, compare, jump, call, return. The translator reads the middle form, one operation at a time, in order, and writes the native instructions each operation becomes. This section works the hello loop from section 4.4 through the translation, operation by operation, and counts the steps.

First, the scheme, stated plainly, because the translation only makes sense once the reader knows where things live. The pile lives on the machine's own stack. The machine's stack is a pile the processor already has, and the middle form's pile maps straight onto it. Named values live in fixed slots in memory, one slot per name, sized to the name's type, in the static memory from section 6.3. The processor's registers, the small fast storage inside the processor itself, are used briefly for the work between a pop and a push: a value is popped into a register, worked on, and pushed back. The pile is a pile, the slots are slots, and the registers are the workbench.

One more piece of the scheme before the table. A jump target in the middle form is a position in the code section, counted in middle-form bytes. But the native code is not the same length as the middle form, because one middle-form step can become more than one native instruction. So a jump target cannot be copied across unchanged. The translator solves this with two passes. The first pass walks the middle form and counts how many native bytes each step becomes, using the encodings Appendix C fixes, so it knows where each middle-form position lands in the native code. The second pass writes the native instructions, and every jump target is looked up in the table the first pass built. Two passes, one table, and every jump lands where it should.

When the translation happens is part of the design, and it is stated here so no reader has to guess. The translator runs at load time, inside the loader, between placing the code section in memory and starting the program. The file on disk holds the middle form, because the middle form is the shared form the tools, the debugger, and the text view all read. The translation is the last short step, done once per load, and its cost is part of the load, counted in Chapter 31's measurements. Say plainly what this does and does not break. Section 2.2 promised that loading is reading, not re-translating, and the promise was about the parse: the parse never happens at load, because the parse happened once, when the program was written. The translation is not a parse. It does no analysis, no tree building, no error recovery. It reads one step and writes its native instructions. It is computing, and this chapter says so. What it is not is the expensive step the binary form exists to skip: the parse is complicated and slow, the translation is mechanical and short, and the book keeps the complicated step out of the load while admitting the mechanical one in.

Now the hello loop, operation by operation. The middle form is the 14 operations from section 4.4, 24 bytes of code. The native instructions are named by their x86-64 names, with what each one does in plain words. The exact machine-code bytes for each instruction are Appendix C's work, and this chapter does not state them, because stating them here would be guessing at bytes the spec has not fixed. The count in the table is native instructions, not native bytes, because the two are different counts and only one of them is fixed here.

| Position | Middle-form step | Native instructions | Count |
| --- | --- | --- | --- |
| 0 | LOAD_CONST 0 | push 0: push the number 0 onto the machine stack | 1 |
| 2 | STORE name 0 | pop [count]: pop the top value into the slot for `count` | 1 |
| 4 | LOAD name 0 | push [count]: push the value in the slot for `count` | 1 |
| 6 | LOAD_CONST 3 | push 3: push the number 3 onto the machine stack | 1 |
| 8 | LESS_THAN | pop rax; cmp [rsp], rax; setl al; movzx eax, al; mov [rsp], rax | 5 |
| 9 | JUMP_IF_FALSE 23 | pop rax; test rax, rax; jz END | 3 |
| 11 | LOAD_STR entry 1 | mov rax, address of `hello`; push rax | 2 |
| 13 | PRINT | pop rdi; call print | 2 |
| 14 | LOAD name 0 | push [count]: push the value in the slot for `count` | 1 |
| 16 | LOAD_CONST 1 | push 1: push the number 1 onto the machine stack | 1 |
| 18 | ADD | pop rax; add [rsp], rax | 2 |
| 19 | STORE name 0 | pop [count]: pop the top value into the slot for `count` | 1 |
| 21 | JUMP 4 | jmp loop test: jump to the native position of the loop test | 1 |
| 23 | END | call finish: call the loader's finish routine, which ends the program cleanly | 1 |
| Total | 14 operations | | 23 |

Walk through the rows that need more than one native instruction.

LESS_THAN needs five, and each one has a reason. First, pop the top value, the second value, into a register called rax. Second, compare the new top of the pile, the first value, with the register: cmp, compare, sets the processor's flags to say which is bigger. Third, set a byte to 1 if the first value is less than the second: setl, set if less, writes the answer into the low byte of rax. The comparison follows the type the operation carries: signed numbers get the signed compare, unsigned numbers get the unsigned one. Fourth, widen that byte to a full number, filling the rest with zeros: movzx, move with zero extend, turns the byte holding 0 or 1 into a full value holding 0 or 1. Fifth, write the answer back onto the top of the pile: mov, move, stores the register into the pile's top. Five instructions, because the machine's compare works on registers and the values live on the pile.

JUMP_IF_FALSE needs three. First, pop the test value into rax. Second, test the value against itself: test sets the processor's zero flag if the value is zero, and a false value is zero, the way section 5.1 defined it. Third, jump if zero: jz, jump if the zero flag is set, to the native position of END, looked up in the table the first pass built. Three instructions, and the jump lands where it should because the first pass counted where every position lands.

LOAD_STR needs two. First, move the address of the string into rax: mov, move, loads the address of the name table entry for `hello`, which the translator knows because it knows where the name table sits in memory. An address is 8 bytes, and it must travel through a register, which is why this step needs two instructions instead of one. Second, push the register onto the pile. The string's bytes live in the name table, and the length byte at the start of the entry says how many characters follow, the way section 4.3 defined the table shape.

PRINT needs two. First, pop the string's address into a register called rdi, because the rule on this machine is that the first value a function receives goes in rdi. Second, call the print routine from the core library, which Chapter 16 defines: call, which jumps to the routine and remembers where to come back to. The routine reads the length byte, prints that many characters, and returns.

ADD needs two. First, pop the top value into rax. Second, add it to the new top of the pile, in place: add, which adds the register to the value on the top of the pile and leaves the sum there.

The rest are one for one. A load of a constant is a push. A load of a name is a push from its slot. A store is a pop into its slot. A jump is a jump. And END is a call to the finish routine, the loader's own routine that ends the program cleanly, the way Chapter 15 designs shutdown. The loader jumped to the entry point, the way section 9.3 described, so there is no return address waiting, and the program ends by asking the loader to finish it.

Now the totals. Count the middle-form operations: 14, the same 14 from section 4.4. Count the native instructions: 1 plus 1 is 2, plus 1 is 3, plus 1 is 4, plus 5 is 9, plus 3 is 12, plus 2 is 14, plus 2 is 16, plus 1 is 17, plus 1 is 18, plus 2 is 20, plus 1 is 21, plus 1 is 22, plus 1 is 23. Fourteen middle-form operations become 23 native instructions. Nine of the fourteen translate one for one. The most any one step needs is five. The average is 23 divided by 14, which is just over one and a half native instructions per middle-form step, under two.

Read the result honestly. The translation is not one for one, and the chapter does not pretend it is. It is under two native instructions per middle-form step, and nine of fourteen steps are exactly one for one. The steps that need more than one are the steps that work on two values at once: a comparison needs five because the machine's compare works on registers and the values live on the pile. That is the price of the pile, and it is a small price, because the pile is what makes the middle form simple to write, simple to check, and simple to walk. The optimizer in Chapter 12 can shrink the multi-instruction steps: a comparison whose result is only ever tested by the next jump can skip the widening and the write back, because the jump can read the compare's flags directly. But that is the optimizer's work, not the translator's. The translator's job is to be mechanical and trustworthy, and the count above is what that costs: 23 instructions for 14 steps.

Why the translation is mechanical is the point of the whole chapter, and it follows from everything before it. The middle form already holds everything the translator needs: the types from Chapter 5, the sizes, the positions, and the ownership from Chapter 6, already checked by the compiler. The translator does no re-analysis, because there is nothing left to analyse. It does no second parse, because the parse happened once, when the program was written. It does no guessing, because the kind of every value is stated. It reads a step and writes its native instructions. It does not need to know what the program means, only what each step does, and each step says what it does.

Say plainly what the translator does not do, because the list is as much a part of the design as the table. It does not optimize. That is Chapter 12, and the optimizer only does what pays. It does not check types. The compiler already did, in Chapter 11. It does not manage memory. Ownership already decided it, in Chapter 6, and the compiler already checked it. Each of those is someone else's job, done once, before the translator runs. The translator is small because the middle form is small, and small is the point: a translator the reader can hold in their head is a translator that can be trusted. Section 2.4's rule, small core and no hidden work, applies to the translator the way it applies to everything else.

The operating system uses the same form, and that is the last point of the chapter, because it is the point section 2.3 was building toward. The kernel's own code is written in the same language and translated the same way, the way Chapter 22 designs it. The kernel is a program like any other to the translator: middle form in, native instructions out. There is no second translator for the kernel, no special form for the operating system. One form, one translator, every program in the system, from the smallest script to the kernel itself. That is what one shared form from top to bottom means in practice: the top and the bottom are the same form.

Two honest notes close the section, the same kind the earlier chapters closed with. The first is about what the count is not. The count is native instructions, not time. This chapter claims no timings, because none were measured on the target machine, and Chapter 3 forbids numbers without a method. How long 23 instructions take to run, and how long the translation takes at load, are measurements, and they belong to Chapter 31, on the real PC, with the comparison against today's stack in Chapter 32. The second note is about what the table is not. It is not the output of a translator, because no translator exists yet. The compiler in Chapter 11 builds the first one. The native instructions above were written by hand, following the scheme in this section, to show what the scheme produces. When the compiler exists, it will produce translations like this one automatically, and Chapter 11 tests every opcode to prove it.

The middle form is defined now: one shared form for the language, the tools, and the operating system; six groups of operations plus the end, with operands inline, positions from 0, and types travelling with the operations; and a translation to native code that is mechanical, counted, and honest about its cost. The next chapter builds the compiler that writes this form: the smallest compiler that works, built first in an existing language, with a test for every opcode.

---

The shared middle form is the program as a list of simple steps, and it is one form for every part of the system: the compiler writes it, the loader runs it, the debugger traces it, the shell executes it, and the kernel schedules it, so work done once is done once. The operations fall into six groups plus the end, loads, stores, arithmetic and comparison, jumps, calls and returns, and the library calls that touch the world, with data-section values addressed by position and their type byte saying what they are. The translation to native code is mechanical: the pile lives on the machine's stack, named values live in fixed slots, and the hello loop's 14 middle-form operations become 23 native instructions, nine of them one for one and none more than five, counted by hand and stated honestly. The translator does not optimize, does not check types, and does not manage memory, because each of those is someone else's job, done once before the translator runs. The form is defined. Chapter 11 builds the compiler that writes it.
