# Chapter 23: Boot: from power on to prompt

Part 6 began with the kernel: Chapter 22 designed the small core at the center of the system, what it does and what it does not do, with no layers for the sake of layers. But a kernel on the disk is a file, and a file does not run itself. Something has to start it, and something has to start that something. This chapter designs the chain from power on to the prompt: the firmware that wakes the machine, the bootloader that starts the kernel, the kernel's first acts, and the first program it starts, the shell, whose prompt is the first thing the user sees.

There are two sections. The first designs the bootloader: the smallest program that runs first, the loader's eight steps run before there is a kernel to run them. The second designs the first process: what the kernel does once it is running, and how the shell starts and the prompt appears.

One warning, stated up front the way Chapters 4 through 22 stated their own. This chapter designs the boot. It does not build it. No bootloader exists yet, no kernel exists yet, and no claim in this chapter says either does. The chapter also claims no measured improvement on real hardware, so no scoreboard table is due. The numbers here are arithmetic on the chapter's own examples, counted by hand: steps, reads, checks, lines, bytes. No time is claimed anywhere in this chapter, because no boot has been measured on the target machine, and Chapter 3 forbids numbers without a method. The measured proof comes in Chapter 31, on the real PC, and the boot test is the first test it names.

## 23.1 Bootloader

Start with the job, in one sentence. The bootloader is the smallest program that runs first, and its one job is to start the kernel.

Before the bootloader, the firmware. The firmware is the program built into the hardware, on a chip on the board, and it is not Riza. It came with the machine, it was written by the machine's maker, and Riza does not control it. The book says so plainly, because the boot does not start from nothing: it starts from the one piece of the machine that belongs to the hardware maker.

When the power comes on, the firmware runs. It wakes the machine: it checks that the memory is there and working, it checks that the devices are present, the screen, the keyboard, the disk, and it looks for a program to run on the disk. The firmware finds the bootloader where the system image put it, the way Chapter 30 builds the image, and it runs the bootloader. The firmware's job ends there. It hands the machine to the bootloader and steps aside. Any screen the firmware shows while it works, the maker's logo or the hardware check, is the firmware's work, not Riza's.

Say what the bootloader is written in, because the answer has one exception in it, and the exception needs its reason. The bootloader is written in Riza, in the same language, in the same middle form, and it is translated by the same translator, the way section 10.3 described: middle form in, native instructions out. But it is translated once, when the system image is built, the way Chapter 30 builds it, and it is stored on the disk as native machine code, not as middle form. The reason is the firmware. The firmware runs native code, and it runs nothing else. There is no translator running yet to translate the bootloader at load, because the translator is a program, and no program runs before the bootloader. So the bootloader meets the firmware on the firmware's terms: native code on the disk, in the form the firmware runs. Everything after the bootloader, the kernel, the shell, every program, is middle form on the disk, translated at load, the way section 10.3 designed it. The bootloader is the one program stored as native code, and the reason is that it is first.

The bootloader carries what it needs to do its job, in native form: the loader's eight steps, the translator that turns the kernel's middle form into native code, the disk driver that reads the kernel's file, and the screen driver that reports a failure. Read the cost honestly, because rule 7 of section 1.5 says to report the number that loses too. The loader lives twice: once in native form in the bootloader, and once in middle form in the kernel, which runs the loader's eight steps for every program it starts, the way section 22.1 said. The disk driver and the screen driver live twice too, once native in the bootloader and once in middle form in the system, the way section 23.2 counts below. One source, two stored forms, the way section 21.1 said a tool's routine lives twice, once in the shell's file and once in the tool's own file.

What the bootloader does is the loader's eight steps, run before there is a kernel to run them. Section 15.1 designed the eight steps for a program, and section 22.1 said the kernel runs them for every program it starts. Here they run for the kernel itself, and the bootloader runs them, because the kernel cannot start itself. The kernel's own startup is the same shape at a bigger scale, the way Chapter 15 closed and Chapter 22 said: loading, checking, placing, translating, and jumping to the entry point.

First, read the header. The bootloader asks the disk driver for the kernel file's size and the first 33 bytes, at the fixed place on the disk where the kernel's file lives. The fixed place is Chapter 26's design: the filesystem's layout fixes a place for the kernel's file and records the file's size there, and the bootloader asks the driver for the size and the bytes at that place. The bootloader never reads the filesystem's layout. It reads one file at one fixed place. From the 33 bytes, the bootloader knows the version, the entry point, and where each section sits and how big it is, the way section 9.1 fixed the header. If the driver reports nothing at the place, the file is not there, and the bootloader reports error code 1 and stops, the way this section says below. The bootloader has no checks before the loader's steps, because there is no kernel yet to run them, so the first read is the check that the file is there.

Second, run the first four validity checks, the ones that need only the header and the file's size: the magic, four bytes compared with R I Z A; the version, one byte compared with the dictionaries the bootloader knows; the sizes, one addition, the header plus the three sections adding up to the file's size exactly; and the bounds, each section inside the file and no two overlapping. Section 9.4 defined these checks and their order, cheapest first, and the bootloader runs them before it reads anything else, because a file that fails one of them is not worth reading further.

Third, read the sections. One read per section that has anything in it, in file order: code, data, dictionary. The reads move forward through the file, the way section 9.3 described, so the disk head moves forward with them, never jumping back. This is the shape section 3.1 said the spinning drive reads fastest.

Fourth, run the last two validity checks, the ones that need the sections. The references: one forward walk of the code, checking every name number against the name table, every jump target against the code section and the operation boundaries, every function number against the function mapping, and the entry point against the code section. The value shapes: one forward walk of the data section, reading each type byte and checking the value that follows it fits the kind it names. Both checks walk data the bootloader has already read. Nothing is read twice.

Fifth, place the sections, and only now, because section 9.4 said a file that fails a check gets no memory placed. The code section goes where the kernel runs from. The data section goes into static memory, the place section 6.3 named for values that live for the whole run. The name table and the function mapping are held for the run. The comments are left on disk, because they are for the text view, not for the run, and the bootloader does not pay for what the run does not use.

Sixth, translate the middle form to native code, inside the bootloader, the way section 10.3 designed it. Two passes. The first pass walks the middle form and counts how many native bytes each step becomes, using the encodings Appendix C fixes. The second pass writes the native instructions, and every jump target is looked up in the table the first pass built. The translation is done once per load, and its cost is part of the load.

Seventh, set up the memory the kernel needs. The pile is set up on the machine's own stack, the way section 10.3 described, empty, ready for the kernel's values. The static memory is set up with the slots for the named values, one slot per name, sized to the name's type, in the static memory from section 6.3. The kernel's memory is ready before its first operation runs.

Eighth, jump to the entry point. The bootloader jumps to the position in the code the header named, and the kernel's first operation runs. The kernel is running, and the bootloader's job is done.

Now count the kernel's file, the way section 9.2 counted the hello loop's file, and say plainly where the counting stops. The header is 33 bytes, always, in the nine fields section 9.1 fixed:

| Field | Bytes | What it holds for the kernel |
| --- | --- | --- |
| Magic | 4 | The letters R I Z A, the file's name tag |
| Version | 1 | The dictionary version the kernel was written against |
| Entry point | 4 | The position in the code where the kernel starts |
| Code offset | 4 | Where the kernel's code section starts in the file |
| Code size | 4 | How many bytes of kernel code |
| Data offset | 4 | Where the kernel's data section starts in the file |
| Data size | 4 | How many bytes of kernel data |
| Dictionary offset | 4 | Where the kernel's dictionary section starts in the file |
| Dictionary size | 4 | How many bytes of kernel dictionary |
| Total | 33 | |

Check the total: 4 plus 1 is 5, plus 4 is 9, plus 4 is 13, plus 4 is 17, plus 4 is 21, plus 4 is 25, plus 4 is 29, plus 4 is 33. The header's values are the kernel's own: its entry point, its section offsets, its section sizes, stated in its header the way every file states them. The sections follow in their fixed order: the code section, the data section, and the dictionary section.

Say plainly what this chapter does not count. The kernel is not written yet, and section 22.1 claims no size for code that is not written yet, so this chapter claims none either. The kernel's code section is as big as the kernel's code, and the kernel's code is not written. What the chapter counts is the shape, not the size: the bootloader reads the header, 33 bytes, and then one read per section that has anything in it. The code section and the dictionary section always have something in them, so the bootloader always reads at least three times: the header, the code, and the dictionary. The data section is read only if it holds anything, so the reads are three or four, and the count waits for the kernel to be written. The steps are exact, eight, and the checks are exact, six, and the passes are exact, two, and the bytes are the file's own size, whatever the header's numbers add to. Chapter 30 counts the kernel's file when the image is built, the way section 9.2 counted the hello loop's.

Say plainly what the bootloader does not do, because the list keeps it small, the way section 2.4 requires. It does not start programs for the user. It starts the kernel and nothing else, and the kernel starts everything after that. It does not run the shell. The shell is a program, and the kernel starts it, the way section 23.2 designs it. It does not read the filesystem's layout. It reads one file at one fixed place, and the layout is Chapter 26's work, not the bootloader's. It does not check for updates. Nothing in the boot reaches for the network, and the update service is a program, the way section 22.1 said, run when the user asks it to. It does not run anything in the background: the bootloader is the first program, and it runs, starts the kernel, and is done.

It does not print anything on a good boot. The screen stays as the firmware left it until the shell prints the prompt, the way section 23.2 designs it. The bootloader has nothing to say until something fails, and printing for the sake of printing is work the user did not ask for. Read the trade honestly, because rule 7 of section 1.5 requires it. The user waits in the dark from power on to the prompt, with nothing on the screen to say the machine is working, and the wait is as long as the boot takes. Chapter 31 measures the boot on the real PC, so the user knows how long the dark lasts.

Now the failure runs, because a bootloader that only works when the kernel file is good is a bootloader the user cannot trust. The kernel file fails a check, and the bootloader reports the failure in plain words on the screen, through the screen driver, and stops. There is no kernel to report to, no program to run, and no shell to type into, so the screen is the only place the report can go. The machine sits at the message until the user turns it off or restarts it, and the recovery, putting a good kernel file back on the disk, is Chapter 33's work.

Work two failures through, with the messages the user sees. The kernel file's first four bytes are not R I Z A. The header is read, the first check fails, and the bootloader writes one line on the screen: `Error 8: the kernel file is not a Riza file.` The code is 8, wrong kind, the code section 22.1 used for a file that fails the validity checks. The message names the file and the check, in plain words, and nothing runs, and no memory is placed, the way section 9.4 requires: no instruction executes, no memory is placed, no program starts.

The kernel file needs a dictionary version the bootloader does not know. The header is read, the version byte says 3, and the bootloader knows up to version 1. The second check fails, and the bootloader writes one line: `Error 8: the kernel file needs dictionary version 3, and this bootloader knows up to version 1.` The code is 8 again, because the file is of a kind this bootloader cannot read, and the message names the versions, so the user knows what is wrong and the builder knows what to fix. The bootloader does not guess what a newer version means, because guessing at a file format is how a program runs the wrong code, the way section 9.4 said.

The third failure is the file that is not there. The disk driver reports nothing at the fixed place, or the place cannot be read, and the bootloader writes one line: `Error 1: the kernel file was not found.` The code is 1, file not found, the way section 16.3 fixed it. Nothing is read, nothing is checked, and the loader never runs, because there is no file to load.

One more piece of the bootloader's work: the debug log layer. Section 17.1 said the layer is set up by the loader, and only after the first four validity checks pass: a file that fails the checks is not a program, and gets no log, and the loader's plain-words report is the record. The bootloader is the loader for the kernel, so the bootloader sets the layer up, after the first four checks pass, and writes the first line, which file was started, and after the last two checks pass, the second line, the checks and how many passed. The lines are held in the buffer, 1,024 bytes, the way section 17.1 designed it, and the log file opens when the filesystem service first runs, the way section 23.2 says below. The buffer holds the early lines until then, and section 23.2 counts them.

## 23.2 First process

Start with the job, in one sentence. Once the kernel is running, it sets up the machine and starts the shell, the first program, and the prompt is the shell's prompt.

The kernel's first acts are its setup, in order, and the order is the design.

First, set up its own memory. The kernel builds the record of who has what, the record section 22.1 said it keeps. The record starts by taking stock of the machine's 8 GB, from section 3.1: the kernel's own code and data are marked used, because the kernel is running in them; the bootloader's memory is released back to free, because the bootloader's job is done and it never runs again until the next boot; and the rest of the memory is free, waiting to be handed out. Ownership runs through the record the way section 6.1 requires: the kernel owns the record, and a program owns what it was handed until it gives it back.

Second, set up the clock. The kernel reads the machine's clock, so the time routines from section 16.2 have a clock to read. The clock is hardware, and only the kernel talks to hardware, the way section 22.1 said, so the time lives with the kernel from the first moment it runs. The time service, the part that keeps the clock set, is Chapter 28's design, and it does not start at boot: `now` asks the kernel, the way section 22.2 worked the call through.

Third, set up the devices, by calling the drivers Chapter 27 designs, one driver at a time, in order. The screen driver first, so the kernel can report anything that goes wrong from here on, in plain words on the screen. The disk driver second, so the shell's file can be read, because the shell lives on the disk. The keyboard driver third, because the user types only after the prompt appears, and the prompt appears after the shell starts. The network driver last, because nothing at the prompt needs the network, and section 3.2 says the system works with no network at all. Four drivers, four calls, one at a time, each finished before the next starts, the way section 27.2 designs one driver at a time.

Say plainly what the kernel loads here, because two of the four were already loaded once. The kernel loads its own copy of each driver, in the middle form, translated at load, the way section 10.3 designed it. The disk driver and the screen driver were already loaded once, in native form, by the bootloader, because the bootloader needed them before the kernel existed. The kernel loads them again, in the middle form, because the kernel runs every program through the loader, and the loader translates the middle form. Read the cost honestly, because rule 7 of section 1.5 requires it: the disk driver and the screen driver are loaded twice, once native by the bootloader and once in middle form by the kernel. One source, two stored forms, the same price section 23.1 counted for the loader.

Fourth, start the first program, the shell. The kernel asks the disk driver whether the shell's file is at its fixed place, the way section 22.1's first check asks whether the file exists. The driver answers from the place's record, the way Chapter 26 designs it. If the answer is no, the boot stops with error code 1, the way this section says below. If the answer is yes, the loader's eight steps run on the shell's file, the way section 15.1 counted them. There is no permission check on the first start, and the reason is stated plainly: the boot starts the shell by design, not by permission. Permissions govern what programs may do once the system is running, and the shell is the first program, started by the boot itself, with no program asking and no user yet to allow or forbid. The permission data Chapter 29 designs governs the first program the shell starts, not the shell.

Count the shell's file by its reads, because the reads are exact even though the bytes are not. The shell's file is read in four reads: the header, 33 bytes; the code section; the data section; and the dictionary section. The data section is not empty, because it holds the command table, 95 bytes, the table section 21.1 counted, loaded once with the program into static memory, the way section 6.3 described. The code section and the dictionary section are the shell's own sizes, and the chapter claims no total for a file whose code is not written yet.

The shell runs. It prints the prompt, two characters, `> `, with print from section 16.1, the way section 21.1 designed it, and it waits for the user to type. The boot is done.

Now the totals, the whole boot, from power on to the prompt.

| Work | Count |
| --- | --- |
| Firmware acts | 3: wake the machine, check the hardware, find and run the bootloader |
| Bootloader steps | 8, the loader's eight steps for the kernel |
| Kernel setup acts | 6: memory 1, clock 1, drivers 4 |
| Shell start steps | 9: 1 ask to the disk driver, 8 loader steps |
| Prompt | 1, the shell prints `> ` |
| Steps in all | 27: 3 plus 8 is 11, plus 6 is 17, plus 9 is 26, plus 1 is 27 |
| Reads | 7 or 8: the kernel's file in 3 or 4, the shell's file in 4 |
| Validity checks | 12: 6 for the kernel's file, 6 for the shell's file |
| Programs started | 2: the kernel, by the bootloader, and the shell, by the kernel |

Read the table honestly, because a count of steps is not a measurement of time, and the chapter does not pretend it is. Twenty-seven steps from power on to the prompt is a count of acts, not a time, and how long 27 steps take on the target machine is a measurement, and it belongs to Chapter 31, on the real PC. What the table shows is enough for the design: the boot is a short chain, each link doing one job, with no layer the boot does not need, the way section 22.2 said. Compare it with the shape section 1.4 counted for today's startup: an interpreter that reads its binary, its startup files, and parts of its standard library from scattered places on the disk before the first line runs. The Riza boot reads two files, the kernel's and the shell's, each in a few long reads, moving forward, and the comparison is in the shape of the work, not in a time this chapter has not measured.

Now the boot's log, because the record is part of the design. The bootloader set the kernel's log layer up after the first four checks passed, the way section 23.1 said, and the kernel writes one line for each act of the boot. The lines sit in the buffer, 1,024 bytes, the way section 17.1 designed it, and the log file opens when the filesystem service first runs, because writing a file needs the service, and the service starts when it is first asked for, the way this section says below. The boot's four lines are these:

| Line | Text | Bytes |
| --- | --- | --- |
| 1 | `1794700800 started kernel` | 25 characters + 1 newline = 26 |
| 2 | `1794700800 checks passed 6 of 6` | 31 characters + 1 newline = 32 |
| 3 | `1794700800 drivers started 4` | 28 characters + 1 newline = 29 |
| 4 | `1794700800 started shell` | 24 characters + 1 newline = 25 |
| Total | | 112 bytes |

Check the total: 26 plus 32 is 58, plus 29 is 87, plus 25 is 112. The four lines are 112 bytes, and the buffer holds 1,024, so the boot's log fits in the buffer with 912 bytes to spare, and nothing is lost while the log file waits for the service. The time is the count section 16.2 gave, 1,794,700,800 at the start of 15 November 2026, and the lines are the same shape as the hello loop's log from section 17.1, because the kernel's log and the program's log are the same shape, written by the same layer. The shell writes its own first line in its own log, `logs/shell.log`, the way section 21.1 said: `1794700800 started shell`, 24 characters plus the newline, 25 bytes. The shell's line waits in the shell's buffer the same way, until the service opens the file.

What happens when the shell ends is the next part of the design, because a machine whose shell never comes back is a machine the user cannot talk to. The user types `exit`, and the shell ends the way section 21.1 said: the finish routine runs its five steps from section 15.2, flush, close in reverse order, free what the program owned, release the static memory, and report the exit in plain words. The shell is gone. The kernel starts it again, by running the loader's eight steps on the shell's file a second time, and the prompt appears again. The new shell is a fresh start: the old shell's values were freed at shutdown, the way section 6.1 requires, and the new shell holds nothing from the old one except the log, which is the same file, `logs/shell.log`, with a new started line, one per session, the way section 21.1 said. The kernel starts the shell again because a machine with no shell has no way for the user to tell it anything.

What if the shell's file is missing at boot? The kernel asks the disk driver whether the shell's file is at its fixed place, and the driver answers no. The boot stops, and the kernel writes one line on the screen, through the screen driver: `Error 1: the shell file was not found.` The code is 1, file not found, the way section 16.3 fixed it. There is no shell to type into and nothing the kernel can do but report and stop. The machine sits at the message until the user turns it off or restarts it, and the recovery, putting a good shell file back on the disk, is Chapter 33's work. The same shape holds if the shell's file fails a validity check: the check names the failure, the kernel reports it in plain words, and nothing runs, the way section 9.4 requires.

Say plainly what the kernel does not do at boot, because the list is the design. It does not start any other program. The shell is the only program the kernel starts. It does not read any file but the shell's. The kernel's file was the bootloader's read, and the shell's file is the kernel's only read. It does not check for updates. Nothing in the boot reaches for the network, and the update service runs when the user asks it to, the way section 22.1 said. It does not run anything in the background. There is no background yet: the machine at the prompt is the kernel, the drivers, and the shell, and nothing else.

Say when the rest starts, because a reader will ask. The filesystem service starts when it is first needed, not at boot. The kernel asks the service for a file's bytes, the way section 22.1 said, and the first time a program asks for a file by name, the kernel starts the service, from its fixed place, and asks it. Starting the service at boot would mean reading a second file before the prompt, for a service nothing at the prompt has asked for, and the boot reads only what the prompt needs. The time service starts the same way, when it is first needed, and the network stays quiet until a program asks for it.

Four cover the bootloader: the bootloader loads the kernel's file and the kernel runs; a kernel file with the wrong magic is reported on the screen, and nothing runs; a kernel file with an unknown version is reported, and nothing runs; and a good boot prints nothing before the prompt. Four cover the first process: the kernel starts the shell, and the prompt appears; the kernel starts the four drivers in order, and the log holds the order; the shell ends and the kernel starts it again; and a missing shell file is reported on the screen, and the boot stops. That is 8 new tests, and the suite grows from 120 to 128: 120 plus 8 is 128. Each test runs on the target PC, the way section 2.5 demands.
