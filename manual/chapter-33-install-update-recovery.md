# Chapter 33: Install, update, recovery

Chapter 30 designed the system image, one file holding the whole system. Chapter 31 designed the run that proves the installed system, which waits for an install to stand on. Chapter 32 designed the scoreboard, and fixed that an update is a change like any other, owing a before and an after. None of that reaches the user until the image is on the machine, the machine is kept current, and a break can be repaired. This chapter designs those three jobs.

Four deferrals from earlier chapters are settled here. Chapter 23 left recovery here twice: a kernel file that fails its checks, and a shell file missing at boot, both end at a plain message, and putting a good file back is this chapter's work. Chapter 28 designed the update service's run, and left two things here in so many words: the order that makes a system update unable to brick the machine, and what happens when a swap is interrupted halfway. Chapter 14 fixed the package level part, check first, then replace, and left the machine level part here. And Chapter 31's run needs the install this chapter designs before its first test can run.

One warning, stated up front the way Chapters 4 through 32 stated their own. This chapter designs the install, the update order, and the recovery. It performs none of them. No install has run, no update has swapped a file, and no machine has been recovered. The numbers here are arithmetic on the layout Chapter 30 counted: blocks, bytes, places. No time is claimed anywhere.

## 33.1 Install on the Mint PC

Start with the job, in one sentence. The install takes the image file from Chapter 30 and writes it to the target machine's disk, at the places Chapter 30 counted, in an order that never leaves a place naming a file that is not there whole, and it is done when the machine boots to the shell prompt on its own.

Say the starting state plainly, because the install begins from the only system the machine has. The target PC runs Linux Mint today, the system from section 3.1, and Riza does not exist on it yet. So the install is run from the running Mint system: the user has the image file on the machine, however it got there, on a stick, on a disk, or fetched at the user's own ask, because section 3.2 assumes no network and the install needs none. The user starts the installer from the Mint desktop. The installer is the one piece of the project that is not a Riza program, and the consequence is named plainly: it runs on Mint, so it is written for Mint, in Python, the language the bootstrap compiler was first built in. It is a tool for the crossing, kept small on purpose. Once Riza is installed, the crossing is not needed again for ordinary life: updates and swap backs are the update service's work, and only a machine that cannot boot sends the user back to it, under section 33.3.

First, check the image before anything is written. The installer reads the image file and runs the six validity checks from section 9.4, magic, version, sizes, bounds, references, value shapes, on every file the image holds: the kernel, the shell, and the four services at their fixed places, read out of the image at the size each place's record names, and the general space files, the core library, the compiler, the build tool, the developer tools, named by the top folder's record the build wrote last. The permission record is counted too: the first form from section 30.1, 8 entries, 67 bytes. A file that fails a check stops the install before a single block of the disk is touched, with the file and the check named in plain words, the way section 9.4 designs a refusal. A bad image installs nothing.

Second, the disk question, faced in the open before any write. Riza's layout owns the disk it is installed on: the fixed places begin at block 0, and the general space runs to the end of the disk, the way section 30.1 counted, so there is no corner of this disk where the Mint system survives as a system. Installing Riza on this disk ends the Mint system on it: the bootloader's place is overwritten, Mint cannot boot again from this disk, and Mint's files are not reachable afterward, because the records that will name files on this disk are Riza's records from this install on. What the user wants to keep must be copied off the disk first, to a stick, another disk, or another machine. The image file itself must survive the install too, kept on the install medium or another disk, because section 33.3 makes the kept image the spare copy of the whole system. The installer does not begin the write until the user confirms that state in so many words: that the disk may be taken whole, and that what the user wants to keep is already off it. An installer that surprises the user about their own disk fails section 2.4's test, can the user see it.

Third, write, following the layout exactly, in the crash safe order section 26.2 designed: bytes first, and the record that names them last. The bootloader's native code goes to blocks 0 to 63, the one place with no size record, because the firmware finds it at block 0 and runs it as it lies, the way section 23.1 designed. Each fixed file goes to its counted place: the kernel to blocks 64 to 1087, the shell to 1088 to 1343, the filesystem service to 1345 to 1600, the time service to 1601 to 1664, the network service to 1665 to 1792, and the update service to 1793 to 1920. For each, the file's bytes are written first, in one long run after the place's first 8 bytes, and the 8 byte size record is written after them, last, in one act, so at no moment does a place name a file that is not there whole: before the record lands, the place reads as size 0, no file there; after it lands, the file it names is complete beneath it. Then the general space files are written, in the blocks the build's layout assigned them, and the permission record as the file `permissions` in the top folder, the 67 bytes counted above. The top folder's entry, at block 1344, is written last of all, the rule section 30.2 fixed for the build applied to the disk: the record that names a thing is written after the thing. The free record is not written at all: the filesystem service rebuilds it at its first start, from the folder records, the way section 26.2 designed, its first free run from block 1921, section 30.1's corrected count. Count the fixed writing in the open: the fixed region is 1,921 blocks, blocks 0 to 1920, which is 1,921 times 4,096, which is 7,868,416 bytes, 64 plus 1,024 is 1,088, plus 256 is 1,344, plus 1 is 1,345, plus 256 is 1,601, plus 64 is 1,665, plus 128 is 1,793, plus 128 is 1,921. The general space files add their own blocks, at the sizes the build's report names: the install claims no file size of its own.

Fourth, read back. The installer reads back everything it wrote, place by place and file by file, and compares it against the image, byte for byte. The read back is part of the install, not an extra the user may skip, because a silently wrong write fails later, at boot, in front of the user, instead of now, in front of the installer. A place whose read back differs stops the install with the place named, and the disk is not called installed. Only when every byte matches does the installer report the install done, in plain words, and tell the user to restart. The first boot after the install is Chapter 23's boot, unchanged, and the install's done condition is that boot: the machine is installed when it boots to the shell prompt on its own, with no help from Mint, and that prompt is also where Chapter 31's run begins.

Say what the install does not do. It does not share the disk: the layout takes it whole, stated above, and a machine that must keep Mint is a machine this install is not for. It does not copy the user's files back: what the user kept lives where the user kept it, and bringing it home into the general space is the user's work at the shell, after the boot, with the file tools. And it does not run again on its own: a later repair is section 33.3's job, not a quiet reinstall.

## 33.2 Updates that cannot brick the machine

Start with the job, in one sentence. An update replaces a working version with a checked newer one in an order where, at every instant, the machine holds either the whole old version as current or the whole new one, and this section fixes that order step by step, settling the deferral Chapter 28 left here.

Define the word first, in plain words. A bricked machine is a machine that cannot boot to a prompt the user can act from: the power works, the disk spins, and nothing the user can do at the machine brings it back. Updates are the ordinary way machines get bricked, because an update rewrites the files the boot itself reads. So the order is designed against that one failure: no interruption may leave the machine unable to boot, and where one can leave a file unusable, a whole version must already be held that recovery can put back.

The pieces are already on the page, and the order is built from them. Chapter 28 fixed the update service's run: the user names what to update and the place to fetch from, the package is fetched or read from a file the user has, and the nine checks run before anything is placed: the package magic, the description with the name matched, the dependencies, and the six validity checks from section 9.4 on the program file inside, 1 plus 1 plus 1 plus 6, which is 9. Section 14.2 fixed that a failed check leaves the old version running. Section 26.2 fixed the write order underneath everything: new blocks first, never over the old; the record that names them changed last, in one act; the old blocks freed in the record only. And section 29.1 fixed that asking the update service to run is a guarded act, refused with code 10 like any refused act.

Take a program in the general space first, the common case, because its swap is section 26.2's shape unchanged. The new version's file is written whole into free blocks in the general space, while the old version sits in its own blocks, named by its folder entry, current and untouched. Only when the new file is complete on the disk and has passed its checks does the swap begin, and the swap is a record change, not a copy: the folder entry is written once, in one act, naming the new file's blocks and its new size, and that one write is the moment the new version becomes the program, the way section 26.2 designed the moment for every file. The old version's blocks are not freed: the old file is kept, named as the old version in the record of installed packages, the way Chapter 28 fixed, until the user removes it. The record names both versions and which one is current.

Now walk the interruptions for that swap, the way Chapter 31's crash tests walk section 26.2's order. Power lost while the new file is being written in the general space: nothing current has changed, the old version is the program, whole, and the half written new file is unfinished work; the free record's rebuild at the service's next start counts its unnamed blocks free again, and the service's log names the work it had begun. Power lost during the record change: the folder entry is one write of one block, and it is either the old entry or the new one, both whole, because the entry names only files already complete beneath it. Power lost just after: the new version is current and whole, and the old version still sits in its blocks, kept. At no point is the current version a mix, and at no point is there no current version: it is section 26.2, applied by the service instead of by an edit tool.

A file at a fixed place is harder, and the chapter says why in one sentence: a fixed place has no folder entry to swing, only the place itself, its 8 byte size record, and the file after it, read directly by the bootloader or the kernel before any service exists to ask. The shell, the four services, and the kernel are such files. Chapter 28 fixed the shape at the level it owned; this chapter fixes the order in full, six steps, the same for every fixed place.

First, the new file waits whole in the general space, fetched as part of the package, extracted, and proven by the six checks, while the working file in the place is untouched and the machine runs on it. Second, the old file is copied out of its place into the general space and read back against the place, byte for byte, and it is named in the record of installed packages as the old version. Third, the place's size record is written as 0, in one act. From this moment the place officially holds no file: a reader at the place finds size 0 and reports no file there, the answer section 23.1 designed. Fourth, the new file's bytes are written into the place, in one long run after the record. Fifth, the place is read back and compared against the checked file in the general space, byte for byte, and the six checks run again on what the place now holds, so the file is proven in its place, not merely written toward it. Sixth, the size record is written with the new file's size, in one act, last. That write is the swap's moment: before it, the place holds no current file; after it, the place holds the new file whole, under its true size.

Walk the interruptions for those six steps. Power lost during the first or second step: the place was never touched, the old file is current and whole, and the machine boots and runs exactly as before. Power lost during the fourth or fifth step, the dangerous window: the size record says 0, so no reader can mistake the half written bytes for a file. The boot, or the kernel's ask, finds no file at the place and stops with the plain message Chapter 23 designed, naming the file, and the recovery entry section 33.3 designs: the machine has not bricked, because both whole versions sit in the general space, and recovery's repair is to write one of them into the place, bytes first and size record last, and read it back. The same holds when the file being swapped is the update service's own, because a service's records on the disk are its truth and survive it, the way Chapter 28 fixed. Power lost just after the sixth step: the new file is current and whole, the old one is kept, and the update is simply done. So the fixed place promise is one step weaker than the general space promise, stated rather than hidden: a fixed file's swap has a window where the place is empty by design, never half full and lying about it, and the way back is already stocked with both versions.

The kernel is the sharpest case, because the boot reads it before any service runs, and the bootloader itself is sharper still. The kernel swaps by the six steps above, unchanged: its place is blocks 64 to 1087, it sits behind its size record, and the zero in the third step is what protects the boot. A kernel whose size record does not match its bytes is never booted, because in the window the record says 0, no file there, and the bootloader reports the failure in plain words and stops: the failure run section 23.1 designed, with section 33.3's recovery entry added, not a dead end. The honest limit is stated at its strength: the kernel swap is the one act in the update design whose interruption is answered by recovery rather than by an untouched old version still in its place, and in exchange no interruption can produce a mixed kernel that boots and misbehaves: the boot sees the old kernel whole, or no kernel and a message, or the new kernel whole, and nothing else is possible. The bootloader has no size record at all: the firmware runs the native code at block 0 as it lies, so no zero can guard its window. A system update that carries a new bootloader therefore writes it last of all the system's files, after every other file is in place and proven, from a file checked six ways in the general space, and reads the place back byte for byte before the update is called done. If that write is interrupted, the chapter does not pretend: the firmware may find a bootloader that does not run, the machine cannot even show the recovery message, and the way back is the firmware's own boot choice to the install medium, where section 33.3's recovery rewrites the place from the kept image. That is the single interruption whose answer begins outside the machine's own disk, confined to the one file that has no record to guard it, with the risk reported in the service's plain words before that file is touched.

A system update, several files at once, runs the swaps in an order chosen so every stopping point still boots: the services first, then the shell, then the kernel, then the bootloader last. Each file's swap is the six steps, complete before the next begins, and each intermediate state is a whole set of files that pass their checks at load, because every file is accepted by its six checks, whichever version it is. An interruption between files leaves a machine that boots on the files it has, some old, some new, each whole, and the service's log names which were swapped and which were not, so the user can finish the update or ask for the swap back below.

The way back is the same mechanism as the way forward, because a kept old version the user cannot return to is only a souvenir. The user asks the update service to make the kept old version current again. For a program in the general space, that is the record change run in reverse: the folder entry is written once, naming the old file's blocks, and the newer version becomes the kept one, named in the record in its turn. For a fixed place, it is the six steps with the old file as the incoming file: it waits whole in the general space where the swap kept it, the current file is copied out and kept, the record is zeroed, the old bytes are written, read back, and the size record lands last.

Two standing rules close the section. The old version is kept until the user removes it: the update service never removes it, on no schedule and for no reason of its own, the rule from sections 14.2 and 28 carried through every swap above. And every update owes Chapter 32's scoreboard a before and an after, the rule section 32.2 fixed for every change that could move a number. The update service's report says so in plain words, naming the debt, and the update is not finished until the after run is recorded beside the before. Updates are asked for, never automatic: the service works only when the user asks, the ask is guarded by the update act in the permission record, and there is no background check and no quiet fetch anywhere in this section, full stop.

## 33.3 Recovery when something breaks

Start with the job, in one sentence. Recovery returns a broken system to a known whole state, the state the install wrote or a later update proved, by repairing the system's fixed places and its records from the kept image, and it never touches the user's programs and files to do it.

Say what recovery is for, from the failures the earlier chapters named. A machine that will not boot: the kernel file failed its checks or is not at its place, the shell file is missing, section 23.2's stopped boot, or section 33.2's two hard windows, the kernel's empty place and the bootloader's interrupted write. A damaged file or record: a fixed file whose bytes no longer match its size record. A bad update the user wants undone: the swap back from section 33.2. And a permission record damaged or removed: removed is a designed state, not damage, because section 29.1 fixed that removing the record turns permission off while protection stands, but a record the user wants back is recovery's to restore, never wider than the user approves.

Recovery starts from outside the installed system, and the assumption is stated plainly: the user kept the install medium, with the image file on it. Keeping the image is a rule of keeping the system, fixed here: a user who keeps it can always rebuild the fixed places exactly as they were. The recovery tool is the installer's companion on that medium, and runs where the installer ran, because the machine it repairs may have no running Riza to repair itself with. There are two doors into it. The user can boot the medium directly, by the firmware's own boot choice, the only door when the bootloader itself is damaged. And the boot itself offers the other door: when the bootloader's checks fail, or the kernel finds the shell's file missing, the plain message on the screen no longer ends at the failure. It names the failure, the way Chapter 23 designed, and beneath it the recovery entry: restart from the install medium to repair. Never a silent halt, and never a message that leaves the user with nothing to do next. When the machine still boots to Riza, the smaller repairs do not need the medium at all: a swap back is the update service's work from inside, and a permission record is restored through the shell, the way section 29.1 designed. The medium is for the machine that cannot reach its own tools.

What recovery does is in order, starting with learning, not writing.

First, read the logs. Every program's log layer from section 17.1 has been writing one line per act into a `logs` folder beside the program, and those files are the account of what the system did before it broke: the boot's four lines, the update service's record of which files it swapped, the kernel's refusal lines. The recovery tool reads the disk's folder records directly, walking from the top folder's entry at block 1344 the way section 26.1 designed the walk, and it reads the log files before it changes anything. A repair that rewrites first can destroy the only account of the failure. If the logs cannot be read, the tool says so and goes on: the checks below do not depend on them.

Second, check the fixed places against their size records and against the kept image. For each place with a size record, the kernel's, the shell's, and the four services', the tool reads the record and the bytes under it and compares both with the image's copy of that file, unless the update service's log names a newer proven version there, held whole in the general space, which is then the comparison. The bootloader's place, with no size record, is compared byte for byte against the image's native code. A place that does not match is damaged, or is the empty window of an interrupted swap, and the tool names it in plain words before repairing anything.

Third, repair by rewriting, in the install's order: bytes first, and the size record last, in one act, then read back and compare. A damaged fixed file is rewritten from the kept image, or, where the update log shows the place should hold a newer version, from that version's whole file in the general space, the user choosing when both exist. An interrupted swap is finished or undone the same way: both whole versions are already on the disk, the way section 33.2 stocked them, the user picks the one to make current, and the place is rewritten from it. The bootloader's place is rewritten from the image's native code and read back byte for byte, there being no record to write last.

Fourth, the records. The free record needs no repair on the disk, because it is not stored on the disk: the filesystem service rebuilds it at every start by reading the folder records, the way section 26.2 designed, so recovery's part is only to confirm the folder records can be walked whole from block 1344 down, every entry naming runs that are there. The permission record is handled under its own rule. If it is missing, permission is off by design, and recovery reports that state rather than treating it as breakage. If it is damaged, or the user asks for it back, recovery offers the image's first form, the 8 entries and 67 bytes from section 30.1, restored as the file `permissions` in the top folder. Any entry wider than the first form is written only when the user names it and approves it: recovery never widens any entry on its own, because section 29.1 fixed that entries are the user's writing, not programs' and not tools'.

Fifth, report, in plain words: what was broken, what was rewritten and from which copy, what was checked and left alone, and what was not touched. Then the machine restarts, and recovery's done condition is the install's: the machine boots to the shell prompt on its own.

Now the bright line, stated plainly. Recovery repairs the system: the fixed places, their size records, and the permission record. It never writes to the user's programs and files in the general space, and it does not rewrite the folder records that name them; its only general space act is reading, logs and kept versions. That separation is what Chapter 30's layout was built for, so the whole system can be rewritten from the image without one byte of the user's work at risk. A full system recovery is not a data loss, and the user can be told so before it runs, in those words.

The worst case, stated at its strength, the way Chapter 29 stated its limits. If the disk itself is damaged beyond the records' ability to describe it, if the folder records cannot be walked or the top folder's entry is gone, recovery cannot invent the truth the records held. Then recovery's answer is a fresh install, section 33.1, onto a sound disk, and the user's files survive only if they were copied elsewhere before the disk failed. The book does not pretend a design survives dead hardware. What the design promises is narrower: every break the software itself can cause, a bad write, an interrupted swap, a damaged record, a failed check at boot, has a named way back that costs the user nothing they had saved.

Close by tying the three sections together, because they are one design at three sizes of job. The install writes the system once, in the order bytes first and the record last. An update changes it one checked file at a time, in the same order, with the old version kept until the user says otherwise. Recovery returns it to a known whole state, from the kept image, in the same order again. One write order, learned once, is the whole of how this system is born, changed, and healed, and a user who understands section 26.2's three steps already understands this chapter.

The test suite grows with this chapter. Eight new tests cover the install, the update order, and recovery. Two cover the install: an image with a file made to fail a validity check is refused with the file and the check named, and nothing is written to the disk; and a completed install reads back byte for byte against the image at every place, and the machine then boots to the prompt on its own. Four cover updates: a power cut while a new program version is being written in the general space leaves the old version current and whole; a power cut inside the fixed place window, after the size record is zeroed, leaves the place reading as no file there, never a half file booted, and recovery restores a whole version from the copies on the disk; a swap back makes the kept old version current by the same record change; and a package that fails any of its nine checks places nothing and leaves the old version untouched. Two cover recovery: a fixed file damaged in its place is rewritten from the kept image, bytes first and size record last, read back matching, and the machine boots to the prompt; and a permission record restored by recovery takes the image's first form at 67 bytes, no entry wider without the user's own approval, while every file in the general space is left byte for byte untouched. That is 8 new tests, and the suite grows from 201 to 209: 201 plus 8 is 209. Each test runs on the target PC, the way section 2.5 demands.

This chapter adds no new routines to the core library. The install and recovery tools run on the crossing, outside Riza, and the update service uses what is already designed. The library stays at 39 routines, and the suite grows to 209 tests.

The chapter counts as done when its three jobs have run on the target PC from section 3.1: the install writes the image and the machine boots to the prompt on its own, an update swaps a program and a fixed file through a power cut at each point in the order and the machine boots after every cut, and a damaged fixed file is recovered from the kept image with the general space untouched. Until that run happens, the chapter's claims are marked plainly as waiting for the real-PC run, the way part 5 of the done test in section 3.3 requires.

Chapter 34 designs what comes after v1, and what to never add: an update mechanism that works unasked is on its never list from Chapter 28, and this chapter adds its own candidates: an installer that takes a disk without the user's plain confirmation, and a recovery that widens a permission entry on its own. The appendices, A to F, hold the final numbers, the fixed places and sizes this chapter used among them.

The install, the update, and the recovery are one write order at three sizes. The install checks the image six ways before anything is written, states that it takes the disk whole and waits for the user's word, writes the bootloader to blocks 0 to 63, each fixed file bytes first with its size record last, the general space files, the permission record, and the top folder's entry last of all, then reads everything back against the image and is done only when the machine boots to the prompt on its own. An update runs its nine checks before anything moves, swaps a program by one record change and a fixed file by six steps with the size record zeroed before the dangerous window and written last after it, keeps the old version until the user removes it, offers the swap back by the same mechanism, and owes the scoreboard a before and an after; the kernel's window is answered by recovery and the bootloader's by the install medium, both stated at their strength. Recovery reads the logs first, checks every fixed place against the kept image, rewrites what is damaged bytes first and record last, restores the permission record at its first form and never wider without the user's word, and never touches the user's files in the general space, which is why a full system recovery is not a data loss. No new routines join the library, and the suite grows from 201 tests to 209.
